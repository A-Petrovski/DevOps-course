## Часть 1. Практические задания (Чекпоинты)

### 1. Подготовка виртуальной машины

1. Создайте виртуальную машину (ВМ) с **Ubuntu Server** в VirtualBox.
2. В настройках сети ВМ выберите режим подключения **Сетевой мост (Bridged Adapter)**, чтобы ВМ получила отдельный IP-адрес в вашей локальной сети.
3. Запустите ВМ и подключитесь к ней по протоколу SSH с основного компьютера:

```bash
ssh username@<IP_АДРЕС_ВМ>
```

**Разбор параметров:**
* `username` — имя пользователя, созданного при установке Ubuntu Server.
* `<IP_АДРЕС_ВМ>` — локальный IP-адрес виртуальной машины.

Пример использования: `ssh -p 22 amp@192.168.1.55`

---

### 2. Установка сервера и создание главной страницы

Обновите индекс пакетов, установите веб-сервер Nginx, узнайте IP-адрес сервера и сгенерируйте стартовую HTML-страницу:

```bash
sudo apt update
sudo apt install nginx -y
hostname -I
echo "My private IP is $(hostname -I)" | sudo tee /var/www/html/index.html
sudo systemctl reload nginx
```

**Разбор флагов и команд:**
* `apt update` — обновляет локальный список доступных пакетов из репозиториев.
* `-y` — автоматически подтверждает установку пакета без интерактивного запроса.
* `hostname -I` — выводит все назначенные сетевым интерфейсам IP-адреса.
* `|` (конвейер / pipe) — перенаправляет стандартный вывод левой команды на стандартный ввод правой.
* `sudo tee /var/www/html/index.html` — записывает входящий поток текста в файл с правами суперпользователя (необходимо, так как обычное перенаправление `>` не работает с `sudo`).
* `systemctl reload nginx` — перечитывает конфигурацию и обновляет рабочие процессы без разрыва текущих соединений.

Пример использования: `echo "<h1>Server $(hostname)</h1>" | sudo tee /var/www/html/index.html`

### 3. Настройка локального DNS (файл hosts)

Для обращения к серверу по доменному имени без покупки публичного домена добавьте статическую привязку на **основном компьютере** (хосте).

* **Linux / macOS:**
```bash
sudo nano /etc/hosts
```

* **Windows (PowerShell от имени Администратора):**
```powershell
notepad C:\Windows\System32\drivers\etc\hosts
```

Добавьте в конец открытого файла строку:

```text
192.168.1.55 my-secure-server.local
```

**Разбор параметров:**
* `192.168.1.55` — актуальный IP-адрес вашей виртуальной машины (подставьте свой).
* `my-secure-server.local` — локальное доменное имя, которое будет разрешаться в указанный IP-адрес.

Пример использования: `echo "192.168.1.55 my-secure-server.local" | sudo tee -a /etc/hosts`

### 4. Создание самоподписанного SSL-сертификата

Создайте защищенную директорию для закрытого ключа и сгенерируйте пару ключ + сертификат на 365 дней:

```bash
sudo mkdir -p /etc/ssl/private
sudo chmod 700 /etc/ssl/private
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/nginx-selfsigned.key \
  -out /etc/ssl/certs/nginx-selfsigned.crt
```

> **Важно при заполнении полей:** в строке `Common Name (e.g. server FQDN or YOUR name)` обязательно укажите ваш домен `my-secure-server.local`.

**Разбор флагов и параметров:**
* `mkdir -p` — создает директорию и все недостающие родительские каталоги без ошибок, если папка уже существует.
* `chmod 700` — разрешает чтение, запись и вход в директорию только владельцу (`root`).
* `openssl req` — запускает утилиту создания запросов на сертификат и самоподписанных сертификатов.
* `-x509` — указывает создать самоподписанный сертификат стандарта X.509 вместо запроса на подпись (CSR).
* `-nodes` (*no DES*) — сохраняет закрытый ключ без шифрования паролем, чтобы Nginx мог запускаться автоматически без ручного ввода пароля.
* `-days 365` — задает срок действия сертификата в днях.
* `-newkey rsa:2048` — одновременно генерирует новый закрытый ключ по алгоритму RSA длиной 2048 бит.
* `-keyout` — путь для сохранения закрытого ключа.
* `-out` — путь для сохранения публичного сертификата.

Пример использования: `sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 -subj "/CN=my-secure-server.local" -keyout /etc/ssl/private/nginx-selfsigned.key -out /etc/ssl/certs/nginx-selfsigned.crt`

### 5. Настройка Nginx для работы с HTTPS

Создайте файл виртуального хоста `/etc/nginx/sites-available/my-secure-server`:

```bash
sudo nano /etc/nginx/sites-available/my-secure-server
```

Запишите в него конфигурацию с принудительным редиректом с HTTP на HTTPS:

```nginx
# Блок для HTTP, выполняющий редирект на HTTPS
server {
    listen 80;
    server_name my-secure-server.local;

    return 301 https://$host$request_uri;
}

# Основной блок для HTTPS
server {
    listen 443 ssl;
    server_name my-secure-server.local;

    # Пути к самоподписанному сертификату и закрытому ключу
    ssl_certificate /etc/ssl/certs/nginx-selfsigned.crt;
    ssl_certificate_key /etc/ssl/private/nginx-selfsigned.key;

    root /var/www/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

Активируйте конфигурацию, проверьте синтаксис и перезапустите службу:

```bash
sudo ln -s /etc/nginx/sites-available/my-secure-server /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl restart nginx
```

**Разбор директив и флагов:**
* `listen 80` / `listen 443 ssl` — указывает порты для приема входящих HTTP и шифрованных HTTPS соединений.
* `return 301 https://$host$request_uri` — возвращает постоянный редирект (код 301) с сохранением исходного хоста и пути запроса.
* `ssl_certificate` / `ssl_certificate_key` — задают пути к файлам публичного сертификата и закрытого ключа.
* `try_files $uri $uri/ =404` — проверяет существование запрошенного файла, затем директории, и при их отсутствии возвращает ошибку 404.
* `ln -s` — создает символическую ссылку в директории `sites-enabled` для включения сайта.
* `nginx -t` — тестирует синтаксис всех конфигурационных файлов Nginx без перезапуска сервиса.

Пример использования: `sudo nginx -T | grep server_name`

### 6. Проверка работы HTTPS

1. Откройте браузер на основном компьютере и перейдите по адресу `http://my-secure-server.local`.
2. Убедитесь, что произошел автоматический редирект на `https://my-secure-server.local`.
3. На странице предупреждения о безопасности (из-за недоверенного самоподписанного сертификата) нажмите **Дополнительно** -> **Перейти на сайт**.
4. Убедитесь, что отображается текст с вашим приватным IP-адресом.

Пример использования (проверка через консоль): `curl -Ik https://my-secure-server.local`

### 7. Настройка редиректов и обработка контента

#### 7.1. Редирект на страницу с картинкой

Создайте страницу `picture.html`, загрузите изображение и обновите главную страницу:

```bash
echo '<img src="/images/my_cat.jpg">' | sudo tee /var/www/html/picture.html
sudo mkdir -p /var/www/html/images
sudo apt install curl -y
sudo curl -L -o /var/www/html/images/my_cat.jpg https://http.cat/images/200.jpg
echo "My private IP is $(hostname -I) <br> <a href='/picture'>Show Picture</a>" | sudo tee /var/www/html/index.html
```

**Разбор флагов:**
* `-L` — заставляет `curl` автоматически следовать по HTTP-редиректам (коды 301/302).
* `-o` — сохраняет скачанный ответ в указанный локальный файл вместо вывода в терминал.

#### 7.2. Загрузка и раздача MP3-файла

Скачайте аудиофайл и добавьте ссылку для его скачивания на главную страницу:

```bash
sudo curl -L -o /var/www/html/music.mp3 https://www.soundhelix.com/examples/mp3/SoundHelix-Song-1.mp3
echo '<br> <a href="/download/music.mp3">Download Music</a>' | sudo tee -a /var/www/html/index.html
```

**Разбор флагов:**
* `tee -a` (*append*) — дописывает текст в конец файла, не перезаписывая его существующее содержимое.

#### 7.3. Установка модуля обработки изображений и настройка блоков `location`

Установите модуль `image-filter` для Nginx:

```bash
sudo apt install libnginx-mod-http-image-filter -y
```

Добавьте новые блоки `location` внутрь блока `server { listen 443 ssl; ... }` файла `/etc/nginx/sites-available/my-secure-server` и перезапустите сервер:

```nginx
    # Точный редирект на страницу с картинкой
    location = /picture {
        return 302 /picture.html;
    }

    # Раздача файлов для скачивания через alias
    location /download/ {
        alias /var/www/html/;
    }

    # Кеширование статических файлов по регулярному выражению
    location ~* \.(png|gif|ico|css|js)$ {
        root /var/www/html;
        expires 1d;
    }

    # Поворот всех JPG-изображений на 180 градусов на лету
    location ~* \.jpg$ {
        root /var/www/html;
        image_filter rotate 180;
        image_filter_buffer 10M;
    }
```

Примените изменения:

```bash
sudo nginx -t && sudo systemctl restart nginx
```

**Разбор директив и модификаторов:**
* `location = /picture` — модификатор `=` задает строгое точное совпадение URI (имеет наивысший приоритет).
* `return 302` — выполняет временное перенаправление на указанный URI.
* `alias /var/www/html/` — подменяет часть пути из `location` (`/download/`) на указанный путь в файловой системе.
* `location ~*` — модификатор `~*` включает регистронезависимое сопоставление по регулярному выражению.
* `expires 1d` — добавляет заголовки кеширования (`Cache-Control`, `Expires`) со сроком хранения 1 день.
* `image_filter rotate 180` — поворачивает изображение по часовой стрелке на 180 градусов перед отправкой клиенту.
* `image_filter_buffer 10M` — увеличивает максимальный размер буфера для обработки изображения (по умолчанию 1 МБ).

Пример использования: `curl -I -k https://my-secure-server.local/picture`

## Часть 2. Теоретические вопросы для самоконтроля

### Тема 1. Отличия самоподписанного сертификата от Let's Encrypt и недоверие браузеров

| Критерий | Самоподписанный сертификат (Self-Signed) | Сертификат Let's Encrypt |
| :--- | :--- | :--- |
| **Кто подписывает** | Сам владелец сервера своим же закрытым ключом | Доверенный центр сертификации (Certificate Authority — ISRG / Let's Encrypt) |
| **Доверие в браузерах** | Отсутствует; требуется ручное добавление в исключения | Доверие по умолчанию во всех современных ОС и браузерах |
| **Проверка владения доменом** | Не проводится (можно указать любой домен) | Обязательная автоматическая проверка (HTTP-01 или DNS-01) |
| **Срок действия** | Любой (задается при генерации, например 365 дней) | Строго 90 дней с поддержкой автопродления |
| **Область применения** | Локальная разработка, внутренние тестовые стенды | Публичные веб-сайты и боевые сервисы в интернете |

**Почему браузер не доверяет самоподписанному сертификату:**
* В каждую операционную систему и браузер вшит ограниченный список доверенных корневых центров сертификации (Root CA).
* Когда сервер предъявляет самоподписанный сертификат, браузер не может построить цепочку доверия до известного ему корневого центра и не имеет подтверждения, что сервер действительно принадлежит владельцу домена, поэтому блокирует загрузку с предупреждением.

**Проверка полей сертификата в консоли:**

```bash
openssl x509 -in /etc/ssl/certs/nginx-selfsigned.crt -text -noout | grep -E "Issuer:|Subject:|Not After"
```

* `x509` — утилита для просмотра и управления сертификатами формата X.509.
* `-in` — путь к входному файлу сертификата.
* `-text` — выводит содержимое сертификата в читаемом текстовом виде.
* `-noout` — подавляет вывод самого закодированного сертификата (блока `BEGIN CERTIFICATE`).

Пример использования: `openssl s_client -connect my-secure-server.local:443 -servername my-secure-server.local </dev/null`

### Тема 2. Назначение файла hosts и сценарии его применения

Файл `hosts` (`/etc/hosts` в Linux/macOS и `C:\Windows\System32\drivers\etc\hosts` в Windows) — это локальная таблица соответствия доменных имен и IP-адресов. При обращении к домену операционная система проверяет файл `hosts` **раньше**, чем отправляет запрос внешним DNS-серверам.

**Основные случаи применения:**
* **Локальная разработка и тестирование:** привязка выдуманных доменов (`.local`, `.test`) к `127.0.0.1` или IP-адресу виртуальной машины.
* **Проверка сайта до переключения реального DNS:** тестирование работы перенесенного сайта на новом хостинге по боевому домену до обновления записей у регистратора.
* **Работа в изолированных сетях:** разрешение имен внутренних корпоративных ресурсов без поднятия полноценного DNS-сервера.
* **Блокировка нежелательных хостов:** перенаправление рекламных или телеметрических доменов на `0.0.0.0` или `127.0.0.1`.

**Проверка разрешения имени с учетом файла hosts:**

```bash
getent hosts my-secure-server.local
```

* `getent hosts` — запрашивает разрешение имени через системную библиотеку NSS (учитывая и `/etc/hosts`, и DNS, в отличие от `nslookup` и `dig`, которые опрашивают только DNS-серверы).

Пример использования: `getent ahosts my-secure-server.local`

### Тема 3. Использование команды sudo для привилегированных операций в скриптах

Команда `sudo` (*superuser do*) позволяет авторизованному пользователю выполнять отдельные команды от имени суперпользователя (`root`) или другого пользователя согласно правилам в `/etc/sudoers`.

**Почему `sudo` используется в скриптах вместо запуска всего скрипта от `root`:**
* **Принцип наименьших привилегий:** только конкретные системные действия (запись в `/etc/nginx`, установка пакетов, перезапуск демонов) получают права `root`, а остальные операции выполняются от обычного пользователя.
* **Защита от случайного повреждения системы:** ошибка в переменной пути (например, `rm -rf $DIR/*` при пустой `$DIR`) без глобальных прав `root` не уничтожит критические системные каталоги.
* **Аудит и журналирование:** каждое обращение к `sudo` фиксируется в системном журнале (`/var/log/auth.log`) с указанием пользователя, времени и выполненной команды.
* **Корректное владение файлами:** файлы конфигурации или артефакты сборки, созданные без `sudo`, принадлежат текущему пользователю, а не `root`.

**Полезные флаги `sudo` при автоматизации:**

```bash
sudo -n systemctl reload nginx
```

* `-n` (*non-interactive*) — запрещает запрашивать пароль интерактивно; если права без пароля не настроены, команда сразу завершится с ошибкой вместо зависания скрипта.
* `-u www-data` — выполняет команду от имени указанного сервисного пользователя (например, веб-сервера).

Пример использования: `sudo -u www-data test -r /var/www/html/index.html && echo "Readable"`

### Тема 4. Основные типы DNS-записей и их назначение

| Тип записи | Расшифровка | Назначение | Пример значения |
| :--- | :--- | :--- | :--- |
| **A** | Address | Связывает доменное имя с IPv4-адресом | `192.168.1.55` |
| **AAAA** | IPv6 Address | Связывает доменное имя с IPv6-адресом | `2001:0db8:85a3::8a2e:0370:7334` |
| **CNAME** | Canonical Name | Создает псевдоним (алиас), ссылающийся на другое доменное имя | `www.example.com -> example.com` |
| **MX** | Mail Exchange | Указывает почтовые серверы, принимающие почту для домена, и их приоритет | `10 mail.example.com` |
| **TXT** | Text | Хранит произвольную текстовую информацию (SPF, DKIM, подтверждение домена) | `"v=spf1 include:_spf.google.com ~all"` |
| **NS** | Name Server | Определяет авторитетные DNS-серверы, отвечающие за данную DNS-зону | `ns1.hosting.com` |
| **PTR** | Pointer | Обратная запись: связывает IP-адрес с доменным именем (Reverse DNS) | `55.1.168.192.in-addr.arpa -> server.local` |
| **SOA** | Start of Authority | Содержит административную информацию о зоне (основной сервер, почта админа, серийный номер) | `ns1.example.com admin.example.com 2026111401 ...` |

**Запрос конкретных DNS-записей через утилиту `dig`:**

```bash
dig +short example.com A
dig +short example.com MX
```

* `+short` — выводит только результирующее значение записи без служебных заголовков DNS-пакета.

Пример использования: `dig @8.8.8.8 example.com TXT +short`

### Тема 5. Важность использования SSL/TLS-сертификатов для безопасного соединения

Протокол TLS (преемник SSL) обеспечивает три ключевые гарантии безопасности при передаче данных между клиентом и веб-сервером:

1. **Конфиденциальность (Шифрование):** весь трафик (пароли, токены сессий, персональные данные, содержимое форм) шифруется симметричным сеансовым ключом, что делает его бесполезным при перехвате в открытых Wi-Fi сетях или на промежуточных узлах (атаки класса *Man-in-the-Middle*).
2. **Целостность данных:** каждый передаваемый пакет защищен кодом аутентификации сообщений (MAC/AEAD). Если злоумышленник попытается изменить хотя бы один байт ответа сервера (например, внедрить вредоносный скрипт), клиент обнаружит нарушение подписи и разорвет соединение.
3. **Аутентификация сервера:** цифровой сертификат, подписанный доверенным центром сертификации, подтверждает, что пользователь подключился именно к подлинному серверу, а не к поддельному узлу, замаскированному через подмену DNS или ARP-спуфинг.

**Проверка поддерживаемых версий TLS и шифров:**

```bash
curl -Iv --tlsv1.2 https://example.com 2>&1 | grep "SSL connection"
```

* `-I` — запрашивает только HTTP-заголовки (`HEAD`).
* `-v` — включает подробный вывод процесса TLS-рукопожатия.
* `--tlsv1.2` — принудительно задает минимальную версию протокола TLS.

Пример использования: `nmap --script ssl-enum-ciphers -p 443 my-secure-server.local`

### Тема 6. Получение сертификатов Let's Encrypt через Certbot и автообновление

**Certbot** — официальный клиент для автоматического выпуска и продления бесплатных SSL-сертификатов от Let's Encrypt по протоколу **ACME** (*Automatic Certificate Management Environment*).

**Этапы выпуска сертификата (плагин Nginx):**
1. Установка клиента: `sudo apt install certbot python3-certbot-nginx -y`.
2. Запуск выпуска: `sudo certbot --nginx -d example.com -d www.example.com`.
3. **Прохождение проверки (Challenge):** Let's Encrypt должен убедиться, что вы контролируете домен. Чаще всего используется метод **HTTP-01** — Certbot временно размещает специальный токен в `/.well-known/acme-challenge/` на вашем сервере, а серверы Let's Encrypt запрашивают его по порту `80`. (Для wildcard-сертификатов `*.example.com` используется проверка **DNS-01** через добавление TXT-записи).
4. После успешной проверки Let's Encrypt выдает сертификат, а Certbot автоматически прописывает пути к файлам и редирект на HTTPS в конфигурацию Nginx.

**Механизм автоматического обновления:**
Сертификаты Let's Encrypt действуют **90 дней**. При установке пакета `certbot` в системе автоматически создается таймер `systemd` (`certbot.timer`), который запускается дважды в сутки и проверяет срок действия всех установленных сертификатов. Если до истечения срока остается менее 30 дней, Certbot тихо обновляет сертификат и выполняет команду `systemctl reload nginx`.

**Управление и проверка автообновления:**

```bash
sudo systemctl status certbot.timer
sudo certbot renew --dry-run
```

* `certbot renew` — запускает процедуру продления сертификатов, у которых истекает срок действия.
* `--dry-run` — выполняет тестовую симуляцию продления на тестовых серверах Let's Encrypt без перезаписи рабочих сертификатов.

Пример использования: `sudo certbot certificates`

### Тема 7. Цепочки сертификатов (Root CA и Intermediate CA)

Доверие в инфраструктуре открытых ключей (PKI) строится иерархически в виде цепочки сертификатов, чтобы защитить корневые ключи от компрометации:

1. **Корневой центр сертификации (Root CA):**
   * Находится на вершине иерархии. Его самоподписанный сертификат заранее вшит в хранилище доверенных сертификатов ОС и браузеров.
   * Закрытый ключ Root CA хранится в строжайшей изоляции (офлайн, в аппаратных модулях HSM) и используется только для подписи сертификатов промежуточных центров.
2. **Промежуточный центр сертификации (Intermediate CA):**
   * Получает свой сертификат, подписанный корневым центром (Root CA).
   * Непосредственно занимается проверкой заявок и выдачей конечных сертификатов владельцам сайтов. В случае компрометации промежуточного центра его можно отозвать, не затрагивая корневой сертификат в браузерах миллиардов пользователей.
3. **Сертификат сервера (End-Entity / Leaf Certificate):**
   * Выдается конкретному домену (например, `example.com`) и подписывается ключом Intermediate CA.

**Зачем нужен файл `fullchain.pem`:**
Браузеры хранят только сертификаты Root CA и часто не имеют в кэше сертификат нового Intermediate CA. Поэтому веб-сервер при TLS-рукопожатии должен отправить клиенту связку из **своего сертификата + всех промежуточных сертификатов** (файл `fullchain.pem`). Получив их, браузер проверяет подпись сертификата сервера ключом Intermediate CA, а подпись Intermediate CA — ключом доверенного Root CA, замыкая цепочку доверия.

**Проверка всей цепочки сертификатов удаленного сервера:**

```bash
openssl s_client -connect example.com:443 -showcerts </dev/null
```

* `-showcerts` — выводит все сертификаты в цепочке, переданные сервером во время TLS-рукопожатия (от сертификата домена до промежуточных центров).

Пример использования: `openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt /etc/letsencrypt/live/example.com/fullchain.pem`
