# Теория: NGINX — Архитектура, проксирование и балансировка (Темы 1–5)

## 1. Настройка и установка NGINX

### Установка и управление службой
В дистрибутивах на базе Debian/Ubuntu NGINX устанавливается из официальных репозиториев через менеджер пакетов `apt` и управляется системой инициализации `systemd`.

```bash
# Установка и запуск службы
sudo apt update && sudo apt install nginx -y
sudo systemctl enable --now nginx

# Проверка конфигурации и мягкое применение изменений
sudo nginx -t && sudo systemctl reload nginx
```

* **Разбор флагов и команд:**
  * `enable --now` — одновременно добавляет службу в автозагрузку при старте ОС и запускает её в текущей сессии.
  * `nginx -t` — проверяет синтаксис всех подключенных конфигурационных файлов без прерывания работы текущих соединений.
  * `systemctl reload nginx` — отправляет главному процессу (`master`) сигнал `SIGHUP` для плавного перезапуска рабочих процессов (`worker`) без потери активных клиентских запросов (Zero-Downtime Reload).

### Архитектура и раздача статики
NGINX использует асинхронную, событийно-ориентированную архитектуру (**Master — Worker**). Один процесс `master` управляет конфигурацией и привилегиями, а несколько процессов `worker` неблокирующим образом обрабатывают тысячи соединений одновременно.

Для раздачи статических файлов (HTML, CSS, JS, изображения) используется связка директив `root` и `try_files` внутри контекста `server` -> `location`:

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/html;

    location / {
        try_files \(uri\)uri/ =404;
    }
}
```

* **Разбор директив и переменных:**
  * `root /var/www/html;` — задает базовый путь на файловой системе, к которому приписывается URI запроса.
  * `try_files $uri $uri/ =404;` — последовательно проверяет существование запрашиваемого файла (`$uri`), затем директории (`$uri/`), а при их отсутствии возвращает код `404 Not Found`.

**Практический сценарий:** Отдача фронтенд-сборки (SPA на React/Vue) напрямую с диска с высокой скоростью, минуя бэкенд-приложение.

## 2. Роли NGINX

NGINX способен выполнять несколько архитектурных ролей в инфраструктуре:

* **Веб-сервер (Web Server):** Прямая отдача статического контента с диска клиенту по протоколам HTTP/HTTPS. *Сценарий:* хостинг лендингов, документации или медиафайлов.
* **Прямой прокси-сервер (Forward Proxy):** Посредник между клиентами локальной сети и внешним интернетом. Скрывает реальные IP-адреса клиентов от внешних ресурсов и кеширует ответы. *Сценарий:* контроль доступа сотрудников в интернет или обход сетевых ограничений из закрытого контура.
* **Обратный прокси-сервер (Reverse Proxy):** Единая точка входа перед пулом внутренних приложений (Python, Node.js, Go, Java). Принимает запросы от внешних клиентов и перенаправляет их на локальные или внутренние порты приложений. *Сценарий:* терминация SSL/TLS-сертификатов (HTTPS на входе, обычный HTTP внутри сети), защита бэкендов от прямого доступа извне, сжатие трафика (`gzip`).
* **Балансировщик нагрузки (Load Balancer):** Распределение входящего трафика между несколькими экземплярами одного приложения для повышения производительности и отказоустойчивости (High Availability). *Сценарий:* горизонтальное масштабирование веб-сервисов под высокой нагрузкой.

```bash
# Проверка открытых портов и ролей NGINX в системе
sudo ss -tulpn | grep nginx
```

* **Разбор флагов `ss`:**
  * `-t` (`--tcp`) — отображать TCP-сокеты.
  * `-u` (`--udp`) — отображать UDP-сокеты.
  * `-l` (`--listening`) — показать только прослушиваемые (ожидающие подключения) порты.
  * `-p` (`--processes`) — вывести имя и PID процесса, занявшего порт.
  * `-n` (`--numeric`) — не преобразовывать номера портов в имена служб (показывать `80` вместо `http`).

## 3. Конфигурация прокси-сервера

Для работы в режиме Reverse Proxy используется модуль `ngx_http_proxy_module`. Основная директива `proxy_pass` указывает адрес целевого сервера или группы `upstream`.

```nginx
server {
    listen 80;
    server_name app.local;

    location /api/ {
        proxy_pass http://127.0.0;
        proxy_set_header Host \$host;
        proxy_set_header X-Real-IP \$remote_addr;
        proxy_set_header X-Forwarded-For \$proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto \$scheme;
    }
}
```

* **Разбор директив и заголовков:**
  * `proxy_pass http://127.0.0;` — перенаправляет запросы на локальное приложение, работающее на порту `8000`. Слеш `/` в конце URI заставляет NGINX отрезать префикс `/api/` перед передачей запроса на бэкенд.
  * `proxy_set_header Host $host;` — сохраняет оригинальное доменное имя, запрошенное клиентом.
  * `proxy_set_header X-Real-IP $remote_addr;` — передает реальный IP клиента.
  * `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` — формирует цепочку IP-адресов всех прокси-серверов, через которые прошел запрос.
  * `proxy_set_header X-Forwarded-Proto $scheme;` — сообщает бэкенду, по какому протоколу (`http` или `https`) подключился клиент.

**Практический сценарий:** Маршрутизация запросов на одном домене по разным микросервисам (например, `/` ведет на фронтенд, а `/api/` — на бэкенд-сервис).

```bash
# Проверка передачи заголовков и ответа через прокси
curl -I -H "Host: app.local" http://127.0.0
```

* **Разбор флагов `curl`:**
  * `-I` (`--head`) — запросить только HTTP-заголовки ответа без загрузки тела страницы.
  * `-H` (`--header`) — добавить или переопределить произвольный HTTP-заголовок в запросе.

## 4. Балансировка нагрузки

Балансировка настраивается связкой блока `upstream` (в контексте `http`) и директивы `proxy_pass` (в контексте `location`).

### Основные алгоритмы балансировки

1. **Round Robin (по умолчанию):** Запросы распределяются строго по очереди между всеми серверами с учетом их весов (`weight`).
2. **Least Connections (`least_conn`):** Новый запрос отправляется на сервер с наименьшим количеством текущих активных соединений. Эффективен при разной длительности обработки запросов.
3. **IP Hash (`ip_hash`):** Вычисляет хеш от IP-адреса клиента и закрепляет его за конкретным бэкенд-сервером (Sticky Sessions). Полезно, если приложение хранит сессии в локальной памяти сервера.

```nginx
upstream app_cluster {
    least_conn;
    server 10.0.1.10:8080 weight=3 max_fails=2 fail_timeout=15s;
    server 10.0.1.11:8080 weight=1;
    server 10.0.1.12:8080 backup;
}
```

* **Разбор параметров `upstream`:**
  * `weight=3` — вес сервера (на первый сервер будет уходить в 3 раза больше запросов, чем на второй с `weight=1`).
  * `max_fails=2` — количество неудачных попыток подключения подряд, после которых сервер считается недоступным.
  * `fail_timeout=15s` — время, на которое недоступный сервер исключается из ротации, а также окно времени для подсчета ошибок `max_fails`.
  * `backup` — резервный сервер; принимает трафик только при отказе всех основных узлов.

**Практический сценарий:** Вывод одного из серверов на техническое обслуживание без прерывания работы сервиса (добавление параметра `down` к нужному серверу в `upstream` и выполнение `nginx -s reload`).

## 5. Мониторинг и логирование

NGINX ведет два основных типа журналов: `access.log` (все входящие запросы) и `error.log` (ошибки конфигурации, сбои подключения к апстримам, проблемы с правами доступа).

### Кастомное логирование для отладки балансировки
Директива `log_format` позволяет записывать технические метрики времени ответа бэкенда и адрес выбранного узла:

```nginx
log_format detailed '\$remote_addr - [\(time_local] "\)request" '
                    'status=\(status upstream=\)upstream_addr '
                    'rt=\(request_time urt=\)upstream_response_time';

access_log /var/log/nginx/access.log detailed;
error_log /var/log/nginx/error.log warn;
```

* **Разбор переменных и уровней логов:**
  * `$upstream_addr` — IP и порт бэкенд-сервера, обработавшего запрос.
  * `$request_time` — общее время обработки запроса в секундах с точностью до миллисекунд (от первого байта клиента до отправки последнего байта ответа).
  * `$upstream_response_time` — время, за которое ответил сам бэкенд-сервер (позволяет отделить тормоза сети от тормозов кода приложения).
  * `warn` — минимальный уровень критичности сообщений для `error_log` (`debug`, `info`, `notice`, `warn`, `error`, `crit`).

### Мониторинг состояния (`stub_status`)
Встроенный модуль `ngx_http_stub_status_module` предоставляет базовые метрики активных соединений для систем мониторинга (Prometheus, Zabbix):

```nginx
location /nginx_status {
    stub_status;
    allow 127.0.0.1;
    deny all;
}
```

* **Разбор директив:**
  * `stub_status;` — включает страницу статистики (Active connections, accepts, handled, requests).
  * `allow 127.0.0.1;` и `deny all;` — ограничивает доступ к метрикам только с локального хоста.

**Практический сценарий:** Поиск медленных запросов или падающих бэкендов в реальном времени через консоль.

```bash
# Фильтрация только ошибок 502/504 (проблемы с бэкендами) в логе доступа
sudo grep -E "status=(502|504)" /var/log/nginx/access.log | tail -n 20
```

* **Разбор флагов `grep` и `tail`:**
  * `-E` (`--extended-regexp`) — использование расширенных регулярных выражений (оператор `|` для поиска нескольких кодов ошибок одновременно).
  * `-n 20` — вывод последних 20 совпавших строк.

## 6. Развертывание NGINX на Amazon EC2, сетевая безопасность и доступ в Интернет

### 1. Архитектура сети в AWS для веб-сервера
Чтобы инстанс Amazon EC2 с NGINX был доступен пользователям из интернета, должны быть настроены три сетевых уровня:

1. **VPC и Подсеть (Public Subnet):** Инстанс должен находиться в публичной подсети, таблица маршрутизации (**Route Table**) которой содержит маршрут по умолчанию (`0.0.0.0/0`), направленный в **Internet Gateway (IGW)**.
2. **Публичный IP-адрес:** Инстансу должен быть назначен временный **Public IPv4** или постоянный **Elastic IP (EIP)** (чтобы адрес не менялся после остановки и повторного запуска ВМ).
3. **Security Group (SG):** Виртуальный файрвол на уровне инстанса (Stateful — ответный трафик разрешается автоматически). Для работы NGINX открываются входящие правила (**Inbound Rules**):
   * `SSH (TCP, порт 22)` — источник: ваш конкретный IP-адрес (`My IP`) для безопасного администрирования.
   * `HTTP (TCP, порт 80)` — источник: `0.0.0.0/0` (доступ для всех пользователей из интернета).
   * `HTTPS (TCP, порт 443)` — источник: `0.0.0.0/0` (для защищенного трафика по TLS).

### 2. Подключение к EC2 и развертывание NGINX

После создания инстанса Ubuntu Server в консоли AWS подключение выполняется по SSH с использованием приватного ключа (`.pem`), скачанного при запуске машины.

```bash
# 1. Установка строгих прав на файл приватного ключа (обязательное требование SSH-клиента)
chmod 400 ~/Downloads/my-aws-key.pem

# 2. Подключение к инстансу Ubuntu на AWS EC2
ssh -i ~/Downloads/my-aws-key.pem ubuntu@<PUBLIC_IP_EC2>

# 3. Установка и запуск NGINX внутри инстанса
sudo apt update && sudo apt install nginx -y
sudo systemctl enable --now nginx
```

* **Разбор флагов и команд:**
  * `chmod 400 <файл>` — устанавливает права доступа «только чтение для владельца» (`r--------`); без этого SSH-клиент отклонит ключ с ошибкой `UNPROTECTED PRIVATE KEY FILE`.
  * `ssh -i <путь_к_ключу>` (`--identity_file`) — указывает путь к файлу приватного криптографического ключа для аутентификации без пароля.
  * `ubuntu@` — стандартное имя системного пользователя с правами `sudo` в официальных образах (AMI) Ubuntu на AWS.

**Практический сценарий:** Автоматическая установка и запуск NGINX при первом старте инстанса через поле **User Data** (bash-скрипт выполняется от имени `root` при инициализации ВМ):

```bash
#!/bin/bash
apt-get update -y
apt-get install -y nginx
systemctl enable --now nginx
echo "<h1>Deployed on AWS EC2</h1>" > /var/www/html/index.html
```

### 3. Настройка локального файрвола (UFW) и проверка доступности

В базовых образах Ubuntu на AWS встроенный файрвол `ufw` обычно выключен (трафик фильтруется через AWS Security Groups). Если `ufw` активируется дополнительно для защиты на уровне ОС, необходимо разрешить SSH и NGINX до его включения.

```bash
# 1. Разрешение профилей трафика в UFW и активация файрвола
sudo ufw allow 'OpenSSH'
sudo ufw allow 'Nginx Full'
sudo ufw --force enable

# 2. Проверка статуса правил UFW
sudo ufw status verbose

# 3. Проверка публичного IP-адреса инстанса через сервис метаданных AWS (IMDSv2)
TOKEN=\$(curl -s -X PUT "http://169.254.169" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: \$TOKEN" http://169.254.169
```

* **Разбор флагов, параметров и команд:**
  * `ufw allow 'Nginx Full'` — открывает одновременно порты `80` (HTTP) и `443` (HTTPS) по протоколу TCP.
  * `ufw --force enable` — включает файрвол без интерактивного подтверждения (`Command may disrupt existing ssh connections`).
  * `ufw status verbose` — выводит подробный список активных правил, политик по умолчанию и сетевых интерфейсов.
  * `169.254.169.254` — специальный link-local адрес службы метаданных инстанса AWS (IMDS), доступный только изнутри самой виртуальной машины.
  * `curl -X PUT` (`--request`) — отправка HTTP-запроса методом `PUT` для получения сессионного токена безопасности IMDSv2.

**Практический сценарий:** Если сайт на EC2 не открывается в браузере, проверка выполняется строго по цепочке снизу вверх:
1. Локально на сервере: `curl -I http://localhost` (работает ли сам NGINX).
2. Локальный файрвол ОС: `sudo ufw status` (не блокирует ли порты `80`/`443` внутри Ubuntu).
3. Облачный периметр: проверка правил **Security Group** (открыт ли порт `80` для `0.0.0.0/0`), наличия **Public IP** и маршрута `0.0.0.0/0 -> igw-...` в **Route Table** подсети.
