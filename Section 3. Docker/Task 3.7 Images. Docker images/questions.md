### 1. Какие есть режимы запуска контейнеров?

Существует два основных режима запуска контейнеров через `docker run`:
1. **Attached (передний план, режим по умолчанию):** стандартные потоки вывода (`STDOUT` и `STDERR`) контейнера привязаны к текущему терминалу. Консоль блокируется выводом логов процесса, а прерывание (`Ctrl+C`) останавливает контейнер.
2. **Detached (фоновый режим, флаг `-d` или `--detach`):** контейнер запускается в фоне, возвращая в терминал только свой идентификатор и сразу освобождая командную строку. Используется для долгоживущих сервисов (веб-серверов, баз данных).

Дополнительно для интерактивной работы с оболочкой внутри контейнера используются флаги `-i` (`--interactive`, держит открытым `STDIN`) и `-t` (`--tty`, выделяет псевдотерминал).

```bash
# Фоновый запуск веб-сервера
docker run -d nginx:stable-alpine

# Интерактивный запуск оболочки внутри контейнера
docker run -it alpine sh
```

### 2. Роль Docker Registry в распространении и хранении Docker-образов

**Docker Registry** — это централизованное серверное приложение (хранилище) для хранения, версионирования и раздачи Docker-образов.

* **Роль в инфраструктуре:** служит связующим звеном между сборкой (CI) и развертыванием (CD). Сборочные серверы загружают туда протестированные образы, а боевые и тестовые серверы скачивают их для запуска, что гарантирует идентичность окружения на всех этапах.
* **Публичные реестры:** Docker Hub (используется по умолчанию), GitHub Container Registry (`ghcr.io`), Quay.io, Google Artifact Registry, Amazon ECR Public.
* **Приватные реестры:** используются внутри компаний для хранения проприетарного ПО. Разворачиваются локально (Harbor, Sonatype Nexus, JFrog Artifactory, GitLab Container Registry) или в облаке (AWS ECR, Azure Container Registry, Yandex Container Registry).

### 3. Взаимодействие с Docker Registry через CLI и аутентификация

Взаимодействие происходит через стандартный Docker CLI с помощью следующих команд:
* `docker login [registry_url]` — вход в реестр. Если адрес не указан, используется Docker Hub. Учетные данные (токен) сохраняются в `~/.docker/config.json`.
* `docker logout [registry_url]` — выход из реестра и удаление локального токена.
* `docker pull <image>:<tag>` — загрузка образа из реестра на локальный хост (флаг `-a` / `--all-tags` скачивает все теги репозитория).
* `docker push <registry>/<repo>:<tag>` — отправка локального образа в удаленный реестр.
* `docker search <term>` — поиск публичных образов на Docker Hub из терминала.

```bash
# Безопасная аутентификация в приватном реестре с передачей пароля/токена через STDIN
echo "\$REGISTRY_TOKEN" | docker login ://example.com -u deploy-bot --password-stdin

# Отправка образа в приватный реестр
docker push ://example.com/backend/api:1.2.0
```

### 4. Тегирование Docker-образов с помощью Docker Tag

**Тег (tag)** — это человекочитаемый текстовый ярлык (псевдоним), который привязывается к конкретному `IMAGE ID` (уникальному SHA-256 хешу образа).

* **Зачем нужно:** один и тот же образ может иметь несколько тегов одновременно. Теги позволяют указывать версию приложения, базовую ОС, этап жизненного цикла (`dev`, `staging`, `prod`), а также менять адрес целевого реестра перед отправкой образа (`docker push`).
* **Особенность:** в отличие от Git, в Docker принято перемещать теги (например, `stable` или `latest`) на новые `IMAGE ID` при выходе обновлений. Если тег не указан при запуске или скачивании, Docker автоматически подставляет `latest`.

---

### 5. Команды и синтаксис для тегирования Docker-образов

Для создания нового тега используется команда `docker tag` (или её полный синоним `docker image tag`). Команда не дублирует данные на диске, а лишь создает новый указатель на существующий `IMAGE ID`.

**Синтаксис:**
```bash
docker tag ИСХОДНЫЙ_ОБРАЗ[:ТЕГ] [ЦЕЛЕВОЙ_РЕЕСТР/]РЕПОЗИТОРИЙ[:НОВЫЙ_ТЕГ]
```

**Практические примеры:**
```bash
# Назначение нового тега в рамках того же репозитория
docker tag nginx:stable-alpine nginx:inno-dkr-07

# Тегирование по IMAGE ID для отправки в корпоративный реестр
docker tag 8587e8f26fc1 registry.company.local/devops/nginx:1.25.4
```

### 6. Использование Docker Tag для создания версионированных образов и лучшие практики

Для управления версиями одному образу при сборке обычно присваивают сразу несколько тегов разной степени детализации (например, `1.4.2`, `1.4`, `1`).

**Лучшие практики версионирования:**
1. **Использовать SemVer (семантическое версионирование):** формат `MAJOR.MINOR.PATCH` (например, `2.1.0`) позволяет безопасно обновлять минорные версии и контролировать критические изменения.
2. **Добавлять метаданные сборки:** включать в тег короткий SHA-хеш коммита Git или номер CI-сборки (например, `app:1.4.2-git8f3a1c`) для точной трассировки кода.
3. **Указывать базовый дистрибутив:** если образ собирается на разных базовых системах, отражать это в теге (`python:3.12-slim`, `nginx:stable-alpine`).
4. **Не использовать `latest` в продакшене:** тег `latest` не гарантирует стабильность и может незаметно обновиться при перезапуске пода или контейнера, что приведет к несовместимости. В production-окружении всегда фиксируют конкретную версию или SHA-дайджест образа.

```bash
# Сборка образа сразу с несколькими версионными тегами
docker build -t myapp:1.2.0 -t myapp:1.2 -t myapp:1.2.0-a1b2c3d .
```

### 7. Инспектирование объектов с помощью Docker Inspect

**`docker inspect`** — команда для получения подробной низкоуровневой метаинформации об объектах Docker (образах, контейнерах, сетях, томах, плагинах) в структурированном формате JSON.

* **Какие данные возвращает:**
  * *Для образа:* архитектуру и ОС, переменные окружения (`Env`), команду запуска по умолчанию (`Cmd`, `Entrypoint`), открытые порты (`ExposedPorts`), список слоев (`RootFS`) и пути расположения слоев на хост-машине (`GraphDriver.Data`).
  * *Для контейнера:* текущее состояние и PID (`State`), IP-адрес и параметры сети (`NetworkSettings`), примонтированные тома (`Mounts`), политику перезапуска (`RestartPolicy`).
* **Основные флаги:**
  * `-f` / `--format` — форматирование и фильтрация вывода с помощью шаблонов **Go templates** (позволяет извлечь конкретное значение без парсинга всего JSON).
  * `--type` — явное указание типа объекта (`image`, `container`, `network`, `volume`), если их имена совпадают.

```bash
# Получить путь к верхнему слою образа на хосте
docker inspect -f '{{.GraphDriver.Data.UpperDir}}' nginx:stable-alpine

# Узнать команду запуска по умолчанию (Cmd) из метаданных образа
docker inspect --type=image -f '{{.Config.Cmd}}' nginx:inno-dkr-07

# Получить IP-адрес работающего контейнера
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' <container_id>
```
