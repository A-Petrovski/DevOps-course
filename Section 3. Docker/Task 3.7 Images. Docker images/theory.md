## Введение

Итак, мы познакомились с ключевыми командами для работы с контейнерами. Сейчас рассмотрим, что необходимо для запуска контейнеров.

Контейнеры запускаются из образов. **Образ (image)** — это файл, представляющий собой операционную систему с установленными компонентами и файлами. Образ используется только в режиме чтения при запуске контейнера, содержащего все необходимое для запуска конкретного приложения.

Давайте рассмотрим, как взаимодействовать с образами. Самый элементарный метод работы с образами заключается в создании контейнера, так как в команду `docker run` мы передаем, какой образ должен использоваться для запуска контейнера.

Например, команда:
```bash
docker run --name test nginx:stable
```
сообщает нам, что нужно запустить контейнер с именем `test` с образом `nginx:stable` под капотом.

По аналогии с контейнерами, у Docker CLI есть свой набор команд для работы с образами. Также нужно действовать с контейнерами, в которых есть команда `docker container`. У образов есть аналогичная команда `docker image`, она содержит все возможные команды по работе с образами и ряд команд, которые используются чаще всего и вынесены вне `docker image`, хотя и повторяют функциональность некоторых команд.

## Команда pull

Начнем с основной команды, которая позволяет нам получить образ:

* `docker pull` — позволяет скачать образ с определенным приложением из внешнего Docker-реестра.

Данная команда применяется не слишком часто — обычно она вызывается прозрачно мимо нас при запуске контейнера, когда требуемого образа нет на хосте, где запускается контейнер.

---

## Команда images

Для просмотра образов, которые имеются на хосте, нужно вызвать команду:

* `docker images` — выводит список всех образов, содержащихся на хосте.

Пример вывода:
```text
$ docker images
REPOSITORY       TAG                 IMAGE ID            CREATED             SIZE
nginx            stable-alpine       8587e8f26fc1        2 months ago        21.2MB
```

Описание колонок:
* **REPOSITORY** — имя образа. Как правило, содержит еще и адрес внешнего реестра (registry), если он отличается от реестра по умолчанию.
* **TAG** — именованный ярлык (тег) образа, который может отображать определенное состояние образа (например `stable` или `testing`), либо ту операционную систему, на базе которой собран образ, либо ту версию приложения, которая содержится в образе.
* **IMAGE ID** — по аналогии с ID контейнеров, каждый образ имеет свой идентификатор, который можно указывать при запуске контейнера.
* **CREATED** — дата, когда образ был создан (то есть когда он был именно собран, а не скачан).
* **SIZE** — полный размер образа.

## Реестр и репозиторий

**Реестр (registry)** — удаленное хранилище для образов Docker. По умолчанию используется Docker Hub. Не стоит путать с **репозиторием (repository)** — это то, что можно назвать именем образа.

Если взять пример с образом `nginx:stable-alpine`:
* **Реестр** — Docker Hub Container Image Library | App Containerization (по умолчанию, поэтому не указан)
* **Репозиторий** — `nginx`
* **Тег** — `stable-alpine`

## Команда tag

Для работы с тегами существует команда:

* `docker tag` — позволяет назначить образу новый репозиторий и тег.

Фактически это будет такой же образ, как и исходный. В данном случае привязка — к идентификатору образа, а не к исходному тегу. В отличие от git, где тег нежелательно двигать с одного коммита на другой, в Docker переназначать тег на новые образы — обычная практика.

Так, например, в `nginx` образ семейства `stable` указывает на актуальный стабильный образ. Как только выйдет новая стабильная версия `nginx`, будет создан новый образ, содержащий новую версию приложения. В репозитории новый образ будет храниться с тегом `stable`, хотя будет указывать уже на совершенно другой `IMAGE ID`, а старый образ останется без тега. Это верно для случаев, когда на старый образ не был назначен еще какой-нибудь тег — к примеру, `1.16.1`.

> **Важное замечание!** Если у образа тег не указан, то Docker по умолчанию подразумевает, что образ имеет тег `latest`.

## Команда inspect

Для получения информации по конкретному объекту Docker (например образ или контейнер) используется команда:

* `docker inspect` — выводит метаинформацию об объекте Docker.

В случае образа — в каких условиях собран образ, какая команда запускается по умолчанию, из чего образ собран и где хранится на хосте. Так, например, использование `docker inspect nginx:stable-alpine` выведет структурированную (в JSON) метаинформацию об образе `nginx:stable-alpine`, из которой можно узнать, какая версия `nginx` содержится в нашем контейнере и т.д.

В этом файле по JSON пути (он же jsonpath) `.[0].GraphDriver.Data.UpperDir` есть директория на хосте, содержащая файлы нашего образа, но не все, а лишь последнего слоя.
