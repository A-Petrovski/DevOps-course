## Введение

На самом деле, в большинстве случаев Docker ведет себя довольно спокойно с сетью — она просто работает. Однако бывает очень полезно в случае отладки знать, что под капотом у сети Docker и как она работает.

Начнем, пожалуй, с самого простого случая — когда ты ничего не настраивал в системе сам и оно просто магически работает: создал контейнер, ему присвоился адрес, в интернет доступ из контейнера есть. Казалось бы, что еще нужно?

И да, для многих случаев этого действительно хватает. Но все-таки разберемся, что же на самом деле внутри сетевой модели Docker?

По умолчанию Docker использует сетевой мост (`bridge`), к которому подключаются виртуальные сетевые интерфейсы. Они, в свою очередь, создаются на каждый контейнер. Данный `bridge`, как правило, называется в системе `docker0` — можешь проверить его сам, выведя список интерфейсов на хосте.

В целом, этот подход широко распространен и для виртуальных машин, поскольку довольно прост для понимания и реализации на уровне контейнера — он не знает, что вне контейнера что-то существует.

## Сетевые драйверы Docker

По умолчанию в Docker есть 4 сетевых драйвера:

* **`bridge`** — мы рассмотрели его выше.
* **`macvlan`** — в целом, похож на `bridge`, но если в случае `bridge` общение с реальным интерфейсом производится через `bridge`-интерфейс, то здесь подключение осуществляется через виртуальный интерфейс, который сразу подключен к физическому интерфейсу, где у каждого интерфейса свой MAC-адрес.
* **`host`** — контейнер подключается к сети хоста, что позволяет ему общаться с сервисами, запущенными на локальном интерфейсе, и сервисам общаться так, как если бы приложение в Docker было запущено на хосте.
* **`none`** — сети нет. Вообще. Если вдруг не надо.

## Управление сетями (network ls и network create)

Для работы с сетью Docker есть команда `network`.

### `network ls`
`docker network ls` — выводит список всех существующих Docker-сетей. По умолчанию их 3. И, как видно по столбцу `Driver`, нет только сети типа `macvlan`.

Зачем создавать еще сетей? Конечно же, для сетевого отделения приложений друг от друга. Предположим, что мы запустили несколько приложений и хотим, чтобы они могли общаться только между собой и хостом, — не вопрос, отделяем их в свою сеть, в которой у них своя атмосфера.

### `network create`
`docker network create` — создает новую сеть с нужным драйвером и нужными параметрами.

Пример создания новой сети типа `bridge`:
```bash
docker network create -d bridge inno
```
На самом деле, параметр `-d`, в котором указан драйвер, необязателен, поскольку драйвер `bridge` используется по умолчанию, но мы его добавили для примера.

## Взаимодействие контейнеров и DNS

Теперь разберемся, как можно общаться контейнерам между собой. Для этого создадим 2 контейнера, но второй контейнер запустим в интерактивном режиме. Откроем новую консоль и через `inspect` узнаем IP-адрес первого контейнера. Вернемся в консоль с запущенной оболочкой второго контейнера и проверим доступность первого контейнера через `ping`. Можно еще установить `curl` и проверить доступность тестовой страницы `nginx` из первого контейнера. Можешь проверить сам — работать будет.

Как ты понял, по умолчанию Docker подключает контейнеры к сети с именем `bridge` (не путать с драйвером), однако поменять это можно, передав при запуске параметр `--network` с именем требуемой сети.

Окей, контейнеры в рамках одной сети могут общаться — это круто. Но как-то неудобно общаться по IP-адресу. DNS бы! И он есть, но не у сети по умолчанию с именем `bridge`. Если мы создадим новую сеть, то контейнеры в ней смогут общаться между собой по имени.

## Драйвер host

Пожалуй, давай еще разберем `host`. На самом деле, использование этой сети — это своеобразный костыль, но в некоторых вопросах и спасение. К примеру, если с `bridge` наблюдается какая-то проблема, но времени разбираться нет, то почти точно решение с `host` сработает (но разобраться потом обязательно стоит — навскидку, проблема может быть связана с MTU или самим `bridge`).

## Маршрутизация, NAT и взаимодействие с хостом

Теперь разберемся, как устроена маршрутизация при использовании Docker-контейнеров. До смешного просто — в случае, если мы используем драйвер `bridge`, то добавляется маршрут через `bridge`-интерфейс, а если через драйвер `host`, то ничего не добавляется, у нас и так все готово.

Есть еще одна тема — NAT, правила пробросов портов и прочих чудес. Для этого, как правило, используется `iptables`. Как раз там решается и NAT, и пробросы портов.

* **Как обратиться к хосту, если мы в `bridge`?** При использовании сети типа `bridge`, `default gateway`, который вы можете увидеть в `inspect`, — это как раз адрес, по которому можно обратиться к хосту.
* **Как обратиться с хоста к контейнеру?** Да, можем пробросить порты, но, в общем-то, адрес, который мы получали выше у контейнера, доступен для нас и с самого хоста (`bridge`-то связан с реальным интерфейсом, так что роутинг все сделает, как нужно). Так что и проброс, может, не нужен, если нам не нужно делать доступность извне другим хостам.

## Дополнительные драйверы и возможные проблемы

По умолчанию в Docker есть 4 сетевых драйвера, но это не все варианты. Для Docker есть довольно большое число плагинов, которые расширяют этот список, в том числе позволяя нескольким хостам строить `overlay`-сеть поверх физической сети, чтобы выбраться за пределы общения на одном хосте.

В задании мы рассмотрели только две команды по работе с сетями (`ls`, `create`), но список на этом не кончается (`inspect`, `rm`, `prune`).

**Предупреждение о пересечении подсетей:** каждая созданная сеть `bridge` по умолчанию забирает сеть из блока адресов `172.X.0.0/16`. Поэтому, если ваша локальная частная сеть находится в одном из этих диапазонов, возможно пересечение сетей. А это может привести к недопониманию, отчего сломался коннект к внутренним ресурсам или наоборот — к контейнерам.
