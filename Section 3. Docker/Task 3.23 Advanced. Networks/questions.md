# Контрольные вопросы для самопроверки и собеседований (Docker Networking)

### 1. Зачем создавать отдельную пользовательскую сеть, если в Docker по умолчанию уже существует сеть `bridge`?
В дефолтной сети `bridge` отсутствует автоматический DNS-резолвинг: контейнеры могут взаимодействовать только по IP-адресам (которые динамически меняются при перезапуске) или через устаревший флаг `--link`. В пользовательской сети работает встроенный DNS-сервер Docker, позволяющий обращаться к контейнерам по их именам, а также обеспечивается строгая сетевая изоляция между разными проектами на одном хосте.

```bash
# Проверка файла резолвера внутри контейнера в пользовательской сети (укажет на 127.0.0.11)
docker exec inno-dkr-25-pinger cat /etc/resolv.conf
```

### 2. Какие три системные сети всегда присутствуют в Docker по умолчанию и чем принципиально отличаются их драйверы?
При установке Docker создаются три сети:
* **`bridge`** — изолированная виртуальная сеть (мост `docker0` на хосте) с выходом во внешнюю сеть через NAT.
* **`host`** — полностью отключает сетевую изоляцию контейнера; он напрямую использует сетевой стек, интерфейсы и порты хост-машины.
* **`none`** — полностью отключает сеть для контейнера (внутри остается только локальный loopback-интерфейс `lo`).

```bash
docker network ls
```

### 3. Почему при запуске `nginx` мы не использовали флаг проброса портов (`-p`), но при этом второй контейнер смог достучаться до веб-сервера?
Флаг `-p` (`--publish`) создает правила `iptables` (DNAT) для публикации портов контейнера на сетевых интерфейсах **хост-машины**, чтобы принимать трафик извне. Внутри одной виртуальной сети Docker все порты контейнеров открыты друг для друга по умолчанию без необходимости их публикации наружу.

```bash
# Запрос идет напрямую на 80-й порт контейнера внутри виртуального моста
docker exec inno-dkr-25-pinger curl -sI http://inno-dkr-25-nginx | head -n 1
```

### 4. Какой именно IP-адрес отвечает за разрешение имени `inno-dkr-25-nginx` внутри контейнера `alpine` и как это устроено под капотом?
За разрешение имен отвечает встроенный DNS-сервер демона Docker, который слушает локальный адрес **`127.0.0.11`** внутри сетевого пространства имен (network namespace) каждого контейнера пользовательской сети. Демон перехватывает DNS-запросы на этот адрес, сопоставляет имя активного контейнера с его внутренним IP и возвращает A-запись (если имя внешнее — пересылает запрос на DNS-серверы хоста).

```bash
docker exec inno-dkr-25-pinger nslookup inno-dkr-25-nginx
```

### 5. Куда попадет сетевой пакет, если изнутри контейнера отправить запрос на IP-адрес, указанный в поле `Gateway` сети?
Поле `Gateway` в конфигурации bridge-сети — это IP-адрес самого виртуального сетевого интерфейса моста (`br-<ID_сети>`) на **хост-машине**. Запрос на этот адрес попадет непосредственно на хост, что позволяет контейнеру обращаться к сервисам, запущенным на хосте (при условии, что сервис слушает интерфейс моста или `0.0.0.0`, а фаервол не блокирует трафик).

```bash
# Узнать IP-адрес шлюза (хоста) для сети inno-25-bridge
docker network inspect -f '{{range .IPAM.Config}}{{.Gateway}}{{end}}' inno-25-bridge
```

### 6. Сколько сетевых интерфейсов станет внутри работающего контейнера, если подключить его ко второй сети через `docker network connect`?
Внутри контейнера станет **два** виртуальных сетевых интерфейса (`eth0` и `eth1`), не считая `lo`. Команда `docker network connect` не отключает контейнер от его текущей сети, а динамически создает и привязывает к нему дополнительную виртуальную сетевую карту (`veth`-пару) в новой сети.

```bash
docker network connect inno-25-bridge temp-web
docker exec temp-web ip -br addr
```

### 7. К какой скрытой сетевой проблеме в продакшене может привести создание новых `bridge`-сетей без указания параметров IPAM?
По умолчанию Docker выделяет каждой новой bridge-сети подсеть из частного диапазона **`172.17.0.0/16` – `172.31.0.0/16`**. Если корпоративная локальная сеть, облачный VPC или VPN-туннель используют пересекающийся диапазон адресов, возникнет конфликт маршрутизации: хост или контейнеры потеряют доступ к внутренним ресурсам компании.

```bash
# Безопасное создание сети с явным выделением неконфликтующей подсети
docker network create --driver bridge --subnet 192.168.240.0/24 safe-net
```
