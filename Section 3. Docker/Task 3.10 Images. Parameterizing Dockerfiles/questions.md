# Контрольные вопросы для самопроверки: Task 3.10 Images

## 1. Инструкция ENV в Dockerfile. Что представляет собой инструкция ENV и как она используется в Dockerfile? Как можно определить переменные окружения с помощью инструкции ENV?

**Ответ:**
Инструкция `ENV` устанавливает постоянные переменные окружения внутри собираемого Docker-образа. Эти переменные сохраняются в метаданных образа, поэтому они доступны **как на всех последующих этапах сборки** (в инструкциях `RUN`, `COPY`, `ADD`, `WORKDIR`), **так и внутри любого запущенного контейнера** из этого образа (и для основного процесса, и при подключении через `docker exec`).

Определить переменные окружения в `Dockerfile` можно двумя способами:
1. **Простой синтаксис (одна переменная):** `ENV KEY VALUE` — всё, что идёт после первого пробела до конца строки, считается значением переменной (включая пробелы).
2. **Расширенный синтаксис (несколько переменных в одном слое):** `ENV KEY1=VALUE1 KEY2="VALUE 2"` — позволяет задать сразу несколько переменных за одну директиву (что экономит слои образа). Поддерживает перенос строк через обратный слеш `\` и экранирование пробелов двойными кавычками `"`.

**Пример из практики:**
```dockerfile
FROM ubuntu:18.04
ENV APP_ENV=production \
    APP_PORT=8080 \
    PATH="/opt/custom-app/bin:\${PATH}"
```

## 2. Передача переменных окружения при сборке Docker-образа. Как передать значения переменных окружения при сборке Docker-образа? Какие параметры и флаги используются при выполнении команды docker build для передачи переменных окружения?

**Ответ:**
У команды `docker build` **нет** прямых флагов `--env` или `--env-file` (они существуют только у `docker run`). Чтобы передать динамическое значение при сборке и превратить его в постоянную переменную окружения образа, используется связка:
1. В `Dockerfile` объявляется аргумент сборки `ARG` и сразу же передаётся в `ENV`:
   ```dockerfile
   ARG MY_VAR
   ENV MY_VAR=\${MY_VAR}
   ```
2. При запуске сборки используется флаг **`--build-arg KEY=VALUE`** (или `--build-arg KEY`, если одноимённая переменная уже экспортирована в оболочке хоста). Если нужно передать несколько значений, флаг `--build-arg` указывается несколько раз.

**Пример из практики:**
```bash
# Передача значения при сборке образа через --build-arg:
docker build --build-arg APP_VERSION=2.4.1 --build-arg BUILD_ENV=staging -t my-app:2.4.1 .
```

## 3. Инструкция ARG в Dockerfile. Что представляет собой инструкция ARG и как она используется в Dockerfile? Как можно передать аргументы в Dockerfile при сборке Docker-образа с помощью инструкции ARG?

**Ответ:**
Инструкция `ARG` определяет переменную времени сборки (build-time variable), значение которой можно передать пользователю при запуске `docker build`. В отличие от `ENV`, переменные `ARG` существуют **только в процессе сборки образа** и полностью отсутствуют в окружении запущенного контейнера (хотя их следы остаются в истории слоёв `docker history`, поэтому в `ARG` категорически нельзя передавать пароли и секретные ключи).

**Правила использования и области видимости:**
* Синтаксис: `ARG <имя>[=<значение_по_умолчанию>]` (в одной директиве объявляется только один аргумент).
* **До `FROM`:** аргумент доступен только для подстановки в саму инструкцию `FROM` (например, `FROM nginx:${TAG}`). После `FROM` его значение сбрасывается.
* **После `FROM`:** чтобы использовать переданный `--build-arg` внутри инструкций сборки (`RUN`, `ENV`), `ARG` нужно объявить внутри блока образа (или продублировать `ARG <имя>` после `FROM`).

**Пример из практики:**
```dockerfile
ARG BASE_TAG=stable-alpine
FROM nginx:\${BASE_TAG}

# Повторное объявление для доступа внутри образа:
ARG BASE_TAG
ARG AUTHOR="DevOps Team"
RUN echo "Built from \({BASE_TAG} by\){AUTHOR}" > /etc/build-info
```
```bash
docker build --build-arg BASE_TAG=1.25-alpine --build-arg AUTHOR="Alex" -t custom-nginx .
```

## 4. Различия между ARG и ENV. В чем разница между инструкциями ARG и ENV в Dockerfile? Какие особенности и сценарии использования каждой из этих инструкций?

**Ответ:**
Главное различие заключается в **жизненном цикле** и **способе переопределения**:

| Критерий | `ARG` (Аргумент сборки) | `ENV` (Переменная окружения) |
| :--- | :--- | :--- |
| **Где доступен** | Только во время сборки (`docker build`) | И при сборке (`docker build`), и внутри работающего контейнера (`docker run` / `docker exec`) |
| **Переопределение при сборке** | Да, через `docker build --build-arg KEY=VAL` | Напрямую нельзя (только через промежуточный `ARG`) |
| **Переопределение при запуске** | Не применимо (не существует в контейнере) | Да, через `docker run -e KEY=VAL` или `--env-file` |
| **Использование до `FROM`** | Да (для параметризации тега базового образа) | Нет (вызовет ошибку сборки) |
| **Количество в одной строке** | Строго одна переменная на директиву | Можно указать несколько (`ENV K1=V1 K2=V2`) |

**Сценарии использования:**
* **`ARG`:** выбор версии базового образа (`FROM`), передача URL для скачивания исходников/пакетов, настройка флагов компиляции, указание временных путей сборки.
* **`ENV`:** настройка системного `PATH`, задание портов/режимов работы приложения по умолчанию, сохранение метаданных (версии установленного ПО) для проверки внутри контейнера.

**Пример из практики:**
```dockerfile
ARG PYTHON_VER=3.11
FROM python:\${PYTHON_VER}-slim

# ENV сохранится в контейнере и отключает буферизацию вывода Python в логи Docker:
ENV PYTHONUNBUFFERED=1
```

## 5. Использование ARG и ENV для динамической настройки Docker-образов. Как можно использовать инструкции ARG и ENV для динамической настройки Docker-образов при сборке? Какие параметры и аргументы можно передать в Dockerfile для изменения поведения сборки образа?

**Ответ:**
Комбинация `ARG` и `ENV` позволяет превратить статичный `Dockerfile` в универсальный шаблон сборки, который без правки кода адаптируется под разные окружения (`dev`, `stage`, `prod`), версии зависимостей и целевые архитектуры.

**Основные приёмы динамической настройки при сборке:**
1. **Параметризация базового образа:** выбор нужной версии ОС или языка программирования (`ARG GO_VERSION=1.21` -> `FROM golang:${GO_VERSION}`).
2. **Управление установкой зависимостей:** передача флагов сборки или списка дополнительных пакетов (например, установка инструментов отладки только при передаче `--build-arg INSTALL_DEBUG=true` в инструкции `RUN`).
3. **Фиксация версий скачиваемых артефактов и сохранение их в образе:** передача версии релиза через `ARG`, скачивание бинарника по динамической ссылке и запись этой версии в `ENV`, чтобы приложение или инженер при отладке всегда знали, какая версия зашита в контейнер.
4. **Передача системных прокси-серверов при сборке:** Docker автоматически распознаёт стандартные переменные `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, переданные через `--build-arg`, позволяя собирать образы в закрытых корпоративных сетях без сохранения настроек прокси в финальном образе.

**Пример из практики:**
```dockerfile
ARG ALPINE_VER=3.18
FROM alpine:\${ALPINE_VER}

ARG APP_VER=1.0.0
ARG EXTRA_PKGS=""

# Фиксируем версию приложения в образе навсегда
ENV APP_VERSION=\${APP_VER}

# Динамически устанавливаем базовые и опциональные пакеты
RUN apk add --no-cache curl \${EXTRA_PKGS}
```
```bash
# Продакшн-сборка (минимальный образ):
docker build --build-arg APP_VER=1.0.1 -t app:prod .

# Отладочная сборка (с установкой tcpdump и vim):
docker build --build-arg APP_VER=1.0.1-debug --build-arg EXTRA_PKGS="tcpdump vim" -t app:debug .
```
