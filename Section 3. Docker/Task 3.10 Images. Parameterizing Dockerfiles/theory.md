## Введение

В данном задании рассмотрим директивы, которые позволяют задавать параметры приложения.

Для примера, наиболее частый паттерн конфигурирования приложения внутри контейнера - через переменные окружения.

Переменные окружения дают возможность нам сохранить в образе определенную сервисную информацию и данные, необходимые для работы приложения. Такой подход позволяет избавиться от использования конфигурационных файлов и от вопросов, как эти файлы доставлять в контейнер. Увы, данный подход не получится использовать всегда, но, если есть возможность настроить конфигурацию приложений через переменные окружения, лучше именно так и сделать.

Как же использовать переменные окружения в Dockerfile? Для работы с ними используется директива `ENV`.

## ENV

**ENV** — позволяет задать переменную окружения, которая должна содержаться в образе.

Как мы знаем, переменные окружения могут использоваться для:
* **Сохранения сервисной информации** — хранения версии приложения и версий установленных зависимостей;
* **Передачи параметров сборки** — если мы хотим определить, какая версия приложения должна собираться;
* **Настройки окружения** — если мы знаем, что наше приложение будет запускаться из нестандартной директории, но мы хотим, чтобы оно было доступно при `docker exec` из консоли без полного пути. В этом случае можно переопределить системную переменную `PATH` — тогда, откуда бы мы не вызвали команду, запущена она будет именно из того пути, где наше приложение установлено.
* **Передачи параметров приложения** — делается на этапе Dockerfile редко, поскольку само приложение, как правило, работает в определенном контексте и с определенными зависимостями, при которых связь между ними динамическая. Например, адрес, по которому доступна база данных, или уровень логирования. Часто передача подобных переменных окружения производится уже на уровне запуска контейнера, то есть при `docker run` при помощи флага `--env ENV_VARIABLE_NAME=ENV_VARIABLE_DATA` либо флага `--env-file .ENVFILE`, если набор переменных определен в файле по одной переменной окружения на строку. Однако данный метод может использоваться и для сохранения параметров по умолчанию.

**Форматы использования директивы:**
* `ENV KEY VALUE` — простой путь, позволяющий определить одну переменную окружения;
* `ENV KEY1=VALUE1[ ...]` — более сложный путь, который позволяет выставить несколько переменных окружения за одну директиву, тем самым уменьшая количество директив. Возможен перенос строки для удобства чтения методом, аналогичным с директивой `RUN`, — то есть с дописыванием `\` в конце строки и продолжением на следующей. Значения переменных можно внести в двойные кавычки (`"`), если переменная содержит пробел.

Расположение директивы `ENV` напрямую связано с тем, к чему будет привязана переменная. Так, например, если `ENV` находится перед `FROM`, то сборка окончится неудачно, поскольку не существует операционной системы (в понятиях сборки — контекста), к которому переменная окружения должна быть применена.

**Примеры:**
* **Правильно:** переменная окружения будет привязана к образу
  ```dockerfile
  FROM nginx:stable-alpine
  ENV KEY VALUE
  ```
* **Неправильно:** ошибка
  ```dockerfile
  ENV KEY VALUE
  FROM nginx:stable-alpine
  ```

Как следует из формата использования, значения переменных задаются явно и не связаны с тем, что происходит в самом образе. Однако это не значит, что значения можно задавать только непосредственно в Dockerfile. Да, у `docker build` нет параметра `--env` или `--env-file`, нельзя подключать на этапе сборки Volume, как у `docker run`, но есть другая директива, которая позволяет решить вопрос параметризации.

## ARG

**ARG** — данная директива позволяет определить, какие имена аргументов можно передавать при сборке приложения, значения которых позволяется использовать в других директивах.

Другими словами, `ARG` позволяет передать определенный параметр, который потом можно использовать в других директивах, влияя на этапе начала сборки на то, какие действия будут совершаться.

**Формат использования директивы:**
```dockerfile
ARG ARG_NAME[=ARG_DEFAULT_VALUE]
```
в котором:
* `ARG_NAME` — имя аргумента,
* `ARG_DEFAULT_VALUE` — значение аргумента по умолчанию, если при начале сборки этот параметр не передан. Это опциональный параметр, без которого `ARG_NAME` представляет собой пустую переменную.

Как мы видим, в отличие от `ENV`, несколько аргументов для одной директивы здесь задать нельзя.

Передача параметров производится через флаг `--build-arg` вызова команды `docker build`, например, `docker build --build-arg KEY=VALUE`.

Стоит отметить, что `ARG` отличается от `ENV` тем, что данные из `ARG` **НЕ** доступны в контейнере, а доступны только на этапе сборки! `ENV` — доступен и во время сборки, и во время запуска контейнера из собранного образа.

Использовать `ARG` можно в связке с другими директивами. Наиболее распространенные случаи использования:

* **Для установки переменных окружения** — `ARG` не сохраняется в контейнере, но поскольку есть директива `ENV` и с любой из директив можно использовать `ARG`, то можно сохранить значение в `ENV`, используя следующую структуру:
  ```dockerfile
  ARG KEY
  ENV KEY $KEY
  ```
* **Определение версии пакета, которая используется для сборки приложения.** Как правило, используется вместе с первым методом, чтобы сохранить сервисную информацию.
  ```dockerfile
  ARG NODE_VERSION
  ENV NODE_VERSION="$NODE_VERSION"
  RUN curl -SsL https://nodejs.org -o /tmp/node.tgz && tar -xzf /tmp/node.tgz -C /usr/local --strip-components=1 && rm /tmp/node.tgz
  ```
Но можно и без посредника — тогда значения будут браться напрямую из `ARG`, которая выступает как временная переменная окружения, доступная лишь на этапе сборки:
* **Определение версии образа, который используется как основа приложения.**
  ```dockerfile
  ARG NGINX_VERSION
  FROM nginx:$NGINX_VERSION-alpine
  ```

Обрати внимание, что есть один кейс, для которого **НЕ** рекомендуется использовать `ARG` — передача секретных данных. Да, значения `ARG` не будут доступны в контейнере, и позднее мы еще разберем, почему официальная документация запрещает это.

В отличие от `ENV` (который привязывается к конкретному образу, где устанавливается переменная окружения), `ARG` доступен во всех директивах, поэтому, если сравнивать с `ENV`, возможны следующие схемы его применения:

* **Правильно:** переменная окружения будет привязана к образу и взята из `ARG`, НО не может быть использована в директиве `FROM`
  ```dockerfile
  FROM nginx:stable-alpine
  ARG KEY
  ENV KEY $KEY
  ```
* **Правильно:** переменная окружения будет привязана к образу и взята из `ARG`, НО не будет доступна в формировании образа, то есть может быть использована только в директивах `FROM`
  ```dockerfile
  ARG KEY
  FROM nginx:$KEY
  ```
* **Неправильно:** ошибка, вызванная `ENV` - данная директива НЕ может располагаться вне `FROM`
  ```dockerfile
  ARG KEY
  ENV KEY VALUE
  FROM nginx:stable-alpine
  ```
* **Неправильно:** ошибка, вызванная расположением `ARG` - директива находится перед `FROM`, то есть не влияет на после `FROM`
  ```dockerfile
  ARG KEY
  FROM nginx:stable-alpine
  ENV KEY $KEY
  ```

Итак, мы познакомились с новым материалом. Да, мы рассмотрели не все директивы, но мы рассмотрели те, которые реально используются на практике каждый день тысячами людей по всему миру. Для всего остального есть официальная документация с описанием директив и `man dockerfile`.
