### 1. Что такое слой (Layer) в Docker-образе и как он связан с UnionFS?
**Ответ:**
Слой (Layer) — это зафиксированное изменение состояния файловой системы относительно предыдущего состояния. Docker-образ состоит из набора таких слоёв, доступных только для чтения (read-only), которые объединяются в единую файловую систему с помощью драйвера **UnionFS** (основные реализации: `overlay2`, `aufs`, `btrfs`). При запуске контейнера поверх слоёв образа добавляется один тонкий слой для записи (container layer).

**Пример проверки используемого драйвера и слоёв:**
```bash
docker info | grep "Storage Driver"
docker inspect --format='{{json .RootFS.Layers}}' inno-dkr-11:default
```

### 2. Как работают механизмы UnionFS и Copy-on-Write (CoW)?
**Ответ:**
**UnionFS** накладывает директории (слои) друг на друга, формируя единое дерево каталогов для контейнера. Согласно стратегии **Copy-on-Write (CoW)**, каждый последующий слой хранит только дельту (изменения) относительно предыдущего. Если в новом слое требуется изменить или даже просто поменять права доступа к файлу из нижнего слоя, файл целиком копируется в верхний слой, и изменения применяются уже к копии.

**Пример проверки размера верхнего writable-слоя запущенного контейнера:**
```bash
docker ps -s
```

### 3. Какие директивы Dockerfile создают слои и почему важен их порядок?
**Ответ:**
Каждая директива в `Dockerfile` при сборке формирует новый шаг и слой. Основные директивы (`RUN`, `COPY`, `ADD`) создают полноценные слои с изменениями файловой системы, а мета-директивы (`ENV`, `WORKDIR`, `USER`, `CMD`, `EXPOSE`) добавляют метаданные в конфигурацию образа (в `docker history` отображаются с размером `0 B`). Порядок директив критичен, так как слои зависят друг от друга последовательно и кэшируются сверху вниз: часто меняющиеся инструкции (например, `COPY` исходного кода) нужно размещать ближе к концу файла, чтобы не инвалидировать кэш тяжёлых верхних слоёв (установки пакетов).

**Пример просмотра слоёв и команд, которые их создали:**
```bash
docker history inno-dkr-11:default
```

### 4. Почему очистка кэша apt или удаление файлов в отдельной инструкции RUN не уменьшает размер образа?
**Ответ:**
Потому что слои в образе неизменяемы (immutable). Если в одном слое выполнить `apt-get update`, кэш пакетов сохранится в этом слое навсегда. Выполнение `rm -rf /var/lib/apt/lists/*` в следующей инструкции `RUN` лишь создаёт поверх «маркер удаления» (whiteout-файл), скрывающий файлы от глаз внутри контейнера, но физически данные остаются в нижнем слое и продолжают занимать место в итоговом образе. Установку и очистку нужно объединять в одну инструкцию `RUN` через `&&`.

**Пример правильной очистки кэша в одном слое:**
```dockerfile
RUN apt-get update -y && apt-get install -y --no-install-recommends nginx && rm -rf /var/lib/apt/lists/*
```

### 5. Почему отдельная инструкция RUN chown дублирует размер файла и как это исправить?
**Ответ:**
Из-за механизма **Copy-on-Write** при выполнении `RUN chown user:user testfile` Docker копирует весь файл `testfile` (10 МБ) из слоя `COPY` в новый слой `RUN` только ради смены его метаданных (UID/GID), удваивая занимаемое место (20 МБ вместо 10 МБ). Чтобы избежать этого, владельца нужно назначать сразу в момент копирования с помощью флага `--chown`.

**Пример оптимизированного копирования:**
```dockerfile
COPY --chown=user:user testfile .
```

### 6. В чём разница между docker inspect и docker history при анализе слоёв, и почему в скачанных образах отображается `<missing>`?
**Ответ:**
* `docker inspect <имя_образа_или_ID_слоя>` выводит подробные JSON-метаданные, но срабатывает только для локально собранных слоёв, у которых сохранились промежуточные образы. Для слоёв скачанных образов команда вернёт ошибку `No such object`.
* `docker history <имя_образа>` показывает историю всех инструкций сборки, размер и возраст каждого слоя для любого образа.

Метка **`<missing>`** в столбце `IMAGE` у скачанных из Docker Hub образов означает, что образ был собран на другой машине (или в Docker BuildKit) и при публикации были загружены только сами файловые слои и финальный манифест без промежуточных локальных образов сборки.

**Пример анализа истории без обрезания вывода:**
```bash
docker history inno-dkr-11:default --no-trunc
```

### 7. Почему нельзя использовать ARG для передачи и хранения секретов?
**Ответ:**
Значения, переданные через директиву `ARG` и флаг `--build-arg`, сохраняются в метаданных и истории сборки образа в открытом виде. Любой пользователь, имеющий доступ к образу, может прочитать пароли, токены или ключи с помощью команды `docker history`. Для безопасной передачи секретов при сборке следует использовать Docker BuildKit (`RUN --mount=type=secret,...`).

**Пример того, как секрет из ARG раскрывается в истории:**
```bash
docker history test:secret --no-trunc
```

### 8. Для чего при сборке используется флаг --rm=false и что происходит с промежуточными контейнерами по умолчанию?
**Ответ:**
По умолчанию (`--rm=true`) при выполнении каждой инструкции сборщик создаёт временный промежуточный контейнер, фиксирует изменения в новый слой и сразу удаляет этот контейнер (`Removing intermediate container ...`) для экономии места на диске. Флаг `--rm=false` отключает автоматическое удаление, сохраняя промежуточные контейнеры после завершения сборки для отладки.

**Пример сборки с сохранением промежуточных контейнеров:**
```bash
docker build --rm=false -t test:debug .
```

### 9. В чём разница между exec-формой CMD ["sleep", "infinity"] и ошибочной записью CMD ["sleep infinity"]?
**Ответ:**
В **exec-форме** (JSON-массив в квадратных скобках) Docker запускает процесс напрямую без вызова оболочки `/bin/sh -c`, воспринимая первый элемент массива как имя бинарного файла, а последующие — как его аргументы. При записи `CMD ["sleep infinity"]` Docker ищет в `$PATH` один исполняемый файл с пробелом в названии (`"sleep infinity"`), не находит его и завершает старт контейнера с ошибкой `executable file not found in $PATH`.

**Пример правильной exec-формы:**
```dockerfile
CMD ["sleep", "infinity"]
```
