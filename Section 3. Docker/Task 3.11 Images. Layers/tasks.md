## Чекпоинт 1: Создание тестового файла размером 10 МБ

Для наглядной демонстрации механизма Copy-on-Write (CoW) при изменении прав доступа на файлы создаётся бинарный файл фиксированного размера в рабочей директории проекта (`~/task11`).

```bash
dd if=/dev/zero of=./testfile bs=1M count=10
```

### Разбор параметров и флагов:
* `dd` — утилита для поблочного копирования и конвертации данных.
* `if=/dev/zero` (Input File) — источник данных; специальное символьное устройство в Linux, выдающее бесконечный поток нулевых байтов (`0x00`).
* `of=./testfile` (Output File) — путь и имя создаваемого файла в текущей директории.
* `bs=1M` (Block Size) — размер одного блока чтения/записи за одну операцию (1 мегабайт).
* `count=10` — количество блоков для копирования (итоговый размер: `1M × 10 = 10 МБ`).

### Сложные моменты и ошибки:
* Если ранее для проверки сборки создавался пустой файл через `touch testfile`, его **обязательно нужно перезаписать** командой `dd`. Иначе в `docker history` слои с копированием и сменой прав будут весить `0 B` вместо `10.5 MB`, и эффект раздувания образа останется незамеченным.

**Пример использования:**
```bash
# Создание тестового файла размером 50 МБ со случайными данными (не сжимается)
dd if=/dev/urandom of=./random_payload.bin bs=1M count=50 status=progress
```

## Чекпоинт 2: Подготовка исходного Dockerfile и разбор его проблем

В рабочей директории рядом с `testfile` создаётся файл с точным именем `Dockerfile` (с заглавной буквы, без расширения).

```dockerfile
FROM ubuntu:20.04

ENV testenv1=env1

# Создадим пользователя
RUN groupadd --gid 2000 user && useradd --uid 2000 --gid 2000 --shell /bin/bash --create-home user

# Посмотрим состояние кэша apt до установки nginx
RUN ls -lah /var/lib/apt/lists/
RUN apt-get update -y && apt-get install nginx -y

# Повторно проверим состояние кэша apt
RUN ls -lah /var/lib/apt/lists/

# Очистим кэш
RUN rm -rf /var/lib/apt/lists/*
RUN ls -lah /var/lib/apt/lists/

# Скопируем наш тестовый файл
COPY testfile .

# Сменим права
RUN chown user:user testfile

USER user

CMD ["sleep", "infinity"]
```

### Разбор директив и флагов:
* `FROM ubuntu:20.04` — задаёт базовый образ, поверх нижних слоёв которого будут накладываться новые изменения.
* `ENV testenv1=env1` — задаёт переменную окружения на этапе сборки и внутри запускаемого контейнера.
* `RUN groupadd --gid 2000 user` — создаёт системную группу `user` с фиксированным идентификатором GID `2000`.
* `useradd --uid 2000 --gid 2000 --shell /bin/bash --create-home user` — создаёт пользователя `user` с UID `2000`, основной группой `2000`, командной оболочкой `/bin/bash` и домашним каталогом `/home/user`.
* `apt-get update -y && apt-get install nginx -y` — обновляет индексы пакетов и устанавливает `nginx` с автоматическим подтверждением (`-y`).
* `rm -rf /var/lib/apt/lists/*` — рекурсивно (`-r`) и принудительно (`-f`) удаляет скачанные списки пакетов `apt`.
* `COPY testfile .` — копирует `testfile` из контекста сборки на хосте в текущую рабочую директорию образа (по умолчанию `/`, так как `WORKDIR` не задан).
* `RUN chown user:user testfile` — меняет владельца и группу файла на `user:user`.
* `USER user` — переключает активного пользователя для последующих инструкций и запуска контейнера (вместо `root`).
* `CMD ["sleep", "infinity"]` — команда по умолчанию при старте контейнера, удерживающая его в запущенном состоянии.

### Сложные моменты и ошибки в исходном шаблоне:
1. **Синтаксическая ошибка в `CMD ["sleep infinity"]`:** В оригинальном тексте задания команда и аргумент записаны одной строкой внутри массива JSON. В exec-форме Docker ищет исполняемый файл с буквальным именем `"sleep infinity"` (с пробелом), из-за чего образ соберётся, но запуск контейнера упадёт с ошибкой `exec: "sleep infinity": executable file not found in $PATH`. Правильный синтаксис — разделять команду и аргументы: `CMD ["sleep", "infinity"]`.
2. **Неэффективная очистка кэша `apt`:** Инструкции `apt-get update` и `rm -rf /var/lib/apt/lists/*` вынесены в разные директивы `RUN`. Так как каждая директива фиксирует свой слой в UnionFS, удалённые в следующем слое файлы всё равно физически остаются в предыдущем слое и не уменьшают итоговый размер образа.
3. **Дублирование файла при `RUN chown`:** Из-за механизма Copy-on-Write изменение метаданных файла (`chown`) в отдельном слое заставляет Docker скопировать весь 10-мегабайтный `testfile` в новый слой целиком.

**Пример использования:**
```bash
# Проверка синтаксиса и линтер Dockerfile без запуска сборки (через hadolint в контейнере)
docker run --rm -i hadolint/hadolint < Dockerfile
```

## Чекпоинт 3: Сборка базового образа inno-dkr-11:default

Запуск сборки образа из текущей директории с использованием сети хоста:

```bash
sudo docker build --network=host -t inno-dkr-11:default .
```

### Разбор параметров и флагов:
* `docker build` — команда сборки образа из `Dockerfile`.
* `--network=host` — подключает контейнеры этапа сборки (`RUN`) напрямую к сетевому стеку хост-машины в обход виртуального моста `docker0` (помогает при проблемах с DNS, MTU или VPN при скачивании пакетов через `apt`).
* `-t inno-dkr-11:default` (`--tag`) — присваивает собранному образу имя (`inno-dkr-11`) и тег (`default`).
* `.` (точка в конце) — обязательный позиционный аргумент, указывающий путь к **контексту сборки** (текущая директория, откуда демон Docker забирает `Dockerfile` и файлы для инструкций `COPY`/`ADD`).

### Сложные моменты и ошибки:
* **Ошибка `ERROR: docker: 'docker buildx build' requires 1 argument`:** Возникает, если забыть указать точку (`.`) в конце команды `docker build`. Без указания пути к контексту сборки Docker не знает, где искать файлы.
* **Ошибка отсутствия `Dockerfile`:** Перед запуском сборки необходимо убедиться через `ls -la`, что в папке с `testfile` действительно создан файл `Dockerfile`.

**Пример использования:**
```bash
# Сборка без использования кэша предыдущих сборок и с явным указанием файла
docker build --no-cache --network=host -f Dockerfile -t inno-dkr-11:default .
```

## Чекпоинт 4: Анализ образа и слоёв (docker inspect и docker history)

После успешной сборки выполняется исследование метаданных образа и списка его слоёв.

```bash
sudo docker inspect inno-dkr-11:default
sudo docker history inno-dkr-11:default --no-trunc
```

### Разбор параметров и флагов:
* `docker inspect inno-dkr-11:default` — выводит полную низкоуровневую конфигурацию образа в формате JSON: переменные окружения (`Env`), команду запуска (`Cmd`), активного пользователя (`User`), архитектуру и список SHA256-хешей всех слоёв в секции `RootFS.Layers`.
* `docker history inno-dkr-11:default` — отображает таблицу всех слоёв образа от верхнего к базовому, команду создания каждого слоя (`CREATED BY`) и его размер (`SIZE`).
* `--no-trunc` — отключает обрезание длинных строк в выводе (показывает полные SHA256-идентификаторы слоёв и полные команды в столбце `CREATED BY`).

### На что обратить внимание в выводе:
* В секции `RootFS.Layers` команды `docker inspect` отображаются только слои, реально вносящие изменения в файловую систему (`RUN`, `COPY`), тогда как мета-директивы (`ENV`, `USER`, `CMD`) создают слои размером `0 B` в `docker history`.
* В `docker history` слой с `COPY testfile .` занимает `10.5MB`, и следующий за ним слой `RUN chown user:user testfile` **тоже занимает `10.5MB`** — итого один файл занял `21 MB`.
* Слой `RUN apt-get update -y && apt-get install nginx -y` занимает десятки мегабайт, а слой `RUN rm -rf /var/lib/apt/lists/*` весит `0B` — место на диске не освободилось.

**Пример использования:**
```bash
# Вывод только списка хешей слоёв образа с помощью встроенного Go-шаблона
sudo docker inspect --format='{{range .RootFS.Layers}}{{println .}}{{end}}' inno-dkr-11:default
```

## Чекпоинт 5: Оптимизация слоёв (флаг COPY --chown и очистка кэша apt)

Чтобы избежать дублирования `testfile` в слоях при смене владельца, используется встроенный флаг `--chown` директивы `COPY`. Для реального уменьшения размера образа очистка кэша `apt` также объединяется в один слой с установкой пакетов.

```dockerfile
FROM ubuntu:20.04

ENV testenv1=env1

# Создаём пользователя и устанавливаем nginx с очисткой кэша в одном слое
RUN groupadd --gid 2000 user \
    && useradd --uid 2000 --gid 2000 --shell /bin/bash --create-home user \
    && apt-get update -y \
    && apt-get install -y --no-install-recommends nginx \
    && rm -rf /var/lib/apt/lists/*

# Копируем файл и сразу назначаем владельца без создания дополнительного слоя
COPY --chown=user:user testfile .

USER user

CMD ["sleep", "infinity"]
```

Сборка оптимизированного образа с новым тегом для сравнения размеров:

```bash
sudo docker build --network=host -t inno-dkr-11:optimized .
sudo docker images inno-dkr-11
```

### Разбор параметров и флагов:
* `--chown=user:user` — флаг директивы `COPY` (и `ADD`), который назначает владельца и группу для копируемых файлов и директорий сразу при формировании слоя. Принимает имена или числовые `UID:GID` (например, `--chown=2000:2000`).
* `--no-install-recommends` — флаг `apt-get install`, запрещающий установку рекомендуемых (необязательных) зависимостей, что дополнительно сокращает размер слоя.
* `docker images inno-dkr-11` — выводит все локальные образы с именем `inno-dkr-11` и разными тегами (`default` и `optimized`) для прямого сравнения столбца `SIZE`.

**Пример использования:**
```bash
# Проверка прав доступа на скопированный файл внутри контейнера без его длительного запуска
sudo docker run --rm inno-dkr-11:optimized ls -la /testfile
```

## Нюансы рабочего окружения (VS Code Remote-SSH и права sudo)

При разработке через VS Code по протоколу Remote-SSH редактирование `Dockerfile` выполняется в графическом интерфейсе редактора на удалённой машине, а сборка и запуск контейнеров — через встроенный терминал VS Code (`Ctrl + ~` или `Ctrl + J`).

Чтобы работать с Docker без постоянного ввода `sudo` и использовать официальное расширение Docker для VS Code, текущего пользователя добавляют в системную группу `docker`:

```bash
sudo usermod -aG docker $USER
```

### Разбор параметров и флагов:
* `usermod` — утилита для изменения параметров учётной записи пользователя в Linux.
* `-a` (`--append`) — добавляет пользователя в указанные группы, **не удаляя** его из остальных групп (критически важный флаг: без `-a` пользователь потеряет права `sudo` и другие группы).
* `-G docker` (`--groups`) — имя целевой группы, которой разрешён доступ к UNIX-сокету `/var/run/docker.sock`.
* `$USER` — переменная окружения с именем текущего пользователя (`amp`).

*(Для применения новых прав группы необходимо переподключиться по SSH или перезапустить окно VS Code).*

**Пример использования:**
```bash
# Применить изменения групп в текущей сессии терминала без переподключения по SSH
newgrp docker && docker ps
```
