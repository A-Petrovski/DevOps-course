# Контрольные вопросы: Task 3.15 — Dockerfiles и Best-practices

## 1. В каких случаях в одном репозитории используют несколько Dockerfile?
Несколько Dockerfile применяют, когда для одного проекта требуется:
- использовать разные базовые образы (например, полноценный Debian для разработки и минималистичный Alpine или Slim для продакшена);
- добавить разный набор системных утилит и инструментов отладки;
- собрать образы с разным составом зависимостей приложения (например, с тестами и линтерами для `dev` и только с runtime-библиотеками для `prod`).

```bash
docker build -f Dockerfile.dev -t app:dev .
docker build -f Dockerfile.prod -t app:prod .
```

## 2. Как собрать образ, если файл инструкций называется не `Dockerfile` или лежит в подпапке?
Для указания нестандартного имени или пути к файлу используется флаг `-f` (или `--file`) команды `docker build`. При этом точка `.` в конце команды по-прежнему должна указывать на корневой контекст сборки проекта.

```bash
docker build --file ./docker/prod -t my-app:prod .
```

## 3. Зачем копировать `Gemfile` и `package.json` до копирования всего остального кода (`COPY . .`)?
Docker собирает образы послойно и кэширует результат каждой инструкции. Если сначала скопировать только манифесты зависимостей и выполнить `bundle install` / `yarn install`, этот тяжёлый слой закэшируется. При последующих изменениях в коде приложения Docker переиспользует готовый слой с библиотеками вместо их повторного скачивания.

```dockerfile
COPY Gemfile Gemfile.lock package.json yarn.lock ./
RUN bundle install && yarn install
COPY . .
```

## 4. Как исключить установку development- и test-зависимостей в Ruby-образе при использовании Bundler?
Перед запуском `bundle install` необходимо задать в конфигурации Bundler параметр `without` со списком исключаемых групп (`development test`). В современных версиях Bundler это делается через `bundle config set`.

```dockerfile
RUN bundle config set --local without 'development test' \
    && bundle install --jobs 4 --retry 3
```

## 5. Для чего внутри Dockerfile задаётся инструкция `ENV RAILS_ENV=production`?
Инструкция `ENV` записывает переменную окружения внутрь метаданных образа, поэтому она будет доступна как на этапе сборки (например, при компиляции ассетов), так и при каждом запуске контейнера. В Ruby on Rails `RAILS_ENV` определяет режим кэширования, логирования, уровень детализации ошибок и выбор секции настроек базы данных.

```dockerfile
ENV RAILS_ENV=production
```

## 6. Почему базу данных не запускают внутри одного контейнера вместе с веб-приложением?
Согласно принципам Docker (один основной процесс на контейнер) и методологии Twelve-Factor App, приложение должно быть stateless, а хранение состояния выносится во внешние сервисы. Отдельный контейнер для БД позволяет независимое масштабирование, безопасное обновление образа приложения без потери данных (через Docker Volumes) и упрощает управление жизненным циклом сервисов.

```bash
docker run -d --name alonetone-db -e MYSQL_ROOT_PASSWORD=secret mysql:8.0
```

## 7. Что означает точка `.` в конце команды `docker build -t app:latest .`?
Точка задаёт **контекст сборки** — путь на хост-машине, все файлы из которого Docker CLI упаковывает в архив и отправляет Docker-демону перед началом сборки. Инструкции `COPY` и `ADD` могут обращаться только к файлам внутри этого контекста. Чтобы не отправлять демону тяжёлую папку `.git` или локальные логи, используют файл `.dockerignore`.

```bash
cat <<EOF > .dockerignore
.git
log/*
tmp/*
node_modules
EOF
```
