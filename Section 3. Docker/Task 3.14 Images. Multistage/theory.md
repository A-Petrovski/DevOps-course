## Введение и принцип работы Multi-stage builds

В текущем задании рассматривается механизм работы с образами **Multi-stage builds** — многоэтапные сборки.

**Multi-stage builds** — это возможность использовать несколько базовых образов, чтобы выполнять разные действия с исходными файлами, после чего можно передать результат работы в другие образы. Это делается с целью уменьшения размеров образа либо для передачи файлов в другую исполняемую среду.

Приближенный к жизни кейс — компилируемый контент:
* собранная статика;
* собранные бинарные файлы.

Средства, которые используются для сборки контента из-за зависимостей, могут иметь общий объем файлов, превышающий выходной контент в несколько раз, что является нецелесообразным с точки зрения использования конечным пользователем.

## Общая структура Multi-stage Dockerfile

В общем случае `Dockerfile` для Multi-stage выглядит так:

```dockerfile
FROM $BUILD_IMAGE AS build
# Команды, стягивающие зависимости и собирающие конечный контент

FROM $RUNTIME_IMAGE
COPY --from=build $SRC_COMPILED_PATH $DEST_COMPILED_PATH
```

Где:
* **`BUILD_IMAGE`** — образ, который используется для сборки компилиемого контента;
* **`RUNTIME_IMAGE`** — образ, который используется для хранения и запуска скомпилированного контента;
* **`SRC_COMPILED_PATH`** — путь в образе сборки, в котором расположен скомпилированный контент;
* **`DEST_COMPILED_PATH`** — путь в исполняемом образе, в котором сохраняется скомпилированный контент.

## Копирование между этапами и из внешних образов (`COPY --from`)

Флаг `--from=build`, присутствующий рядом с командой `COPY`, дает понять, из какого образа в рамках данного контекста требуется копировать данные. То есть копирование происходит не из директории, где собирается образ (контекст сборки), а из образа, который уже собрали — без опции этот путь применялся бы к контексту.

Данная схема позволяет копировать не только из образов, которые собираются внутри того же файла сборки, но и из внешних образов, например, из `nginx:stable`.

## Кэширование и безопасность (работа с секретами)

* **Кэширование:** в предложенной схеме применимы те же принципы кэширования и те же правила инвалидации кэша, что и при обычной сборке образов.
* **Безопасность:** секретные данные остаются видны в `history`, поэтому, используя multi-stage, можно решить вопрос с обнаружением секретов. Директивы с секретами останутся в образе-сборщике, а в истории конечного образа их не будет.

## Таргетированная сборка промежуточных этапов (`--target`)

Существуют сценарии, при которых необходимо получить образ именно из середины сборки. Для этого у `docker build` есть флаг `--target`, в который передается имя подобраза, который требуется получить.

Пример `Dockerfile`:

```dockerfile
FROM alpine:latest AS build
ARG test
ENV DAEMON_VERSION 1.0.0
RUN echo $test > tmpfile

FROM alpine:latest
COPY --from=build tmpfile tmpfile
```

Сборка в общем случае:

```bash
$ docker build .
Sending build context to Docker daemon  2.048kB
Step 1/6 : FROM alpine:latest AS build
 ---> 965ea09ff2eb
Step 2/6 : ARG test
 ---> Using cache
 ---> 2b3c376d3b77
Step 3/6 : ENV DAEMON_VERSION 1.0.0
 ---> Using cache
 ---> 1e258bed828e
Step 4/6 : RUN echo $test > tmpfile
 ---> Using cache
 ---> 91cecca34cbc
Step 5/6 : FROM alpine:latest
 ---> 965ea09ff2eb
Step 6/6 : COPY --from=build tmpfile tmpfile
 ---> 09fd373940c3
Successfully built 09fd373940c3
```

Получение только образа этапа `build` с помощью флага `--target`:

```bash
$ docker build --target build .
Sending build context to Docker daemon  2.048kB
Step 1/4 : FROM alpine:latest AS build
 ---> 965ea09ff2eb
Step 2/4 : ARG test
 ---> Using cache
 ---> 2b3c376d3b77
Step 3/4 : ENV DAEMON_VERSION 1.0.0
 ---> Using cache
 ---> 1e258bed828e
Step 4/4 : RUN echo $test > tmpfile
 ---> Using cache
 ---> 91cecca34cbc
Successfully built 91cecca34cbc
```

## Типовой сценарий применения (Frontend + Backend)

Самая распространенная ситуация, в которой используется схема таргетированной многоэтапной сборки — это снятие нагрузки по отдаче статики с основного приложения. Перед приложением ставится кэширующий прокси (например, `nginx`), который отдает всю статику, а динамические запросы (REST-запросы) проксирует в backend, стоящий за ним.
