## 1. Что такое multistage Docker build и в чем его преимущества?

**Multi-stage build (многоэтапная сборка)** — это механизм Docker, позволяющий использовать несколько инструкций `FROM` в одном `Dockerfile`. Каждый блок `FROM` начинает новый этап сборки на базе отдельного образа и позволяет выборочно копировать готовые артефакты (бинарные файлы, скомпилированную статику, библиотеки) из одного этапа в другой.

**Основные преимущества:**
* **Минимальный размер итогового образа:** в финальный образ попадают только скомпилированные артефакты и минимальная среда исполнения (например, `alpine` или `scratch`), а тяжелые компиляторы, SDK, менеджеры пакетов и исходный код остаются в промежуточных слоях и не включаются в результат.
* **Повышение безопасности (уменьшение поверхности атаки):** в продакшен-образе отсутствуют утилиты вроде `curl`, `git`, `gcc`, `npm` или `go`, которые злоумышленник мог бы использовать при компрометации контейнера. Также команды передачи секретов (`ARG`), выполненные на этапе сборки, не отображаются в `docker history` финального образа.
* **Единый `Dockerfile` без костылей:** отпадает необходимость писать внешние bash-скрипты и использовать несколько отдельных `Dockerfile` для сборки артефактов на хосте с последующим копированием в runtime-образ.

## 2. Как работает multistage Docker build в контексте создания Docker-образов?

1. **Изоляция этапов:** каждый раз, когда парсер `Dockerfile` встречает новую директиву `FROM`, он инициализирует чистую файловую систему на базе указанного образа. Каждый этап имеет свой порядковый индекс (начиная с `0`) и может иметь собственное имя (`FROM <image> AS <stage_name>`).
2. **Изоляция переменных:** переменные уровня сборки (`ARG`) действуют только внутри того этапа `FROM`, в котором они объявлены.
3. **Межэтапный перенос данных:** инструкция `COPY --from=<stage_name|index> <src> <dest>` монтирует файловую систему указанного предыдущего этапа (или внешнего образа) и переносит нужные файлы в текущий этап.
4. **Отбрасывание промежуточных слоев:** по завершении сборки Docker тегирует только файловую систему последнего этапа (либо этапа, явно указанного через флаг `--target`). Промежуточные этапы не попадают в итоговый образ и не отображаются в его `docker history` (оставаясь лишь в локальном build-кэше на машине сборщика).

## 3. Какие возможности предоставляют multistage Docker builds для оптимизации размера образов и уменьшения времени сборки?

### Оптимизация размера
* **Разделение Build и Runtime сред:** использование тяжелых образов с инструментами сборки (например, `golang:1.19` ~300–800 МБ или `node:10` ~900 МБ) на первом этапе и сверхлегких образов (`alpine` ~5–7 МБ или `nginx:alpine` ~20–40 МБ) на финальном этапе сокращает размер образа в десятки раз.
* **Отсутствие мусора от промежуточных слоев:** даже если на этапе сборки генерируются гигабайты временного кэша компиляции или `node_modules`, они не требуют ручной очистки в той же инструкции `RUN`, так как весь этап целиком отбрасывается.

### Уменьшение времени сборки
* **Независимое кэширование этапов:** каждый этап использует стандартный механизм кэширования слоев Docker. Если код фронтенда не менялся, этап сборки JS полностью берется из кэша при пересборке бэкенда.
* **Параллельное выполнение (BuildKit):** при включенном BuildKit независимые этапы сборки (например, сборка Go-бэкенда и сборка Node.js-фронтенда в `Dockerfile` Grafana) выполняются параллельно на разных ядрах CPU, так как они не зависят друг от друга до момента финального копирования.
* **Таргетированная сборка (`--target`):** позволяет собирать только нужную часть проекта (например, только статику для CDN/Nginx или только тестовый этап), не тратя время на выполнение остальных этапов файла.

## 4. Как правильно разделить этапы сборки в multistage Docker build и как определить, какие компоненты приложения должны быть включены в каждый этап?

При проектировании многоэтапного `Dockerfile` следует придерживаться принципа разделения по жизненному циклу артефактов:

1. **Этап подготовки зависимостей и компиляции (Builder stage):**
   * *Что включать:* базовый образ с нужным SDK/компилятором (`golang`, `node`, `maven`, `rust`), системные утилиты сборки (`git`, `make`, `gcc`), файлы описания зависимостей (`go.mod`, `package.json`, `requirements.txt`) и исходный код.
   * *Правило оптимизации:* сначала копируются только файлы зависимостей и выполняется их установка (`go mod download`, `npm ci`), и только следующим слоем копируется остальной исходный код. Это позволяет кэшировать зависимости при изменении кода.
2. **Этап тестирования / линтинга (опциональный Test stage):**
   * *Что включать:* наследуется от `builder` (`FROM builder AS tester`), запускает unit-тесты и линтеры. Вызывается в CI-пайплайне через `--target tester`.
3. **Финальный этап исполнения (Runtime / Production stage):**
   * *Что включать:* минимально необходимый образ (`alpine`, `distroless`, `nginx:alpine`), системные runtime-зависимости (например, `ca-certificates` для HTTPS-запросов или `tzdata` для часовых поясов), непривилегированного пользователя (`USER`), скомпилированный артефакт (бинарник/статика) и конфигурационные файлы по умолчанию.
   * *Что строго исключать:* исходный код (для компилируемых языков), компиляторы, пакетные менеджеры сборки, отладочные утилиты, секреты и ключи доступа к приватным репозиториям.
