## Введение

Вернемся к работе с образами. Как уменьшить объем образа, мы уже обсудили, теперь давай рассмотрим пути для уменьшения времени сборки.

Основной механизм по уменьшению времени — это кэширование. Дальнейшее ускорение сборки возможно только за счет увеличения ресурсов хоста, который собирает образ, и за счет средств сборки, используемых внутри самого контейнера.

В этом задании рассматривается, как кэширование можно применить на практике и как строить `Dockerfile` таким образом, чтобы повторная сборка происходила с максимальным количеством закэшированных слоев за минимальное время.

Рассмотрим зависимости кода (`requirements.txt`, `Gemfile`, `package.json`). Docker-образ содержит внутри приложение и зависимости, требуемые для запуска этого приложения. Приложение мы можем использовать по минимуму, но зависимости нужно использовать максимально.

Как правило, зависимости в образе бывают двух видов — **системные** и **зависимости кода**. Главное в них то, что они могут не меняться долгое время. Но если зависимости кода могут меняться, например, раз в неделю, то список системных зависимостей обуславливается зависимостями кода. Например, когда требуются dev-пакеты какой-то библиотеки для сборки зависимости. Эти зависимости используются далеко не во всех проектах, но устанавливаться могут довольно долго.

## Универсальная структура Dockerfile

Алгоритм построения `Dockerfile` почти для каждого проекта, в котором производится сборка:

1. Определение базового образа
2. Определение переменных окружений — опционально
3. Установка системных зависимостей — через пакетные менеджеры ОС, `curl` и прочие утилиты
4. Определение рабочей директории — опционально
5. Копирование списка зависимостей кода из репозиториев
6. Установка зависимостей кода
7. Копирование исходного кода
8. Сборка исходного кода — если требуется
9. Определение директивы запуска приложения

Следование этому алгоритму позволяет повторной сборке с использованием кэширования сэкономить много времени.

## Практический пример ускорения сборки

Пример `Dockerfile`:

```dockerfile
FROM ubuntu:18.04
ARG NODE_VERSION=13.1.0
ENV NODE_VERSION="$NODE_VERSION"
RUN apt update \
    && apt install sed curl ca-certificates -y --no-install-recommends \
    && curl -SsL https://nodejs.org/dist/v$NODE_VERSION/node-v$NODE_VERSION-linux-x64.tar.gz -o /tmp/node.tgz \
    && tar -xzf /tmp/node.tgz -C /usr/local --strip-components=1 \
    && rm /tmp/node.tgz
WORKDIR /app/
COPY package.json .
RUN npm install
COPY server.js .
CMD ["npm", "start"]
```

Первичная сборка образа:

```bash
$ time docker build .
...
real    3m40.199s
user    0m0.232s
sys     0m0.077s
```

Вся операция заняла 3 минуты 40 секунд.

Изменение зависимостей кода для проверки скорости сборки с учетом уже собранного образа, где присутствуют все системные зависимости:

```bash
$ echo >> package.json
$ time docker build .
...
real    0m22.975s
user    0m0.062s
sys     0m0.024s
```

Повторная сборка заняла около 23 секунд. Сборка образа занимает немного времени при изменении исходного кода.

## Разбиение образа на подобразы

Еще один подход к оптимизации времени сборки — разбиение образа на подобразы. Как правило, этот метод актуален в том случае, если используется микросервисная архитектура и все приложения написаны на одном языке с одинаковыми зависимостями, плюс есть свои инфраструктурные зависимости (например, корневой сертификат). В этом случае базовый образ может быть довольно объемным, но все зависит от потребностей проекта.
