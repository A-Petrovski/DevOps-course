# Контрольные вопросы для самопроверки: Оптимизация сборки Docker-образов

### 1. Почему при первичной сборке образа скачивание базового образа и установка зависимостей занимают основную часть времени?
При первом запуске сборки у Docker отсутствует локальный кэш. Демон `dockerd` вынужден загружать по сети все слои базового образа (`python:3.7-buster`), распаковывать их на диск, скачивать пакеты из PyPI и выполнять их установку с нуля.
```bash
docker system df  # Проверка объема локального кэша образов и слоев
```

### 2. Какие шаги сборки пропускаются при изменении исходного кода и почему не пересобирается слой с зависимостями?
Docker проверяет инструкции `Dockerfile` сверху вниз. Инструкции `FROM`, `WORKDIR`, `COPY Pipfile* ./` и `RUN pipenv install...` не изменились (контрольные суммы `Pipfile` и `Pipfile.lock` остались прежними), поэтому они берутся из кэша (`CACHED`). Кэш сбрасывается только начиная с инструкции `COPY *.py ./`, где изменился хеш файла с кодом.
```bash
docker history counter:normal  # Просмотр слоев образа и времени их создания
```

### 3. Что произойдет с объемом образа, если удалить `Pipfile*` и `pip` в отдельной директиве `RUN`, а не в той же, где они устанавливались?
Итоговый размер образа не уменьшится. Файловая система Docker (OverlayFS) работает по принципу Copy-on-Write: каждая инструкция `RUN` создает новый неизменяемый слой поверх предыдущего. Удаление файлов в следующем слое лишь создает специальную метку скрытия (whiteout file), но сами файлы физически остаются в нижнем слое и продолжают занимать место.
```dockerfile
# Правильно: установка и удаление в одном слое
RUN pip install pipenv && pipenv install --system --deploy && pip uninstall -y pipenv pip && rm -rf Pipfile*
```

### 4. Как меняется время повторной сборки при использовании ключа `--squash` по сравнению с обычной пересборкой и почему?
Повторная сборка с флагом `--squash` занимает больше времени, чем обычная пересборка с кэшем. Хотя тяжелые шаги установки зависимостей берутся из кэша, после выполнения `COPY *.py ./` демон Docker обязан выполнить дополнительную ресурсоемкую операцию: экспортировать слои, объединить их файловые системы и заново упаковать в один финальный слой.
```bash
DOCKER_BUILDKIT=0 time docker build -f Dockerfile.mini --squash -t counter:squash .
```

### 5. За счет чего образ `counter:squash` занимает меньше места на диске, чем `counter:normal`?
Размер уменьшается за счет двух факторов:
1. Физического удаления ненужных в runtime инструментов (`pip`, `pipenv`), манифестов (`Pipfile*`) и кэша загрузки внутри единой инструкции `RUN`.
2. Схлопывания метаданных промежуточных слоев в один слой с помощью флага `--squash`.
```bash
docker images counter
```

### 6. Почему при использовании флага `--squash` может потребоваться переменная `DOCKER_BUILDKIT=0`?
В современных версиях Docker по умолчанию включен движок сборки BuildKit, который не поддерживает классический флаг `--squash` (вместо этого в BuildKit используются multi-stage builds). Установка переменной окружения `DOCKER_BUILDKIT=0` принудительно переключает сборку на legacy-движок Docker Engine, где `--squash` работает корректно.
```bash
DOCKER_BUILDKIT=0 docker build --squash -t my-app:squashed .
```
