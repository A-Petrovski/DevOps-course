# Контрольные вопросы для самопроверки: Task 3.9 Images

## 1. Инструкция CMD в Dockerfile. Что представляет собой инструкция CMD и как она используется в Dockerfile? Какие различные форматы и параметры могут быть использованы для определения команды или исполняемого файла в инструкции CMD?

**Ответ:**
Инструкция `CMD` задаёт команду или параметры по умолчанию, которые будут выполнены при запуске контейнера. В `Dockerfile` может быть только одна активная директива `CMD` (если указать несколько, сработает только последняя). Если при запуске контейнера пользователь передаст свою команду в `docker run`, значение `CMD` из `Dockerfile` будет полностью перезаписано.

Существует два формата написания:
1. **Exec-формат (предпочтительный):** `CMD ["executable", "param1", "param2"]` — записывается в виде JSON-массива (обязательно в двойных кавычках). Команда запускается напрямую без вызова командной оболочки, получает `PID 1` и корректно обрабатывает сигналы завершения ОС (например, `SIGTERM` при `docker stop`).
2. **Shell-формат:** `CMD command param1 param2` — запускается как дочерний процесс оболочки `/bin/sh -c 'command param1 param2'`. Позволяет использовать переменные окружения оболочки (например, `$HOME`), но процесс получает `PID` отличный от `1` и может игнорировать сигналы остановки.
3. **Формат параметров для ENTRYPOINT:** `CMD ["param1", "param2"]` — используется в паре с `ENTRYPOINT` в exec-формате для передачи аргументов по умолчанию.

**Пример из практики:**
```dockerfile
# Exec-формат (рекомендуемый способ запуска)
CMD ["nginx", "-g", "daemon off;"]

# Переопределение CMD при запуске контейнера (вместо nginx запустится bash)
# docker run -it nginx:inno-dkr-09 /bin/bash
```

## 2. Разница между инструкциями CMD и ENTRYPOINT. Как инструкции CMD и ENTRYPOINT отличаются друг от друга? В каких ситуациях рекомендуется использовать каждую из этих инструкций?

**Ответ:**
Главное отличие заключается в поведении при передаче аргументов в `docker run`:
* **`CMD`** — это команда по умолчанию, которая **легко заменяется** любыми аргументами, переданными после имени образа в `docker run <image> <arg>`.
* **`ENTRYPOINT`** — это жестко заданный исполняемый файл («точка входа»), который **выполняется всегда** при старте контейнера. Любые аргументы, переданные после имени образа в `docker run`, не заменяют `ENTRYPOINT`, а дописываются в конец как его параметры. Переопределить сам `ENTRYPOINT` можно только специальным флагом `--entrypoint`.

**Когда что использовать:**
* Используйте **`CMD`**, когда создаёте универсальный образ (например, базовую ОС или среду разработки), где пользователю может понадобиться запускать разные команды по умолчанию.
* Используйте **`ENTRYPOINT`**, когда превращаете контейнер в специализированный сервис или CLI-утилиту (например, веб-сервер `nginx`, `curl` или скрипт резервного копирования), чтобы контейнер всегда запускал конкретную программу.

**Пример из практики:**
```bash
# Если в образе задан ENTRYPOINT ["curl"], то переданный URL добавится как аргумент:
docker run --rm my-curl-image https://example.com
# Внутри контейнера выполнится: curl https://example.com

# Принудительное переопределение ENTRYPOINT для отладки контейнера:
docker run -it --entrypoint /bin/sh nginx:inno-dkr-09
```

## 3. Инструкция ENTRYPOINT в Dockerfile. Что представляет собой инструкция ENTRYPOINT и как она используется в Dockerfile? Какие различные форматы и параметры могут быть использованы для определения команды или исполняемого файла в инструкции ENTRYPOINT?

**Ответ:**
Инструкция `ENTRYPOINT` определяет главный исполняемый файл или стартовый скрипт, который будет запущен при инициализации контейнера, превращая сам контейнер в исполняемое приложение. Как и в случае с `CMD`, если в `Dockerfile` указано несколько директив `ENTRYPOINT`, сработает только последняя.

Существует два формата написания:
1. **Exec-формат (рекомендуемый):** `ENTRYPOINT ["executable", "param1"]` — запускает бинарный файл или скрипт напрямую без оболочки `/bin/sh`. Только в этом формате `ENTRYPOINT` способен принимать аргументы из директивы `CMD` и из командной строки `docker run`.
2. **Shell-формат:** `ENTRYPOINT command param1` — оборачивает команду в `/bin/sh -c 'command param1'`. Существенный недостаток этого формата в том, что он **полностью игнорирует** любые аргументы из `CMD` и аргументы, переданные в `docker run`.

**Пример из практики:**
```dockerfile
# Использование ENTRYPOINT для запуска скрипта инициализации перед стартом приложения
COPY docker-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["docker-entrypoint.sh"]
```

## 4. Комбинирование инструкций CMD и ENTRYPOINT. Как можно комбинировать инструкции CMD и ENTRYPOINT для определения стартовой команды контейнера? Как порядок этих инструкций влияет на поведение контейнера?

**Ответ:**
Совместное использование `ENTRYPOINT` и `CMD` — это стандартный паттерн в Docker для разделения **неизменяемого исполняемого файла** и **аргументов по умолчанию**, которые при необходимости легко изменить при запуске.

* **Как это работает:** В `ENTRYPOINT` указывается сама программа (`ENTRYPOINT ["nginx"]`), а в `CMD` — её флаги по умолчанию (`CMD ["-g", "daemon off;"]`). При старте Docker склеивает оба JSON-массива в единую команду: `nginx -g "daemon off;"`. Если запустить `docker run nginx:inno-dkr-09 -t`, то `CMD` перезапишется на `-t`, и внутри выполнится проверка конфигурации `nginx -t`.
* **Обязательное условие:** Оба инструктажа **должны быть написаны в exec-формате** (в виде JSON-массива). Если хотя бы один из них записан в shell-формате, объединение не сработает (shell-формат `ENTRYPOINT` отбросит `CMD`, а shell-формат `CMD` передаст в `ENTRYPOINT` лишние аргументы `/bin/sh -c`).
* **Влияние порядка:** Порядок расположения `ENTRYPOINT` и `CMD` относительно друг друга в `Dockerfile` **не влияет** на итоговую команду (Docker всё равно объединит последнюю инструкцию `ENTRYPOINT` с последней инструкцией `CMD`), однако по стандартам оформления `ENTRYPOINT` всегда пишут перед `CMD` для логической читаемости.

**Пример из практики:**
```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
```
```bash
# Запуск со стандартными параметрами из CMD (выполнится: nginx -g "daemon off;"):
docker run -d nginx:inno-dkr-09

# Переопределение только параметров CMD (выполнится: nginx -v):
docker run --rm nginx:inno-dkr-09 -v
```

## 5. Инструкция WORKDIR в Dockerfile. Что представляет собой инструкция WORKDIR и как она используется в Dockerfile? Какая директория устанавливается в качестве текущей (рабочей) для выполнения команд внутри контейнера при использовании инструкции WORKDIR?

**Ответ:**
Инструкция `WORKDIR` задаёт текущую рабочую директорию внутри образа для всех последующих инструкций `RUN`, `CMD`, `ENTRYPOINT`, `COPY` и `ADD`, а также определяет стартовую папку при подключении к работающему контейнеру. Если указанной директории ещё не существует в файловой системе образа, Docker создаст её автоматически (включая все промежуточные родительские каталоги, аналогично `mkdir -p`).

**Какая директория устанавливается:**
* Устанавливается ровно тот путь, который передан в директиве `WORKDIR /path/to/dir` (в нашей задаче — `/etc/nginx/`).
* В одном `Dockerfile` можно использовать `WORKDIR` несколько раз подряд: если указать относительный путь (например, `WORKDIR /app`, а затем `WORKDIR src`), итоговой рабочей директорией станет `/app/src`.
* Если `WORKDIR` не указан в `Dockerfile` (и не унаследован от базового образа), рабочей директорией по умолчанию является корень файловой системы (`/`).

**Пример из практики:**
```dockerfile
WORKDIR /etc/nginx/
# Теперь относительный путь "." указывает прямо на /etc/nginx/:
COPY nginx.conf .
```
```bash
# При входе в контейнер оболочка сразу откроется в /etc/nginx/:
docker exec -it inno-nginx-09 bash
# root@container:/etc/nginx#
```
