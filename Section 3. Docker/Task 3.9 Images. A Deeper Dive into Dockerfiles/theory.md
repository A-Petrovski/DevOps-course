## Введение

В этом задании мы продолжим с тобой знакомиться с директивами Dockerfile и здесь будут более сложные кейсы, чем те, с которыми мы работали ранее. Начнем мы с команды, которая позволяет совершать практически любые действия внутри самого контейнера.

## RUN

**RUN** — выполняет команду внутри контейнера. Директива может содержать одну или несколько команд. `RUN` — команда запускается в shell. Итак, использование директивы `RUN` выглядит следующим образом:

```dockerfile
RUN command1
```

А если нужно выполнить несколько команд? Конечно же, можно написать несколько строк с отдельными директивами `RUN`, но каждая такая директива будет создавать отдельный слой (о чем мы с тобой поговорим в последующих заданиях). Поэтому несколько команд можно записать в одну директиву, используя операторы объединения команд.

```dockerfile
RUN command1 && \
    command2 && \
    command3 | command4
```

Приведенный формат позволяет вызывать несколько команд, и при провале любой из них будет провален весь этап. Провалом является код выхода, отличный от `0`, в результате команды.

* В данном случае оператор `&&` — это оператор логического И. То есть, следующая команда после `&&` выполнится, только если предыдущая выполнилась без ошибки.
* Иногда также можно обнаружить вместо `&&` использование `;`, но данный оператор не обеспечивает отлов ошибок.
* Обратный слеш `\` используется для переноса строки, а при непосредственном выполнении в оболочке она превратится в одну строку. Рекомендуется использовать для лучшей читаемости Dockerfile при большом количестве команд.

Как мы видим, операторы перенаправления ввода-вывода также разрешено использовать в рамках директивы `RUN` (`>`, `<`, `>>`, `<<`, `|`). Такая команда присутствует практически в любом образе и используется для установки зависимостей и/или сборки исходного кода в рабочий проект.

Давайте рассмотрим директивы, управляющие тем, как образ будет взаимодействовать с внешним миром, когда будет запущен в контейнере.

## VOLUME

**VOLUME** — определяет, к какому пути требуется подключить том (Volume). При запуске контейнера из образа с такой директивой, Docker автоматически создает Volume, который подключается к контейнеру. Обращение к Volume производится штатными командами `docker volume`. Данная директива должна использоваться только в том случае, если мы уверены, что выходные данные контейнера должны быть сохранены для корректной работы во внешнем хранилище.

**Формат использования:**
```dockerfile
VOLUME PATH[ ...]
```
в котором:
* `PATH` — путь внутри контейнера, к которому должен быть подключен Volume. Можно указать несколько путей.

**Пример использования:**
```dockerfile
VOLUME /mnt/ /var/log/app/
```

## EXPOSE

**EXPOSE** — информационная директива, которая регламентирует, какие порты используются внутри контейнера. Данная директива — это то, что нам показывает контейнер при `docker ps`, когда у нас нет никаких проброшенных портов. По большей части эта директива применяется для сообщения о том, какие порты используются внутри контейнера. У `docker run` есть флаг `-P`, который автоматически пробрасывает порты внутри контейнера со случайными портами на хосте, но чаще используется флаг `-p`, о котором мы с тобой знаем.

**Формат использования:**
```dockerfile
EXPOSE PORT[/PROTOCOL][ ...]
```
в котором:
* `PORT` — порт приложения,
* `PROTOCOL` — протокол (`udp`/`tcp`).

Из примера следует, что в одной директиве можно указать несколько портов.

**Пример использования:**
```dockerfile
EXPOSE 80 443/tcp 4444/udp
```

Давайте разберем команды, определяющие рабочее окружение внутри образа, в котором будет работать приложение.

## WORKDIR

**WORKDIR** — определяет, какая директория будет использоваться как рабочая внутри контейнера. Эта директива используется в том случае, если мы копируем приложение со всеми зависимостями, а не единый бинарный файл, и нам требуется вызвать другую команду для запуска приложения. Или когда приложение ожидает, что конфигурационный файл расположен в конкретной относительной директории. При подключении к контейнеру через `docker exec -ti CONTAINER_NAME sh` окружение будет забрасывать именно в эту директорию.

## CMD

**CMD** — определяет, какую команду по умолчанию требуется использовать при запуске контейнера.

Есть два формата написания данной директивы:
* **shell** — `CMD command arg` — по факту внутри запускает команду в виде `/bin/sh -c 'command arg'`;
* **exec** — `CMD ["command", "arg"]` — напрямую запускает команду `command arg` без дополнительного создания оболочки.

У данной директивы есть еще один кейс использования, и он связан с директивой `ENTRYPOINT`.

## ENTRYPOINT

**ENTRYPOINT** — определяет, что требуется запустить при запуске контейнера.

Есть два формата написания данной директивы:
* **shell** — `ENTRYPOINT command arg` — внутри запускает команду в виде `/bin/sh -c 'command arg'`.
* **exec** — `ENTRYPOINT ["command", "arg"]` — напрямую запускает команду `command arg` без дополнительного создания оболочки.

Разница между `ENTRYPOINT` и `CMD` в том, что при отсутствии `ENTRYPOINT`, `CMD` выступает как команда, которая должна запускаться по умолчанию при старте и может быть переопределена в момент запуска контейнера командой `docker run IMAGE_NAME COMMAND`. Если же директива `ENTRYPOINT` присутствует, то содержимое директивы `CMD` передается как параметр к `ENTRYPOINT`, но только при использовании exec-формата.

Для того, чтобы переопределить команду в `ENTRYPOINT`, у `docker run` используется параметр `--entrypoint`.
