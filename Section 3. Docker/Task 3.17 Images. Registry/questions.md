# Контрольные вопросы по теме: Docker Registry (Task 3.17)

## 1. Какую роль играет команда `docker login` в процессе работы с Docker Registry? Какие данные и учетные данные требуются для успешного выполнения команды?

Команда `docker login` аутентифицирует локальный Docker-клиент на сервере реестра образов и сохраняет полученные учетные данные или токен для последующих операций `docker push` и `docker pull` (для приватных репозиториев).

Для успешного выполнения команды требуются:
1. **Адрес реестра** (домен или `IP:порт`, например `quay.io` или `localhost:5000`; если не указан, используется Docker Hub).
2. **Имя пользователя** (`--username` / `-u`).
3. **Пароль или персональный токен доступа (PAT)** (`--password-stdin` или интерактивный ввод).

```bash
echo "$REGISTRY_TOKEN" | docker login registry.example.com -u ci-bot --password-stdin
```

## 2. Какие протоколы и методы аутентификации поддерживает `docker login`? Как выбрать наиболее безопасный и удобный метод аутентификации для своей среды?

Docker Registry API v2 работает поверх протоколов **HTTP/HTTPS** и поддерживает два основных метода аутентификации:
* **Basic Authentication (`htpasswd`):** Передача пары `логин:пароль` в заголовке `Authorization: Basic ...`. Подходит для простых изолированных стендов, но требует строгого использования HTTPS.
* **Bearer Token Authentication (OAuth2 / JWT):** Клиент обращается к серверу авторизации (Auth Service), обменивает учетные данные или облачный IAM-токен на временный JWT-токен с ограниченным сроком жизни и набором прав (scope) и использует его для запросов к реестру.

**Выбор метода:**
* Для **локальной разработки** — персональные токены доступа (PAT) вместо основного пароля.
* Для **CI/CD** — короткоживущие токены (OIDC / GitLab CI Job Token / GitHub Token) или сервисные аккаунты с правами только на нужный репозиторий.
* Для **продакшен-кластеров (Kubernetes)** — `imagePullSecrets` с ролевыми сервисными токенами (только права на чтение `pull`).

## 3. Как происходит процесс аутентификации и авторизации при выполнении `docker login`? Какие проверки и механизмы безопасности применяются при входе в систему Docker Registry?

1. **TLS-рукопожатие:** Клиент устанавливает зашифрованное HTTPS-соединение с реестром и проверяет валидность TLS-сертификата сервера (исключение сделано только для `localhost` / `127.0.0.0/8` и адресов из списка `insecure-registries`).
2. **Запрос к эндпоинту `/v2/`:** Клиент отправляет `GET /v2/`. Если требуется авторизация, сервер отвечает статусом `401 Unauthorized` и заголовком `Www-Authenticate`, указывающим тип авторизации (Basic или Bearer) и URL сервера аутентификации.
3. **Верификация учетных данных:** Клиент отправляет логин и пароль. Сервер проверяет их по базе пользователей (`htpasswd`, LDAP, OAuth-провайдер) и возвращает `200 OK` (или выданный JWT-токен).
4. **Сохранение сессии:** Клиент записывает данные для данного хоста в `~/.docker/config.json` (отбрасывая путь к репозиторию и тег, если был передан полный URL образа).

## 4. Какие варианты хранения учетных данных Docker Registry доступны при использовании `docker login`? Какие методы рекомендуются для безопасного хранения учетных данных?

1. **В открытом (закодированном в Base64) виде в `~/.docker/config.json`:** Поведение по умолчанию в Linux при отсутствии внешних утилит. **Небезопасно**, так как Base64 легко декодируется обратно в пароль.
2. **Системные хранилища секретов (`credsStore`):** Интеграция с менеджерами паролей ОС, где в `config.json` пишется только имя драйвера:
   * `desktop` / `osxkeychain` (macOS Keychain)
   * `wincred` (Windows Credential Manager)
   * `secretservice` / `pass` (Linux GNOME Keyring / GPG-хранилище `pass`)
3. **Хранилища для конкретных реестров (`credHelpers`):** Использование облачных хелперов (например, `ecr-login` для AWS ECR, `gcr` для Google Artifact Registry), которые динамически запрашивают временные токены через IAM.

**Рекомендация:** На рабочих машинах настраивать `credsStore` (`pass` или `secretservice`), а в CI/CD использовать временные переменные окружения и удалять конфиг через `docker logout` после завершения пайплайна.

```json
{
  "credsStore": "pass"
}
```

## 5. Какие альтернативные методы аутентификации и авторизации могут быть использованы вместо `docker login`? Какие факторы следует учитывать при выборе метода аутентификации?

* **Cloud IAM Credential Helpers (`credHelpers`):** Автоматическая генерация временных токенов на основе ролей облачной инфраструктуры (AWS IAM Roles, GCP Service Accounts, Azure Managed Identities) без ручного ввода `docker login`.
* **Mutual TLS (mTLS — клиентские сертификаты):** Аутентификация клиента на уровне TLS-соединения с помощью X.509-сертификатов, размещенных в `/etc/docker/certs.d/<registry_host>/client.cert`.
* **Кубернетес `imagePullSecrets` / Docker Swarm `--with-registry-auth`:** Передача заранее подготовленного секрета с авторизацией непосредственно оркестратору контейнеров.
* **Прокси-аутентификация (Reverse Proxy / Nginx):** Вынос проверки доступа на уровень Nginx/Traefik перед контейнером реестра.

**Факторы выбора:** Среда выполнения (локальный ПК, CI-раннер или прод-сервер), срок жизни токенов (TTL), поддержка ролевой модели (RBAC) и необходимость автоматической ротации секретов.

## 6. Как работает команда `docker push` и какую роль она играет в процессе публикации Docker-образов в Docker Registry?

`docker push` публикует локально собранный или тегированный образ в централизованный реестр, делая его доступным для развертывания на других серверах и в оркестраторах.

**Механика работы пошагово:**
1. Клиент парсит имя образа (`<registry>/<namespace>/<repo>:<tag>`), определяя адрес сервера (по умолчанию `registry-1.docker.io`).
2. Проверяет наличие сохраненных кредов в `~/.docker/config.json` для этого реестра.
3. Для каждого слоя образа (`layer digest`, SHA-256) отправляет `HEAD`-запрос в registry, чтобы проверить, существует ли уже этот слой на сервере.
4. Загружает по сети (`POST`/`PATCH`/`PUT`) **только отсутствующие слои** (дедупликация трафика и места).
5. В самом конце загружает **манифест образа** (JSON-файл со списком всех слоев и конфигурацией) и привязывает его к указанному тегу.

## 7. Какие параметры и флаги доступны для команды `docker push`? Какие дополнительные настройки можно использовать для оптимизации процесса загрузки образов?

Основные флаги команды `docker push`:
* `-a`, `--all-tags` — отправить все локальные теги, принадлежащие указанному репозиторию, одной командой.
* `-q`, `--quiet` — подавить вывод прогресс-баров по каждому слою (удобно для чистых логов в CI/CD).
* `--disable-content-trust` — отключить криптографическую подпись образов (Docker Content Trust / Notary; по умолчанию подпись отключена).

**Настройки для оптимизации загрузки:**
* **Multi-stage builds и легкие базовые образы (`alpine`, `distroless`):** Уменьшение физического объема передаваемых слоев.
* **Кэширование неизменяемых слоев:** Размещение инструкций установки зависимостей в `Dockerfile` выше инструкций копирования часто меняющегося кода, чтобы при новом `docker push` отправлялся только верхний тонкий слой приложения.
* **Параллелизм демона:** Настройка параметра `"max-concurrent-uploads"` (по умолчанию `5`) в `/etc/docker/daemon.json`.

```bash
docker push --all-tags localhost:5000/gocalc
```

## 8. Как происходит проверка доступа и правильность авторизации при выполнении команды `docker push`? Какие механизмы защиты используются для предотвращения несанкционированной загрузки образов?

1. При обращении к API реестра (`POST /v2/<repo>/blobs/uploads/`) клиент передает заголовок `Authorization` (Basic или Bearer JWT).
2. Реестр (или связанный с ним Auth-сервер) проверяет подпись токена, его срок действия и наличие области прав (**scope**) формата `repository:<name>:push,pull`.
3. Если прав недостаточно или токен невалиден, сервер возвращает `401 Unauthorized` или `403 Forbidden` (`denied: requested access to the resource is denied`).

**Механизмы защиты от несанкционированной загрузки:**
* Принудительное шифрование трафика через **TLS/HTTPS**.
* Разделение прав на чтение (`pull`) и запись (`push`) на уровне конкретных репозиториев.
* **Immutable tags (неизменяемые теги):** Запрет на перезапись уже опубликованных тегов (например, запрет перезаписывать `v1.0.0`) в корпоративных реестрах (Harbor, GitLab, Quay).
* **Подпись образов (Cosign / Notary):** Проверка криптографической подписи образа перед тем, как кластер разрешит его запуск.

## 9. Какие роли и полномочия могут быть назначены пользователям и командам при работе с Docker Registry? Как ограничить доступ и контролировать загрузку образов?

Сам базовый опенсорсный контейнер `registry:2` поддерживает только простую проверку «логин/пароль» через `htpasswd` без гранулярных ролей. Полноценная ролевая модель (**RBAC**) реализуется в корпоративных реестрах (Harbor, GitLab Container Registry, Quay, Docker Hub Organizations, Nexus):

* **Guest / Read-Only (`pull`):** Разрешено только скачивание образов. Назначается прод-серверам и Kubernetes-нодам.
* **Developer / Maintainer (`pull` + `push`):** Разрешено скачивание и публикация новых образов в рамках конкретного проекта/неймспейса. Назначается разработчикам и CI-пайплайнам.
* **Project Admin (`pull` + `push` + `delete` + управление правами):** Полный контроль над репозиторием, включая удаление тегов и настройку политик очистки (Retention policies).
* **System Admin:** Управление всем реестром, квотами хранилища, репликацией и сканированием уязвимостей (Trivy/Clair).

**Способы ограничения и контроля:**
* Изоляция репозиториев по проектам/неймспейсам (`registry.company.com/<team>/<service>`).
* Выдача токенов с минимально необходимыми правами (принцип наименьших привилегий).
* Настройка политик блокировки загрузки/запуска образов с критическими уязвимостями (CVE) и запрет перезаписи релизных тегов.
