## Подготовка окружения (ВМ, SSH и права доступа)

Для максимального приближения к реальным серверным условиям практическая часть выполняется на виртуальной машине **Ubuntu Server** (в VirtualBox), а не в графическом Docker Desktop на Windows.

### Настройка сети и SSH-доступа к ВМ
1. Внутри виртуальной машины устанавливается и запускается SSH-сервер:
   ```bash
   sudo apt update && sudo apt install -y openssh-server
   sudo systemctl enable --now ssh
   ```
   **Разбор флагов и параметров:**
   * `update` — обновляет локальный индекс доступных пакетов из репозиториев.
   * `install` — устанавливает указанный пакет (`openssh-server`).
   * `-y` — автоматически подтверждает установку без интерактивного запроса (`yes`).
   * `enable` — добавляет службу в автозагрузку при старте системы.
   * `--now` — запускает службу немедленно, не дожидаясь перезагрузки.

2. **Нюанс подключения с хоста Windows (ошибка `Connection timed out`):**
   * По умолчанию в VirtualBox используется режим сети **NAT**, при котором ВМ получает внутренний адрес `10.0.2.15`, недоступный напрямую с хост-машины.
   * **Решение 1 (Проброс портов в NAT):** В настройках ВМ (*Сеть → Адаптер 1 → Дополнительно → Проброс портов*) создаётся правило TCP: Хост `127.0.0.1:2222` → Гость `10.0.2.15:22`. Подключение с Windows выполняется командой `ssh -p 2222 amp@127.0.0.1`.
   * **Решение 2 (Сетевой мост / Bridged Adapter):** ВМ получает IP-адрес напрямую из домашней подсети (например, `192.168.1.x`), что удобнее при работе с множеством портов в Docker.

**Пример использования:**
```bash
ssh -p 2222 amp@127.0.0.1
```

## Пункт 1. Установка Docker, запись сессии, запуск и проверка контейнера Nginx

### Шаг 1.1. Установка Docker Engine (Ubuntu) и настройка прав

```bash
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://docker.com -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=\$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://docker.com \((. /etc/os-release && echo "\)VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker \$USER
newgrp docker
```

**Разбор флагов и параметров:**
* `-m 0755` — задаёт права доступа на создаваемую директорию (`rwxr-xr-x`).
* `-d` (в команде `install`) — создаёт указанную директорию и все недостающие родительские каталоги.
* `-f` (в `curl`) — тихий сбой при ошибках HTTP (не выводит HTML-страницу ошибки в файл).
* `-s` — тихий режим (скрывает прогресс-бар и статистику).
* `-S` — показывает сообщение об ошибке, даже если включен тихий режим `-s`.
* `-L` — автоматически следует за HTTP-редиректами.
* `-o` — записывает результат скачивания в указанный файл вместо вывода в терминал.
* `a+r` — выдаёт права на чтение (`read`) всем пользователям (`all`).
* `-aG` (в `usermod`) — добавляет пользователя в дополнительную группу (`-G`), сохраняя его во всех текущих группах (`-a`).

### Шаг 1.2. Запуск записи терминала и развертывание контейнера

```bash
script docker_logs.txt
docker run -d -p 127.0.0.1:28080:80 --name rbm-dkr-01 nginx:stable
docker ps
curl -I http://127.0.0.1:28080
```

**Разбор флагов и параметров:**
* `script docker_logs.txt` — начинает запись всего ввода и вывода терминальной сессии в файл `docker_logs.txt`.
* `-d` (в `docker run`) — запускает контейнер в фоновом режиме (detached mode), возвращая управление в терминал.
* `-p 127.0.0.1:28080:80` — публикует (пробрасывает) порт контейнера на хост: запросы на локальный интерфейс хоста `127.0.0.1` и порт `28080` перенаправляются на порт `80` внутри контейнера.
* `--name rbm-dkr-01` — присваивает контейнеру фиксированное понятное имя вместо случайного.
* `nginx:stable` — имя образа (`nginx`) и тег стабильной версии (`stable`), из которого создаётся контейнер.
* `docker ps` — выводит список только активных (запущенных в данный момент) контейнеров.
* `-I` (в `curl`) — запрашивает только HTTP-заголовки ответа (для быстрой проверки кода `200 OK`; без флага выводит полный HTML-код стартовой страницы Nginx).

**Пример использования:**
```bash
docker run -d -p 8080:80 --name web-test nginx:alpine
```

## Пункт 2. Остановка контейнера и проверка недоступности сервиса

```bash
docker stop rbm-dkr-01
docker ps
curl http://127.0.0.1:28080
```

**Разбор флагов и параметров:**
* `stop` — корректно останавливает запущенный контейнер (отправляет основной процесс сигнал `SIGTERM`, а через 10 секунд — `SIGKILL`, если процесс не завершился сам).
* `rbm-dkr-01` — имя целевого контейнера (также можно использовать его ID).
* `docker ps` — проверяет список активных контейнеров (после остановки список должен быть пустым).
* `curl http://127.0.0.1:28080` — выполняет GET-запрос к локальному порту; ожидаемый результат — ошибка `Failed to connect to 127.0.0.1 port 28080: Connection refused`, так как порт больше никем не прослушивается.

**Нюанс из задания:**
* Команда `docker stop` только **останавливает** контейнер, но **не удаляет** его с диска (в отличие от `docker rm`). Его файловая система и конфигурация сохраняются в системе.

**Пример использования:**
```bash
docker stop \$(docker ps -q)
```

## Пункт 3. Просмотр всех контейнеров, завершение записи и отправка логов в GitLab

### Шаг 3.1. Проверка остановленных контейнеров и завершение записи логов

```bash
docker ps -a
exit
```

**Разбор флагов и параметров:**
* `-a` (`--all`) — показывает **все** контейнеры в системе, включая остановленные (в колонке `STATUS` отобразится `Exited (0) ...`).
* `exit` (или комбинация `Ctrl + D`) — завершает дочернюю оболочку, запущенную утилитой `script`, и сохраняет буфер вывода в файл `docker_logs.txt`.

### Шаг 3.2. Настройка SSH-ключа и загрузка файла в GitLab

```bash
ssh-keygen -t ed25519 -C "linux-server-vm"
cat ~/.ssh/id_ed25519.pub
# (Копирование публичного ключа в GitLab -> Preferences -> SSH Keys)

ssh -T git@gitlab.com
git clone git@gitlab.com:devops7071547/study-docker.git
cd ~/study-docker
mv ~/docker_logs.txt .
git add docker_logs.txt
git commit -m "Add docker ps -a logs"
git push -u origin main
```

**Разбор флагов и параметров:**
* `-t ed25519` — указывает криптографический алгоритм генерации SSH-ключа (современный, быстрый и компактный).
* `-C "linux-server-vm"` — добавляет текстовый комментарий в конец публичного ключа для удобной идентификации устройства.
* `-T` (в `ssh`) — отключает выделение псевдотерминала (используется при проверке аутентификации на Git-серверах, где интерактивный shell запрещён).
* `-m` (в `git commit`) — передаёт сообщение коммита прямо в командной строке без открытия текстового редактора.
* `-u` (`--set-upstream`) — связывает локальную ветку `main` с удалённой веткой `origin/main` для последующих команд `git push` / `git pull` без аргументов.

**Разбор сложных моментов и ошибок из практики:**
1. **Сохранность старых ключей при `ssh-keygen`:** Утилита не перезаписывает существующий ключ без подтверждения (запрашивает `Overwrite (y/n)?`). Кроме того, ключи внутри ВМ полностью изолированы от хоста Windows, а в профиль GitLab можно добавить неограниченное количество ключей с разных машин.
2. **Ошибка `fatal: adding files failed` / `error: 'study-docker/' does not have a commit checked out`:**
   * **Причина:** Команда `git init` была случайно выполнена в домашней директории (`/home/amp/.git`), а затем команда `git add .` запускалась из `~`, а не из папки склонированного проекта `~/study-docker`. Git воспринял `study-docker/` как вложенный (неинициализированный) подмодуль.
   * **Решение:** Удалить лишний `.git` из домашней папки (`rm -rf ~/.git`), перейти строго в каталог репозитория (`cd ~/study-docker`) и выполнять `git add` / `git commit` / `git push` оттуда.

**Пример использования:**
```bash
git status && git add docker_logs.txt && git commit -m "Update container logs" && git push
```
