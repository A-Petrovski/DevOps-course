# Questions: Task 3.1 Basics. Знакомство с Docker

## 1. Какова роль Docker в разработке и развертывании приложений и какие проблемы он решает?

Docker решает проблему несовместимости окружений («у меня на машине всё работает»), упаковывая приложение вместе со всеми его зависимостями, библиотеками и конфигурациями в единый изолированный артефакт — **образ (image)**.

* **Единообразие сред:** Один и тот же образ одинаково запускается на ноутбуке разработчика, на тестовом стенде (QA) и на продакшн-серверах.
* **Скорость и лёгкость развертывания:** В отличие от классических виртуальных машин, контейнеры не запускают отдельную гостевую ОС с собственным ядром, а используют ядро хоста. Запуск занимает миллисекунды и требует минимум ресурсов.
* **Изоляция и отсутствие конфликтов:** На одном сервере можно одновременно запустить несколько приложений с конфликтующими версиями пакетов (например, Python 3.8 и Python 3.12).
* **Масштабирование и CI/CD:** Контейнеры легко автоматизировать в пайплайнах сборки, быстро откатывать на предыдущую версию образа и горизонтально масштабировать в оркестраторах (например, Kubernetes).

**Пример из практики (запуск изолированной тестовой БД за секунды без установки в систему):**
```bash
docker run -d --name test-postgres -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:16-alpine
```

## 2. Какие существуют проблемы и ограничения при использовании UnionFS (слоистой файловой системы)?

UnionFS (например, `overlay2`) объединяет несколько слоёв только для чтения (read-only) и верхний слой для записи (read-write) в единую файловую систему по принципу **Copy-on-Write (CoW)**. У такого подхода есть ряд ограничений:

* **Падение производительности при записи и изменении файлов (CoW overhead):** При первой попытке изменить крупный файл из нижнего слоя драйвер хранилища вынужден целиком скопировать его в верхний слой (`copy-up`) перед внесением правок. Для баз данных и высоконагруженного дискового ввода-вывода (I/O) это критично, поэтому для постоянных данных используют **Volumes**, минующие UnionFS.
* **Рост размера образа и замедление сборки при большом количестве слоёв:** Каждая инструкция `RUN`, `COPY`, `ADD` в `Dockerfile` создаёт новый слой. Множество слоёв увеличивает накладные расходы ядра на поиск файлов (lookup) и раздувает размер образа, даже если в следующем слое вы удалили временные файлы из предыдущего (данные всё равно остаются в истории нижнего слоя).
* **Проблемы совместимости и ограничения файловых систем:**
  * Некоторые старые приложения ожидают строгого соответствия стандарту POSIX (например, специфические блокировки файлов или поведение жестких ссылок hardlinks при `copy-up`), что в `overlay2` может вызывать ошибки (например, при работе `yum`/`rpm` внутри контейнера).
  * Не любая нижележащая файловая система хоста подходит для `overlay2` (например, XFS должна быть отформатирована с поддержкой `d_type=true`, иначе возможны сбои при удалении файлов внутри контейнера).
* **Эфемерность данных:** Все изменения в верхнем слое UnionFS существуют ровно до тех пор, пока существует сам контейнер. После выполнения `docker rm` все записанные туда данные безвозвратно удаляются.

**Пример из практики (проверка используемого драйвера хранилища и монтирование Volume в обход UnionFS):**
```bash
docker info | grep "Storage Driver"
docker run -d -v pg_data:/var/lib/postgresql/data --name prod-db postgres:16
```

## 3. Что такое namespaces и cgroups в Linux и как они работают в Docker?

Контейнер в Linux — это не отдельная виртуальная машина, а обычный процесс (или группа процессов) на хостовой системе, изолированный и ограниченный средствами самого ядра Linux: **namespaces** и **cgroups**.

* **Namespaces (пространства имён) — «что процесс может видеть»:**
  Обеспечивают изоляцию ресурсов на уровне видимости, создавая у процесса иллюзию, что он работает в отдельной операционной системе:
  * `pid` — изолирует дерево процессов (внутри контейнера главный процесс имеет `PID 1` и не видит процессы хоста).
  * `net` — предоставляет собственный сетевой стек (свои интерфейсы, IP-адреса, таблицы маршрутизации и порты).
  * `mnt` — изолирует точки монтирования и файловую систему (контейнер видит только свою корневую ФС).
  * `ipc` — изолирует межпроцессное взаимодействие (разделяемую память, семафоры).
  * `uts` — позволяет задать контейнеру собственное имя хоста (`hostname`) и доменное имя.
  * `user` — сопоставляет пользователей и группы внутри контейнера и на хосте (например, `root` внутри контейнера может быть обычным непривилегированным пользователем на хосте).

* **cgroups (Control Groups, контрольные группы) — «сколько ресурсов процесс может потребить»:**
  Механизм ядра, который ограничивает, учитывает и распределяет физические ресурсы хоста между группами процессов, не позволяя одному контейнеру «положить» весь сервер:
  * **CPU:** ограничение процессорного времени и количества доступных ядер.
  * **Memory (RAM):** жёсткий лимит оперативной памяти (при превышении срабатывает `OOM Killer`, завершающий процесс контейнера).
  * **Block I/O:** ограничение скорости чтения и записи на диск.
  * **PIDs:** ограничение максимального числа процессов внутри контейнера (защита от fork-бомб).

**Пример из практики (запуск контейнера с жёсткими лимитами cgroups и просмотр его namespaces на хосте):**
```bash
docker run -d --name limited-nginx --memory="256m" --cpus="0.5" nginx:alpine
sudo lsns -p \$(docker inspect --format '{{.State.Pid}}' limited-nginx)
```
