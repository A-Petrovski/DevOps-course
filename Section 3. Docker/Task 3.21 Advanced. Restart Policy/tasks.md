## 1. Запуск 4 контейнеров с разными политиками перезапуска

### Решение
```bash
for policy in no always unless-stopped on-failure; do
  sudo docker run -d --name inno-dkr-23-$policy --restart $policy nginx:stable-alpine
done
```

### Разбор параметров и флагов
- `for policy in ...; do ...; done` — цикл `for` в оболочке Bash для последовательного перебора всех четырех политик перезапуска.
- `sudo` — выполнение команды с правами суперпользователя (требуется, если текущий пользователь не добавлен в группу `docker`).
- `docker run` — создание и запуск нового контейнера из указанного образа.
- `-d` (`--detach`) — запуск контейнера в фоновом режиме с выводом его идентификатора.
- `--name inno-dkr-23-$policy` — присвоение контейнеру уникального имени по заданному шаблону.
- `--restart $policy` — установка политики перезапуска (`no`, `always`, `unless-stopped`, `on-failure`).
- `nginx:stable-alpine` — имя образа и тег для развертывания контейнера.

### Разбор ошибок и нюансов
- **Синтаксис однострочного цикла в Bash:** при написании цикла `for` в одну строку перед ключевым словом `done` обязательно ставится точка с запятой (`;`). Без нее оболочка интерпретирует `done` как аргумент команды `docker run` и переходит в режим ожидания ввода (`>`). Выход из зависшего ввода — комбинация `Ctrl + C`.
- **Правило 10 секунд:** политики перезапуска вступают в силу только после того, как контейнер успешно проработал минимум 10 секунд, поэтому перед отправкой сигналов в следующих шагах нужно выждать это время.

**Пример использования:**
```bash
docker run -d --name web-prod --restart unless-stopped -p 8080:80 nginx:stable-alpine
```

## 2. Отправка сигнала SIGTERM (15) и запись вывода в kill_15.txt

### Решение
```bash
for policy in no always unless-stopped on-failure; do
  sudo docker kill -s 15 inno-dkr-23-$policy
done

sudo docker ps -a | tee /home/user/kill_15.txt
```

### Разбор параметров и флагов
- `docker kill` — отправка системного сигнала главному процессу (`PID 1`) внутри работающего контейнера.
- `-s 15` (`--signal`) — указание конкретного сигнала для отправки (`15` соответствует `SIGTERM` — мягкому запросу на завершение работы).
- `docker ps` — вывод списка контейнеров.
- `-a` (`--all`) — отображение всех контейнеров, включая остановленные (`Exited`).
- `|` (pipe) — перенаправление стандартного вывода (`stdout`) первой команды на стандартный ввод (`stdin`) следующей.
- `tee /home/user/kill_15.txt` — утилита, которая одновременно выводит полученные данные на экран терминала и записывает их в указанный файл.

### Разбор ошибок и нюансов
- **Поведение Nginx при получении `SIGTERM`:** Nginx корректно обрабатывает сигнал `15`, штатно завершает рабочие процессы и выходит с кодом `0` (`Exited (0)`).
- **Реакция политик:** поскольку код возврата равен `0` (штатное завершение без ошибок), политика `on-failure` не перезапускает контейнер. В статусе `Up` остается только `always`, а `no`, `unless-stopped` и `on-failure` переходят в `Exited (0)`.

**Пример использования:**
```bash
docker kill -s SIGHUP nginx-proxy
```

## 3. Запуск неактивных контейнеров и проверка списка

### Решение
```bash
sudo docker start inno-dkr-23-no inno-dkr-23-unless-stopped inno-dkr-23-on-failure
sudo docker ps -a
```

### Разбор параметров и флагов
- `docker start` — запуск одного или нескольких ранее остановленных контейнеров без пересоздания.
- `docker ps -a` — проверка статуса всех контейнеров (убеждаемся, что все 4 контейнера перешли в состояние `Up`).

### Разбор ошибок и нюансов
- **Счетчик перезапусков (`RestartCount`):** ручной запуск через `docker start` не увеличивает счетчик автоматических перезапусков в метаданных контейнера (`docker inspect`), но обновляет целевое состояние контейнера для демона Docker (теперь демон снова считает их запущенными).

**Пример использования:**
```bash
docker start $(docker ps -aq -f status=exited)
```

## 4. Отправка сигнала SIGKILL (по умолчанию) и запись вывода в kill.txt

### Решение
```bash
for policy in no always unless-stopped on-failure; do
  sudo docker kill inno-dkr-23-$policy
done

sudo docker ps -a | tee /home/user/kill.txt
```

### Разбор параметров и флагов
- `docker kill <имя>` — вызов команды без флага `-s` по умолчанию отправляет сигнал `9` (`SIGKILL`), который обрабатывается напрямую ядром ОС и немедленно завершает процесс.
- `| tee /home/user/kill.txt` — дублирование актуального состояния контейнеров в консоль и файл `/home/user/kill.txt`.

### Разбор ошибок и нюансов
- **Код возврата `137`:** принудительное завершение через `SIGKILL` приводит к выходу с кодом `137` (\(128 + 9\)), что интерпретируется Docker как аварийный сбой.
- **Изменение реакции `on-failure`:** в отличие от шага с `SIGTERM`, теперь в статусе `Up` остаются **два** контейнера: `always` и `on-failure` (так как код возврата отличен от нуля). Контейнеры `no` и `unless-stopped` остаются в статусе `Exited (137)`.

**Пример использования:**
```bash
docker kill --signal=SIGKILL hung-container
```

## 5. Перезапуск демона Docker и финальная проверка

### Решение
```bash
sudo systemctl restart docker
sudo docker ps -a
```

### Разбор параметров и флагов
- `systemctl` — утилита управления системными службами и менеджером инициализации `systemd` в Linux.
- `restart` — команда полной перезагрузки указанного юнита (службы).
- `docker` — имя системной службы демона Docker (`docker.service`).
- `docker ps -a` — итоговый аудит состояния контейнеров после рестарта демона.

### Разбор ошибок и нюансов
- **Разница между `always` и `unless-stopped` после рестарта демона:** в рамках данного сценария после `systemctl restart docker` в статусе `Up` окажутся `always`, `unless-stopped` и `on-failure` (так как они не были остановлены штатной командой `docker stop`, а были либо запущены, либо убиты аварийно). Если бы перед перезапуском демона контейнеры `always` и `unless-stopped` были остановлены через `docker stop`, то после рестарта службы поднялся бы **только** `always`.

**Пример использования:**
```bash
sudo systemctl status docker --no-pager
```
