# Вопросы для самоконтроля: Restart Policy в Docker

### 1. Какие основные типы политик перезапуска существуют в Docker и чем они отличаются?
В Docker есть 4 политики перезапуска, задаваемые через флаг `--restart`:
- **`no`** (по умолчанию) — контейнер не перезапускается автоматически ни при каких обстоятельствах.
- **`on-failure[:max-retries]`** — контейнер перезапускается только при завершении главного процесса с ненулевым кодом возврата (ошибкой). Опционально можно ограничить число попыток перезапуска.
- **`always`** — контейнер перезапускается всегда, независимо от кода возврата. Если он был остановлен вручную (`docker stop`), он не запустится сразу, но обязательно поднимется после перезапуска демона Docker или хоста.
- **`unless-stopped`** — работает аналогично `always`, но если контейнер был остановлен вручную (или иным явным образом), он **не** будет запущен автоматически даже после рестарта демона Docker или сервера.

```bash
docker update --restart unless-stopped my-container
```

### 2. Как ведут себя контейнеры с разными политиками при отправке `SIGTERM` (сигнал 15) и `SIGKILL` (сигнал 9)?
- **При `SIGTERM` (`docker kill -s 15`):** корректно написанные приложения (например, Nginx) перехватывают сигнал, завершают работу штатно и возвращают код `0` (`Exited (0)`). В результате перезапускается **только** контейнер с политикой `always`. Контейнер с `on-failure` остается выключенным, так как ошибки не произошло.
- **При `SIGKILL` (`docker kill` без флагов):** ядро Linux принудительно уничтожает процесс, и контейнер завершается с кодом ошибки `137` (\(128 + 9\)). Демон Docker фиксирует сбой (ненулевой код выхода), поэтому автоматически перезапускаются контейнеры с политиками **`always`** и **`on-failure`**.

```bash
# Проверка кода выхода и количества автоматических перезапусков контейнера
docker inspect -f 'ExitCode: {{.State.ExitCode}} | RestartCount: {{.RestartCount}}' inno-dkr-23-on-failure
```

### 3. В чем практическая разница между `always` и `unless-stopped` при перезапуске демона Docker или хоста?
Разница проявляется только в том случае, если контейнер был предварительно остановлен вручную командой `docker stop`:
- Контейнер с политикой **`always`** после выполнения `systemctl restart docker` или перезагрузки сервера **будет запущен автоматически**.
- Контейнер с политикой **`unless-stopped`** запомнит состояние ручной остановки и после перезапуска демона/сервера **останется в статусе `Exited`**.

```bash
# Остановка обоих контейнеров и проверка поведения после рестарта демона
docker stop inno-dkr-23-always inno-dkr-23-unless-stopped
sudo systemctl restart docker
docker ps -a
```

### 4. Почему Docker не перезапускает упавший контейнер мгновенно после запуска и как изменить политику без пересоздания контейнера?
- **Задержка 10 секунд:** политика перезапуска активируется только после того, как контейнер непрерывно проработал минимум **10 секунд**. Это защищает хост от бесконечного цикла перезапусков (crash loop) при критических ошибках конфигурации или отсутствующих зависимостях.
- **Изменение на лету:** в отличие от переменных окружения или проброса портов, политику перезапуска можно обновить у уже существующего контейнера без его удаления и пересоздания с помощью `docker update` (на Linux-хостах).

```bash
docker update --restart on-failure:5 my-app
```
