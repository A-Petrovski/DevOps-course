# Вопросы для самоконтроля: Task 3.19 Images. Dockerignore

### 1. Цель и назначение `.dockerignore`. Почему важно определить, какие файлы и директории должны быть исключены из контекста сборки Docker-образа?

**Ответ:**
Файл `.dockerignore` служит для фильтрации файлов и директорий в рабочей папке проекта **до** того, как клиент Docker упакует их в архив (контекст сборки) и передаст демону Docker.

Определять список исключений критически важно по трем причинам:
1. **Безопасность:** предотвращает случайное попадание в образ конфиденциальных данных (файлов `.env`, приватных SSH-ключей, токенов, локальных конфигов с паролями) при использовании общих инструкций вроде `COPY . .`.
2. **Чистота и минимальный размер образа:** отсекает артефакты разработки, которые не нужны для работы приложения в продакшене (историю `.git`, логи, тесты, локальные зависимости, документацию).
3. **Предсказуемость сборки:** исключает локальные конфигурационные файлы разработчика, которые могут конфликтовать с настройками окружения внутри контейнера.

**Пример из практики:**
Исключение чувствительных данных и служебных директорий в `.dockerignore`:
```text
.git
.env*
*.pem
*.key
logs/
```

### 2. Влияние `.dockerignore` на производительность сборки: как использование `.dockerignore` может повлиять на производительность процесса сборки Docker-образа? Как исключение ненужных файлов и директорий может ускорить время сборки и уменьшить размер финального образа?

**Ответ:**
Использование `.dockerignore` напрямую ускоряет сборку и уменьшает итоговый вес образа за счет трех механизмов:
1. **Сокращение времени передачи контекста (Transferring context):** Перед выполнением первой инструкции `Dockerfile` Docker архивирует весь контекст и отправляет его демону. Если в папке лежат тяжелые директории (например, `node_modules`, `.git` или медиафайлы на сотни мегабайт), эта передача занимает значительное время при каждом запуске `docker build`. Исключение этих папок сокращает передачу данных до долей секунды.
2. **Защита кэша слоев (Layer Caching):** Docker вычисляет контрольную сумму (хэш) файлов для инструкции `COPY . .`. Если в директории изменился любой неигнорируемый файл (например, дописался лог или обновился файл в `.git`), хэш слоя меняется, кэш сбрасывается (инвалидируется), и Docker заново выполняет все последующие шаги сборки (установку зависимостей, компиляцию). `.dockerignore` изолирует кэш от таких изменений.
3. **Уменьшение размера финального образа:** Файлы, отсеченные на этапе формирования контекста, физически не могут попасть в слои образа при выполнении `COPY`, что уменьшает вес образа на диске и ускоряет его загрузку (`docker push` / `docker pull`) в реестр.

**Пример из практики:**
Проверка объема передаваемого контекста в логах сборки:
```bash
docker build --progress=plain --no-cache -t my-app:test .
# В логах отобразится строка:
# #4 [internal] load build context
# #4 transferring context: 1.42MB done (вместо 150MB+ без .dockerignore)
```
