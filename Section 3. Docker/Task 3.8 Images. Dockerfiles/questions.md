# Контрольные вопросы: Task 3.8 Images. Dockerfiles

## 1. Структура Dockerfile. Какая типичная структура имеет Dockerfile? Какие инструкции обычно включаются в Dockerfile для настройки и создания контейнера?

Типичный `Dockerfile` строится сверху вниз по принципу слоёв — от базовой операционной системы или среды выполнения к конкретному коду приложения и параметрам его запуска. Инструкции принято располагать от наиболее редко изменяемых к наиболее часто изменяемым для эффективного кэширования слоёв.

**Стандартная последовательность инструкций:**
1. `FROM` — выбор базового образа (всегда первая инструкция, за исключением `ARG`).
2. `LABEL` / `ARG` / `ENV` — метаданные, аргументы сборки и переменные окружения.
3. `RUN` — установка системных пакетов, зависимостей и компиляция.
4. `WORKDIR` — установка рабочей директории внутри образа.
5. `COPY` / `ADD` — перенос конфигураций и исходного кода приложения в образ.
6. `USER` — переключение на непривилегированного пользователя для безопасности.
7. `EXPOSE` — документация сетевых портов, которые слушает приложение.
8. `ENTRYPOINT` / `CMD` — определение процесса, запускаемого при старте контейнера.

**Пример типового Dockerfile для веб-приложения:**
```dockerfile
FROM python:3.11-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER nobody
EXPOSE 8000
CMD ["python", "app.py"]
```

## 2. Команды и инструкции в Dockerfile. Какие команды и инструкции можно использовать в Dockerfile? Какие основные команды, такие как FROM, RUN, COPY и CMD, имеются в Dockerfile и для чего они используются?

Инструкции в `Dockerfile` делятся на две категории: выполняемые **на этапе сборки образа** (создают новые слои файловой системы) и определяющие **поведение при запуске контейнера**.

**Основные инструкции:**
- `FROM` — задаёт базовый образ, поверх которого будут накладываться последующие изменения.
- `RUN` — выполняет shell-команды внутри контейнера *во время сборки образа* и фиксирует результат в новом слое (установка ПО, создание папок, правка прав).
- `COPY` — копирует файлы и директории из локального контекста сборки на хосте в файловую систему образа.
- `ADD` — аналог `COPY`, но с поддержкой автоматической распаковки локальных `.tar`-архивов и скачивания файлов по URL (не рекомендуется без прямой необходимости).
- `WORKDIR` — задаёт текущую рабочую директорию для всех последующих инструкций `RUN`, `CMD`, `ENTRYPOINT`, `COPY` и `ADD`.
- `ENV` — устанавливает постоянные переменные окружения, доступные как во время сборки, так и внутри запущенного контейнера.
- `CMD` — задаёт команду и аргументы по умолчанию, которые выполняются *при старте контейнера* (может быть легко переопределена аргументами в `docker run`).
- `ENTRYPOINT` — задаёт основной исполняемый процесс контейнера, который не перезаписывается обычными аргументами `docker run` (они передаются ему как параметры).

**Пример разницы между `RUN` (этап сборки) и `CMD` (этап запуска):**
```dockerfile
FROM ubuntu:22.04
# Выполнится один раз при docker build:
RUN apt-get update && apt-get install -y curl
# Выполнится каждый раз при docker run:
CMD ["curl", "--version"]
```

## 3. Управление зависимостями и пакетами в Dockerfile. Как можно управлять зависимостями и устанавливать пакеты в Dockerfile? Какие инструкции, такие как ADD, COPY и RUN, могут использоваться для работы с файлами и установки программных компонентов?

Управление зависимостями в `Dockerfile` строится на связке переноса манифестов зависимостей (`COPY`) и запуска пакетных менеджеров (`RUN`) с обязательной очисткой кэша для минимизации размера итогового образа.

**Основные правила работы с пакетами и файлами:**
- **Системные пакеты:** устанавливаются через `RUN` с помощью пакетного менеджера базового образа (`apt-get` для Debian/Ubuntu, `apk` для Alpine). Обновление индексов и установка пакетов объединяются в одну инструкцию `RUN` через `&&`, чтобы избежать проблем с устаревшим кэшем слоёв, а временные файлы удаляются в той же команде.
- **Зависимости приложения:** сначала через `COPY` переносятся только файлы описания зависимостей (`requirements.txt`, `package.json`, `go.mod`), затем через `RUN` устанавливаются библиотеки, и только после этого через `COPY` копируется остальной исходный код. Это позволяет Docker кэшировать слой с зависимостями и не перекачивать их при каждом изменении кода.
- **Локальные архивы и бинарники:** готовые скомпилированные бинарные файлы переносятся через `COPY`, а локальные `.tar.gz`-архивы при необходимости автоматического извлечения — через `ADD`.

**Практический пример установки системного пакета и зависимостей приложения:**
```dockerfile
FROM node:20-alpine
WORKDIR /usr/src/app

# 1. Установка системного пакета и очистка кэша в одном слое
RUN apk add --no-cache curl

# 2. Копирование только файлов зависимостей для эффективного кэширования
COPY package.json package-lock.json ./
RUN npm ci --only=production

# 3. Копирование исходного кода проекта
COPY . .

CMD ["node", "server.js"]
```
