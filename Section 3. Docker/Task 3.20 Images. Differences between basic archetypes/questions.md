# Вопросы для самоконтроля: Task 3.20 — Базовые образы Docker

## 1. В чем заключаются основные различия между образами Alpine, Slim, Stretch, Buster, Jessie и Bullseye?

* **Jessie, Stretch, Buster, Bullseye** — это кодовые имена релизов дистрибутива **Debian** в хронологическом порядке:
  * `Jessie` — Debian 8 (устарел, в архиве).
  * `Stretch` — Debian 9 (устарел, в архиве).
  * `Buster` — Debian 10 (устарел, переведен в LTS/архив).
  * `Bullseye` — Debian 11 (стабильный релиз с длительной поддержкой).
  * Все стандартные образы Debian используют стандартную библиотеку языка Си (**`glibc`**), пакетный менеджер `apt` и полный набор утилит GNU, из-за чего весят ~110–125 МБ в базе.
* **Slim (например, `debian:buster-slim`)** — это урезанная версия стандартного образа Debian, из которой удалены документация (`man`-страницы), локали и некритичные утилиты. Сохраняет полную совместимость с **`glibc`**, но весит почти вдвое меньше (~69 МБ).
* **Alpine** — минималистичный дистрибутив Linux (~5.5 МБ в базе), построенный на базе легковесной библиотеки **`musl libc`** и набора утилит **BusyBox** с пакетным менеджером `apk`.

**Сценарии использования:**
* **Alpine** — для большинства микросервисов (Go, Java, Node.js, Nginx), где критичен минимальный размер образа и быстрая доставка по сети.
* **Slim** — оптимальный компромисс для приложений (особенно на Python или C/C++), которым нужна стандартная `glibc`, но не нужен лишний вес полного Debian.
* **Стандартные Debian/Ubuntu** — для отладки, разработки или сложных приложений с большим количеством системных зависимостей.

**Пример проверки версии ОС внутри контейнера:**
```bash
docker run --rm debian:bullseye-slim cat /etc/os-release
docker run --rm alpine:latest cat /etc/os-release
```

## 2. Каковы преимущества и недостатки использования компактных образов (Alpine и Slim)?

**Преимущества:**
1. **Минимальный размер:** Быстрее скачиваются из Registry (`docker pull`), быстрее разворачиваются на нодах Kubernetes и занимают меньше места на диске.
2. **Повышенная безопасность (меньшая поверхность атаки):** В образе отсутствуют лишние системные утилиты (компиляторы, сетевые сканеры, шеллы), которыми мог бы воспользоваться злоумышленник при взломе приложения.
3. **Меньше уязвимостей (CVE):** Чем меньше пакетов установлено в базовом образе, тем реже сканеры безопасности (Trivy, Clair) находят в них известные уязвимости.

**Недостатки и ограничения:**
1. **Несовместимость `musl` и `glibc` (в Alpine):** Скомпилированные бинарные пакеты (например, Python-библиотеки `numpy`, `pandas`, `psycopg2` или Go-программы с включенным `CGO`), собранные под `glibc`, могут падать с ошибками линковки в Alpine.
2. **Долгая сборка:** Из-за отсутствия готовых бинарных пакетов под `musl` пакетным менеджерам (например, `pip`) приходится компилировать зависимости из исходного кода на C/C++, что требует установки `gcc`/`build-base` и сильно замедляет `docker build`.
3. **Сложность отладки:** В `Slim` и `Alpine` отсутствуют привычные диагностические утилиты (`curl`, `ping`, `netstat`, `vim`, `bash`), их приходится доставлять вручную при расследовании инцидентов.

**Пример проверки используемой библиотеки C в образе:**
```bash
docker run --rm alpine ldd --version
```

## 3. Почему при удалении файлов в отдельной инструкции `RUN` размер Docker-образа не уменьшается?

Файловая система Docker (`OverlayFS`) работает по принципу **Copy-on-Write** и состоит из неизменяемых слоев (*read-only*). 

Когда файл создается в одном слое `RUN`, он навсегда записывается в этот слой. Если удалить его в следующей инструкции `RUN`, Docker не стирает данные из нижнего слоя — вместо этого в новом верхнем слое создается специальный служебный файл-заглушка (*whiteout file*), который просто скрывает удаленный файл при объединении слоев. 

Чтобы физически освободить место, создание, использование и удаление временных файлов (архивов, кэша пакетов, инструментов сборки) должны происходить **внутри одной транзакции (одной инструкции `RUN`)** через `&&` до момента фиксации слоя.

**Пример правильной очистки в одном слое:**
```dockerfile
RUN apt-get update && apt-get install -y curl \
    && curl -fsSL https://example.com -o /tmp/archive.tar.gz \
    && tar -xzf /tmp/archive.tar.gz -C /opt \
    && rm -rf /tmp/archive.tar.gz /var/lib/apt/lists/*
```

## 4. В чем разница между базовыми образами `BusyBox` и `Scratch`?

* **`BusyBox`** (~1.2 МБ) — содержит минимальный набор базовых UNIX-утилит (`sh`, `ls`, `cp`, `ping`, `wget` и др.), упакованных в один исполняемый файл. Не имеет пакетного менеджера. Идеально подходит для легких debug-контейнеров или скриптов.
* **`Scratch`** (`0 B`) — абсолютно пустой зарезервированный образ без файловой системы, библиотек и оболочки (`sh`). Его невозможно скачать через `docker pull scratch`. Используется только для статически скомпилированных бинарных файлов (например, на Go, Rust или C++), которым для запуска не требуется ничего, кроме ядра Linux.

**Пример запуска debug-контейнера на базе BusyBox:**
```bash
docker run --rm -it busybox:latest sh
```
