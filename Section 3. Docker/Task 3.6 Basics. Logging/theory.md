## Введение

В рамках одного из заданий мы забирали логи nginx в отдельные файлы в директорию, которая находилась на хосте, но это далеко не единственный и, конечно же, не родной механизм сбора логов в Docker. Как и с другими командами по работе с контейнерами, для работы с логами есть отдельная команда, которая, как можно угадать, называется `logs`.

---

## Команда `docker logs` и её флаги

`docker logs` — позволяет вывести логи контейнера в консоль. Как и с другими командами, у команды `logs` есть свои флаги, которые позволяют решать разные задачи:

* `-f` — подключается к логам и выводит их по мере поступления. Аналогично использованию `tail -f` по файлу в своей консоли;
* `--tail N` — выводит последние `N` строк лога (без параметра выводит все, а не 10, как с консольным `tail`);
* `--since DATE` — позволяет вывести логи, начиная с определенной даты (пример — `2019-09-10`) или с дельты (пример — `1h`, то есть начиная с часа назад);
* `-t|--timestamps` — позволяет вместе с логами выводить timestamp — временную метку, показывающую, когда эти логи были получены.

Для получения списка всех флагов можно ввести команду `docker logs --help`.

## Механизм сборки логов в Docker

Интересен механизм сборки логов — вывод в стандартные потоки (`stdout`, `stderr`) принимает Docker и сохраняет эти логи. То есть все, что выводит приложение в консоль при ручном запуске, автоматически попадает в логи.

Существуют еще более интересные кейсы по работе с логами. Поскольку контейнер под капотом запускает Linux, то можно немного схитрить при выводе логов в Docker Logs: если приложение не умеет само писать логи в `stdout`, то можно предложить ему вместо файла логов ссылки на файлы `/dev/stdout` или `/dev/stderr`, которые работают как устройства вывода процесса.

Образ `nginx` работает именно так. Чтобы убедиться в этом, выполните следующую команду:

```bash
docker run --rm -ti nginx:stable ls -al /var/log/nginx
```

А для того, чтобы посмотреть, как эти логи отображаются в логах докера, — запусти `nginx` и увидишь в логах стандартный лог по запросу.

## Хранение логов и драйверы логирования

В хостовой системе логи хранятся в директории контейнера — в `/var/lib/docker/containers/$CONTAINER_ID/$CONTAINER_ID-json.log`. Обратите внимание, что в файле лог хранится в JSON формате с сохранением лога и времени (что позволяет использовать флаг `-t` при вызове `logs`).

На самом деле, Docker умеет писать логи не только в JSON, но и в другие форматы при помощи разных драйверов с разными параметрами. Вот некоторые из них:

* `json-file` — дефолтный драйвер, параметры позволяют описать параметры ротации логов;
* `syslog` — позволяет писать в syslog хоста либо в удаленный syslog сервер;
* `gcplogs` — позволяет писать в Google Cloud Logging (он же StackDriver Logs). Это актуально, если вы живете в реалиях Google Cloud Platform.

Официальный список драйверов можно узнать в документации Docker, но этим все не ограничивается: Docker еще позволяет устанавливать плагины, расширяющие возможности, мы поговорим об этом позже.

## Настройка логирования на уровне контейнера и хоста

Для того, чтобы изменить метод логирования для конкретного контейнера, необходимо передать параметры `--log-driver` и `--log-opt` при запуске контейнера через `run`, где в первом указывается требуемый драйвер, а во втором — параметры драйвера (если они есть). Так, для запуска контейнера с логированием в `syslog` команда будет выглядеть следующим образом:

```bash
docker run --rm --log-driver syslog --log-opt syslog-address=unix:///tmp/syslog.sock nginx:stable
```

Если же требуется настроить другой драйвер, отличный от `json-file`, по умолчанию для всего хоста либо поменять параметры работы драйвера (добавить опций логирования), то можно описать требуемые параметры в файле `/etc/docker/daemon.json` либо передать эти параметры при запуске демона Docker.

## Режимы вывода логов

По умолчанию вывод логов производится в блокирующем режиме. При большом количестве запросов можно столкнуться с проблемой в работе приложения из-за того, что логи не успевают закидываться в устройства вывода. Этот момент частично устранили, позволив выводить логи в неблокирующем режиме, передав параметр вывода `--log-opt mode=non-blocking`.

Существует еще много интересных фактов о логировании, которые значительно облегчат жизнь и которые необходимо знать. Многие из них находятся в «Полезных ссылках». Некоторые актуальны, другие не очень — из-за обновлений (например, dual logging появился в 18.03.1). Но это прекрасная теоретическая база. Скоро мы рассмотрим наиболее интересные методы сбора логов, которые будут актуальны в инсталляциях более одного хоста.
