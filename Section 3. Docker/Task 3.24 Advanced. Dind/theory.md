## Введение

Docker in Docker. Казалось бы, зачем такая конструкция вообще может потребоваться? На самом деле, самый главный кейс — это сборка образов в среде, ограниченной от всего. Да, можно собирать образы на сервере с Linux. Но это потенциально может привести к проблемам с безопасностью (например утечки данных), поскольку файловая система делится еще и с другими приложениями. И это опасно, как владельцу сервера (скажем, доступ к файлам другого проекта), так и тому, кто вообще собирает проект (секретные данные, приватный код).

Если же собирать образ внутри другого контейнера, мы можем получить окружение, которое перед началом работы содержит необходимые инструменты, никаких секретных данных, а главное после своей работы может быть уничтожено, освободив необходимые на хосте ресурсы, не оставляя за собой никакого мусора.

Данный подход используется практически в каждой современной CI/CD — GitLab CI (хотя и не ограничивается), Circle CI, Travis CI и др.

Связано это с несколькими возможностями:
- возможность запуска повторяющегося рабочего окружения;
- контейнер представляет собой песочницу, отделенную от мастера;
- позволяет, как правило, запустить требуемые сервисы в считанные секунды рядом с основным контейнером сборки.

## Реализации Docker in Docker

Существует 2 реализации Docker in Docker:
1. **Историческая и чистая** — образ `docker:dind`.
2. **Безопасная (или не очень)** — запуск контейнера Docker внутри Docker с пробросом сокета с хоста.

### Историческая (docker:dind)

```bash
docker run --privileged -d docker:dind
```

Данный метод был предложен, реализован и, в целом, широко использовался. Однако, как видно, самая большая его проблема состоит в том, что мы, по факту, нашему контейнеру даем права на все — все устройства, все сетевые чудеса. Многовато. Однако данный метод все еще широко используется во многих местах.

### Безопасная (проброс сокета)

```bash
docker run -v /var/run/docker.sock:/var/run/docker.sock docker
```

Как видно, данный метод позволяет нам запустить Docker в защищенном окружении, но при этом мы реально имеем Docker, который позволяет взаимодействовать с Docker API без проброса доступа к тем же дисковым устройствам. Этот вариант более безопасный.

Но интересно то, что оба подхода были предложены одним и тем же человеком и, в общем-то, ровно также используются много где, благодаря удобству взаимодействия. Просто в некоторых случаях удобнее обращаться к Docker в виде рядом стоящего сервиса, а в других — выдавая команды напрямую.

## Чекпоинты

1. Запусти Docker в Docker, используя первый метод (`dind`).
2. Подключись к контейнеру c Docker и выполни внутри него следующие действия:
   - Получи список текущих образов и всех контейнеров;
   - Скачай образ `redis:5`;
   - Создай из загруженного образа контейнер с именем `inno-dkr-26`, работающий в фоне;
   - Еще раз выведи список всех контейнеров;
   - Удали контейнер;
   - Еще раз выведи список всех контейнеров.
3. Запусти Docker в Docker, используя второй метод (проброс сокета). Повторите те же самые действия из предыдущего пункта.

## Темы на изучение

- **Цели использования Docker DIND:** Например, это может быть полезно для разработки и тестирования приложений, когда вам нужно создавать и управлять контейнерами в изолированной среде.
- **Как работает Docker DIND:** Внутреннее устройство Docker DIND и механизмы, которые позволяют ему работать внутри контейнера. Как взаимодействует внутренний демон Docker с внешним демоном Docker на хостовой системе.
- **Альтернативы Docker DIND:** Альтернативные подходы к работе с Docker, которые могут быть применимы вместо Docker DIND.
