# Контрольные вопросы для самопроверки: Task 3.24 Docker-in-Docker

## 1. Цели использования Docker DinD

**Вопрос:** Для каких задач и почему на практике применяют подход Docker-in-Docker?

**Ответ:**
Главный сценарий использования — **изолированная сборка образов и запуск интеграционных тестов в CI/CD-пайплайнах** (GitLab CI, GitHub Actions, Jenkins). Контейнер выступает как чистая одноразовая «песочница»: он содержит только нужные для сборки утилиты, не имеет доступа к секретам и файлам других проектов на хосте, позволяет быстро поднимать вспомогательные сервисы (БД, брокеры сообщений) рядом со сборкой и бесследно удаляется после завершения задачи.

**Пример из практики (фрагмент `.gitlab-ci.yml`):**
```yaml
build-image:
  image: docker:24.0.5
  services:
    - docker:24.0.5-dind
  script:
    - docker build -t my-registry.example.com/app:latest .
    - docker push my-registry.example.com/app:latest
```

## 2. Как работает Docker DinD (внутреннее устройство и взаимодействие с хостом)

**Вопрос:** Как устроен Docker DinD изнутри и как взаимодействуют внутренний и внешний демоны Docker?

**Ответ:**
В классическом DinD (`docker:dind`) внутренний и внешний демоны **никак не взаимодействуют** — это два абсолютно независимых процесса `dockerd` с собственными пространствами имен (`namespaces`), контрольными группами (`cgroups`) и изолированными хранилищами (`/var/lib/docker`). Чтобы внутренний демон мог создавать дочерние контейнеры и монтировать файловые системы (`overlay2` поверх `overlay2`), контейнеру передается флаг `--privileged`, снимающий ограничения ядра Linux.

При подходе **Docker-out-of-Docker (DooD)** второй демон вообще не запускается: внутри контейнера работает только клиент (`docker` CLI), который через примонтированный сокет `/var/run/docker.sock` общается напрямую с родительским демоном хоста, создавая контейнеры как «соседей» (siblings) на одном уровне.

**Пример проверки изоляции процессов и хранилищ:**
```bash
# На хосте виден только один родительский DinD-контейнер
docker ps --format "{{.Names}} -> {{.Image}}"

# Внутри DinD запущен свой независимый демон dockerd (PID 1 или дочерний от entrypoint)
docker exec dind-test ps aux | grep dockerd
```

## 3. Альтернативы Docker DinD

**Вопрос:** Какие существуют безопасные и современные альтернативы классическому Docker DinD для сборки образов в контейнерах?

**Ответ:**
Поскольку `--privileged` создает критические риски безопасности (побег из контейнера на хост), а наложение файловых систем снижает производительность, в современном DevOps применяют инструменты **без демона (daemonless) и без root-прав (rootless)**:
1. **Kaniko (Google)** — собирает образы из `Dockerfile` полностью в пространстве пользователя (userspace) внутри контейнера/пода Kubernetes без доступа к Docker-демону и без флага `--privileged`.
2. **Buildah (Red Hat)** — утилита для сборки OCI-образов без фонового демона с поддержкой rootless-режима.
3. **BuildKit (Rootless mode)** — современный движок сборки от Docker, способный работать в изолированном непривилегированном контейнере (`moby/buildkit:rootless`).
4. **Podman** — демон-независимый контейнерный движок с CLI, совместимым с Docker, штатно поддерживающий запуск от обычного пользователя.

**Пример сборки образа без демона и привилегий с помощью Kaniko:**
```bash
docker run --rm \
  -v $(pwd):/workspace \
  gcr.io/kaniko-project/executor:latest \
  --context=/workspace \
  --dockerfile=/workspace/Dockerfile \
  --no-push
```
