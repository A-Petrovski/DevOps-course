## Введение

Capabilities позволяют выдавать конкретному контейнеру определенные возможности по взаимодействию с хостовой системой, делая грань между хостовой и гостевой системой очень тонкой. Казалось бы, чистой воды дыра в безопасности, однако некоторым приложениям могут требоваться эти параметры для нормального функционирования.

На самом деле Docker Capabilities напрямую связаны с Linux Capabilities (помните, мы говорили, что Docker использует фичи Linux? Оттуда ноги и растут), но замаплены в ограниченный список.

Итак, зачем вообще нужны Capabilities? В основном для того, чтобы запускать приложения, которые не могут работать без определенных возможностей по работе с ядром. К примеру, если приложению требуется возможность конфигурировать время или менять параметры файлов, то ему на это требуется выдавать права. Если прав нет, то в лучшем случае ты получишь ошибку, в худшем — твое приложение не запустится совсем.

## Управление Capabilities в Docker

Настройка списка возможностей конкретного контейнера определяется двумя опциями, передаваемыми при запуске контейнера: `--cap-add` и `--cap-drop`, где одна команда добавляет, а вторая — убирает возможности соответственно.

Так, если нам требуется дать доступ для использования команды `ptrace` (отладочный инструмент, используемый в ряде программ), то команда запуска будет выглядеть следующим образом:

```bash
docker run --cap-add SYS_PTRACE -d nginx:stable
```

Если же нужно убрать возможность, к примеру, менять параметры владения файлами, то команда запуска будет иметь следующий вид:

```bash
docker run --cap-drop CHOWN -d nginx:stable
```

Часть возможностей выставляется контейнеру по умолчанию, поэтому он и способен работать корректно. Но если есть необходимость, то можно и отобрать все возможности.

Кроме того, можно добавить или удалить все возможности разом при помощи `ALL`. Так, к примеру, если нам нужно как раз убрать все возможности, но оставить возможность менять параметры файлов, то запуск будет выглядеть следующим образом:

```bash
docker run --cap-drop ALL --cap-add CHOWN -d nginx:stable
```

Важно отметить, что `--cap-(drop|add)` может быть использован по нескольку раз за один вызов.

Полный список возможностей мы приводить в этом блоке не будем, поскольку они хорошо описаны в основной документации, да и, как правило, ручное управление возможностями контейнеров приходится делать крайне редко.

## Privileged режим

Пожалуй, на этом можно было бы и закончить тему, но давай дополним ее парой блоков по вопросам безопасности в контейнерах и образах. Рассмотрим другие параметры безопасности — `privileged` режим, параметр `devices` и директива `USER` в Dockerfile.

`privileged` режим контейнера позволяет дать доступ ко всем устройствам (сетевым, дисковым и т.д.) хостовой системы, а также делать все что угодно с сетевыми настройками хоста (на самом деле, возможности по работе с сетями можно добиться и через Capabilities). Вообще это довольно опасная штука с точки зрения безопасности и нужно несколько раз подумать, стоит ли ее использовать.

Для запуска контейнера в `privileged` режиме используется флаг `--privileged`, передаваемый `docker run`. По умолчанию он равен `false`.

## Проброс устройств (--devices)

Далее рассмотрим, как можно пробрасывать конкретные устройства в контейнер для разрешения работы с ними — это может использоваться, если, скажем, приложение управляет дисковыми устройствами. Чтобы сделать это, существует опция `--devices`, в которую передается маппинг устройства.

Так, если мы хотим пробросить диск `/dev/sdd` внутрь контейнера, требуется запустить контейнер следующей командой:

```bash
docker run --device /dev/sdd:/dev/sdd nginx:stable
```

## Директива USER в Dockerfile

И последнее, что осталось рассмотреть с точки зрения безопасности, — это директива `USER` в Dockerfile. Она позволяет нам определить, под каким пользователем запускается приложение внутри контейнера.

По умолчанию это пользователь `root`, если, конечно, директива `USER` не была определена в образах, которые используются как основа для нашего образа. Таким образом мы можем ограничить действия внутри контейнера аналогично тому, как мы бы ограничивали их на удаленном сервере.
