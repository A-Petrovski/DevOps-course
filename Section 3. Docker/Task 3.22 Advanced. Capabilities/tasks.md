## 1. Запуск контейнера с минимальными capabilities

### Выполнение

```bash
docker run -d \
  --name inno-dkr-24 \
  --cap-drop=ALL \
  --cap-add=CHOWN \
  --cap-add=SETGID \
  --cap-add=SETUID \
  --cap-add=NET_BIND_SERVICE \
  nginx:stable-alpine
```

### Разбор флагов и параметров
- `docker run` — команда создания и запуска нового контейнера из указанного образа.
- `-d` (`--detach`) — запуск контейнера в фоновом режиме с выводом его полного ID в терминал.
- `--name inno-dkr-24` — присвоение контейнеру фиксированного человекочитаемого имени `inno-dkr-24`.
- `--cap-drop=ALL` — полное удаление всех стандартных Linux capabilities, выданных контейнеру по умолчанию.
- `--cap-add=CHOWN` — разрешение менять владельца и группу файлов/директорий (требуется entrypoint-скриптам Nginx при инициализации директорий кэша и логов).
- `--cap-add=SETGID` — разрешение процессу менять свой GID (требуется мастер-процессу `nginx` для запуска воркеров от группы `nginx`).
- `--cap-add=SETUID` — разрешение процессу менять свой UID (требуется мастер-процессу `nginx` для сброса прав `root` до пользователя `nginx`).
- `--cap-add=NET_BIND_SERVICE` — разрешение процессу привязываться к привилегированным сетевым портам ниже 1024 (стандартный HTTP-порт `80` внутри контейнера).
- `nginx:stable-alpine` — имя и тег образа, на базе которого разворачивается контейнер.

### Сложные моменты и нюансы
- **Почему контейнер падает при нехватке capabilities:** Официальный образ `nginx:stable-alpine` стартует от имени `root`, выполняет скрипт `/docker-entrypoint.sh`, меняет права на служебные директории (`/var/cache/nginx`), открывает порт `80` и запускает рабочие процессы от пользователя `nginx`. Если убрать `ALL` и оставить только `NET_BIND_SERVICE` (или не добавить ничего), ядро Linux заблокирует системные вызовы `chown`, `setuid` или `setgid` ошибкой `EPERM` (`Operation not permitted`), и контейнер мгновенно завершится с ненулевым кодом возврата.
- **Вариативность (2–4 capabilities):** Если переопределить конфигурацию Nginx на прослушивание непривилегированного порта (`>= 1024`, например `8080`), необходимость в `NET_BIND_SERVICE` отпадает, и количество требуемых capabilities сокращается до трёх (`CHOWN`, `SETGID`, `SETUID`) или двух при отключении entrypoint-скриптов.

**Пример использования:**
```bash
docker run -d --name web-hardened --cap-drop=ALL --cap-add=NET_BIND_SERVICE --cap-add=CHOWN --cap-add=SETGID --cap-add=SETUID -p 8080:80 nginx:stable-alpine
```

## 2. Проверка статуса работающего контейнера

### Выполнение

```bash
docker ps
```

### Разбор флагов и параметров
- `docker ps` — вывод таблицы активных (запущенных в данный момент) контейнеров на хосте.

### Сложные моменты и нюансы
- **Как отличать успешный запуск от мгновенного падения:** Если при настройке capabilities допущена ошибка, контейнер появится на долю секунды и сразу остановится. В этом случае обычный `docker ps` не покажет его в списке — потребуется `docker ps -a`, где в колонке `STATUS` будет отображаться `Exited (1) ...` вместо `Up ...`.

**Пример использования:**
```bash
docker ps --filter "name=inno-dkr-24" --format "table {{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Image}}"
```

## 3. Вывод детальной информации о контейнере через docker inspect

### Выполнение

```bash
docker inspect inno-dkr-24
```

### Разбор флагов и параметров
- `docker inspect` — получение полной низкоуровневой конфигурации и текущего состояния объекта Docker в формате JSON.
- `inno-dkr-24` — имя целевого контейнера, передаваемое в качестве аргумента.

### Сложные моменты и нюансы
- **Где искать подтверждение применённых capabilities:** В полном JSON-выводе параметры привилегий находятся внутри объекта `HostConfig` в массивах `"CapDrop"` и `"CapAdd"`. Проверка этих полей гарантирует, что настройки передались демону Docker корректно.

**Пример использования:**
```bash
docker inspect --format '{{json .HostConfig.CapDrop}} {{json .HostConfig.CapAdd}}' inno-dkr-24
```
