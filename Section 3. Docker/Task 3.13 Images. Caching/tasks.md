## Подготовка рабочего окружения

Создаем рабочую директорию и `Dockerfile` по условию задачи:

```bash
mkdir -p ~/docker-cache-lab && cd ~/docker-cache-lab

cat << 'EOF' > Dockerfile
FROM alpine:latest
ARG MYARG
RUN apk update && apk add build-base
EOF
```

* `mkdir -p` — создает директорию (и родительские каталоги при необходимости) без ошибки, если она уже существует.
* `cat << 'EOF' > Dockerfile` — записывает многострочный текст в файл `Dockerfile` без раскрытия shell-переменных.

## Пункт 1. Первичная сборка образа `cache:1`

Выполняем первичную сборку с замером времени и полным выводом прогресса:

```bash
time docker build --progress=plain -t cache:1 .
```

* `time` — системная утилита для замера реального времени (`real`), пользовательского (`user`) и системного (`sys`) процессорного времени выполнения команды.
* `docker build` — запускает процесс сборки образа из `Dockerfile`.
* `--progress=plain` — отключает интерактивное сворачивание шагов в современном сборщике **BuildKit**, позволяя видеть полный статичный лог каждого шага и статус `CACHED`.
* `-t cache:1` (`--tag`) — задает имя репозитория (`cache`) и тег (`1`) для собираемого образа.
* `.` — указывает текущую директорию в качестве контекста сборки (build context).

**Пример использования:**
```bash
docker build --progress=plain -f Dockerfile.prod -t myapp:1.0.0 .
```

## Пункт 2. Повторная сборка образа `cache:2` с использованием кэша

Собираем образ с новым тегом `cache:2` без изменения `Dockerfile` и контекста:

```bash
time docker build --progress=plain -t cache:2 .
```

* `-t cache:2` — присваивает тот же набор кэшированных слоев новому имени/тегу `cache:2`.
* `--progress=plain` — явно показывает строку `=> CACHED [2/2] RUN apk update && apk add build-base 0.0s`.

**Пример использования:**
```bash
docker build -t myapp:latest -t myapp:stable .
```

---

## Пункт 3. Сборка образа с принудительным отключением кэша (`--no-cache`)

Пересобираем образ `cache:2`, заставляя сборщик игнорировать локальный кэш:

```bash
time docker build --progress=plain --no-cache -t cache:2 .
```

* `--no-cache` — запрещает движку использовать существующие слои из локального кэша; каждая инструкция `Dockerfile` выполняется заново с нуля.
* `-t cache:2` — перезаписывает тег `cache:2` на новый собранный образ (старый образ остается в системе как `<none>:<none>`, то есть *dangling image*).

**Пример использования:**
```bash
docker build --no-cache --pull -t security-patched-app:latest .
```

## Пункт 4. Сравнение скорости выполнения, выводов и ID слоев

Проверяем список образов и историю слоев для `cache:1` и `cache:2`:

```bash
docker images cache
docker history cache:1 --no-trunc
docker history cache:2 --no-trunc
```

* `docker images cache` — выводит список всех локальных образов репозитория `cache`, их ID (`IMAGE ID`), время создания и размер.
* `docker history` — отображает историю создания слоев образа снизу вверх (от базового образа к финальному слою).
* `--no-trunc` — отключает обрезку длинных SHA256-хэшей и полных команд в колонке `CREATED BY`.

### Разбор результатов сравнения и нюансов BuildKit:
1. **Скорость:** Первая сборка (`cache:1`) и сборка с `--no-cache` занимают ~15–55 секунд (зависит от сети), так как реально скачивают индексы репозиториев Alpine и устанавливают 18 пакетов `build-base`. Повторная сборка с кэшем выполняется за ~0.1–0.2 секунды.
2. **Вывод:** При использовании кэша в выводе BuildKit (`--progress=plain`) на шаге установки пакетов появляется метка `CACHED` и время `0.0s`, а лог `fetch http://...` отсутствует. При `--no-cache` шаг выполняется полностью с выводом процесса установки.
3. **ID слоев и образов:**
   * До запуска `--no-cache` образы `cache:1` и `cache:2` имели **абсолютно идентичный** `IMAGE ID` (один набор слоев с двумя тегами).
   * После пересборки `cache:2` с `--no-cache` его `IMAGE ID` изменился: даже при неизменных командах создается новый слой с новой временной меткой (`CREATED`) и актуальными версиями пакетов из репозитория.
   * **Нюанс BuildKit:** В колонке `IMAGE` вывода `docker history` промежуточные слои отображаются как `<missing>` — это штатное поведение BuildKit, который хранит только хэш итогового манифеста/конфига и diff-хэши слоев файловой системы ради экономии места.

**Пример использования:**
```bash
docker history --format "table {{.ID}}	{{.Size}}	{{.CreatedBy}}" cache:2
```

## Пункт 5. Сборка образа `cache:3` с аргументом `MYARG=3`

Передаем значение переменной сборки `MYARG=3` без флага `--no-cache`:

```bash
time docker build --progress=plain --build-arg MYARG=3 -t cache:3 .
```

* `--build-arg MYARG=3` — передает значение `3` в инструкцию `ARG MYARG` внутри `Dockerfile` на время сборки.

### Что происходит «под капотом»:
Несмотря на отсутствие `--no-cache`, шаг `RUN apk update && apk add build-base` выполняется заново. В предыдущих сборках `MYARG` был пустым (`MYARG=`), а теперь стал `MYARG=3`. BuildKit инжектирует активные `ARG`-переменные в сигнатуру команды шага `RUN` (`RUN |1 MYARG=3 /bin/sh -c ...`), из-за чего строка инструкции перестает совпадать с кэшем и вызывает пересборку всех последующих слоев.

**Пример использования:**
```bash
docker build --build-arg APP_VERSION=2.4.1 --build-arg GO_ENV=production -t app:2.4.1 .
```

## Пункт 6. Повторная сборка `cache:3` и проверка срабатывания кэша

Повторяем сборку с тем же значением `MYARG=3`:

```bash
time docker build --progress=plain --build-arg MYARG=3 -t cache:3 .
```

* `--progress=plain` — подтверждает, что в логе появилась строка `=> CACHED [2/2] RUN apk update && apk add build-base 0.0s`.
* `--build-arg MYARG=3` — совпадает с сохраненным в кэше значением `ARG`, поэтому хэш-сумма всех шагов идентична предыдущей сборке.

**Пример использования:**
```bash
docker build --progress=plain --build-arg MYARG=3 -t cache:3-verified .
```

## Пункт 7. Сборка образа `cache:4` с аргументом `MYARG=4` (инвалидация кэша)

Меняем значение аргумента на `MYARG=4` и собираем `cache:4`:

```bash
time docker build --progress=plain --build-arg MYARG=4 -t cache:4 .
```

* `--build-arg MYARG=4` — изменяет контекст сборки начиная со второй строки `Dockerfile` (`ARG MYARG`), инвалидируя кэш для инструкции `RUN` и создавая новый слой.

**Пример использования:**
```bash
docker build --build-arg NODE_VERSION=20 -t frontend:node20 .
```

## Пункт 8. Поиск аргумента `MYARG` через `docker inspect` и `docker history`

Проверяем метаданные образа `cache:4`:

```bash
docker inspect cache:4 | grep -i MYARG
docker history cache:4 --no-trunc | grep MYARG
```

* `docker inspect cache:4` — возвращает полные низкоуровневые метаданные образа в формате JSON.
* `grep -i MYARG` — фильтрует вывод, оставляя только строки с упоминанием `MYARG` без учета регистра.
* `docker history cache:4 --no-trunc` — выводит полную историю инструкций, сформировавших слои.

### Важный нюанс (Legacy Builder vs BuildKit):
* В классическом сборщике Docker (`DOCKER_BUILDKIT=0`) аргумент `MYARG=4` сохраняется в JSON-выводе `docker inspect` внутри секции `ContainerConfig.Cmd` (например, `|1 MYARG=4 /bin/sh -c ...`).
* В современном сборщике **BuildKit** (используется по умолчанию в актуальных версиях Docker) поле `ContainerConfig` из `docker inspect` исключается для оптимизации метаданных, а в секции `Config.Env` переменные `ARG` отсутствуют (туда попадают только `ENV`). Поэтому в BuildKit значение `MYARG=4` гарантированно находится через `docker history cache:4 --no-trunc` в колонке `CREATED BY` (`RUN |1 MYARG=4 /bin/sh -c apk update && apk add build-base # buildkit`).

**Пример использования:**
```bash
docker inspect --format '{{json .Config.Env}}' cache:4
```
