# Контрольные вопросы для самопроверки и собеседований

## 1. Что делает опция `--no-cache` в Docker?
Опция `--no-cache` принудительно отключает поиск и переиспользование локальных кэшированных слоев при выполнении `docker build`. Каждая инструкция в `Dockerfile` выполняется заново с нуля, формируя новые слои с новыми контрольными суммами и временными метками.

```bash
docker build --no-cache -t myapp:fresh .
```

---

## 2. Как работает кэширование промежуточных слоев в Docker при сборке образа?
Docker строит образ последовательно, слой за слоем (снизу вверх), сравнивая текущую инструкцию с уже существующими в локальном кэше слоями, имеющими того же родителя:
* Для инструкций `RUN`, `ENV`, `ARG` сравнивается сама строка команды (включая значения всех объявленных выше `ARG`).
* Для инструкций `COPY` и `ADD` дополнительно вычисляется контрольная сумма (хэш) содержимого копируемых файлов.
* Если родительский слой и текущая инструкция полностью совпадают с записью в кэше, Docker не запускает временный контейнер, а берет готовый слой (`CACHED`). Как только хотя бы один слой не совпал, кэш инвалидируется для него и **всех последующих** инструкций в `Dockerfile`.

```bash
# Проверка срабатывания кэша по шагам в логе BuildKit
docker build --progress=plain -t cache:test .
```

## 3. Когда имеет смысл использовать опцию `--no-cache` при сборке образов?
* **Обновление системных пакетов и зависимостей:** когда в `Dockerfile` используются команды без жесткой фиксации версий (например, `apk update && apk add ...`, `apt-get update && apt-get install ...`), а старый кэш содержит устаревшие пакеты с уязвимостями.
* **Загрузка внешних ресурсов по неизменному URL:** когда инструкции `RUN curl ...` или `git clone` обращаются к ссылке, содержимое которой обновилось на удаленном сервере, хотя сама строка в `Dockerfile` осталась прежней.
* **Проверка воспроизводимости сборки:** в CI/CD пайплайнах (например, при ночных релизных сборках), чтобы убедиться, что образ собирается с нуля без опоры на старые локальные артефакты.

```bash
docker build --no-cache --pull -t service:nightly .
```

## 4. Какие проблемы могут возникнуть при использовании кэша промежуточных слоев и в каких случаях опция `--no-cache` может помочь их избежать?
* **Проблема 1: Устаревший индекс пакетов (404 Not Found при установке).** Если `apt-get update` и `apt-get install` разнесены по разным инструкциям `RUN`, слой с `update` может взяться из старого кэша, а последующий `install` попытается скачать удаленные из репозитория старые версии пакетов и упадет с ошибкой. Сборка с `--no-cache` заставит заново выполнить `update` (хотя правильная практика — объединять `update` и `install` в один `RUN`).
* **Проблема 2: Накопление уязвимостей (CVE).** Длительное использование кэша для слоя установки системных библиотек приводит к тому, что в продакшен попадает софт без патчей безопасности. Флаг `--no-cache` (в паре с `--pull`) решает эту проблему, вытягивая свежие версии пакетов.
* **Проблема 3: Неактуальные внешние артефакты.** Кэширование шагов `RUN wget/curl/git clone` маскирует изменения во внешних источниках; `--no-cache` принудительно загружает свежие данные.

```bash
# Полное обновление базового образа и всех слоев сборки
docker build --no-cache --pull -t app:secure .
```

## 5. Как передача и изменение `ARG` влияет на кэш и безопасность образа?
* **Влияние на кэш:** Переменные `ARG` участвуют в формировании сигнатуры всех последующих слоев `RUN`. Изменение значения через `--build-arg` сбрасывает кэш начиная со строки объявления этого `ARG`.
* **Влияние на безопасность:** В отличие от `ENV`, переменные `ARG` не попадают в окружение запущенного контейнера, однако их значения в открытом виде записываются в историю слоев (`docker history --no-trunc`). Поэтому передавать пароли, токены и приватные ключи через `ARG` небезопасно — для этого следует использовать `docker build --secret`.

```bash
# Просмотр истории слоев, где видны значения ARG
docker history cache:4 --no-trunc
```
