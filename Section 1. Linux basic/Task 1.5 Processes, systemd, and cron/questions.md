# Теоретические основы: Управление процессами, Systemd и Cron (Часть 1: Темы 1–5)

## 1. Состояния и сигналы процессов в Linux

### Основные состояния процессов (Process States):
- **`R` (Running / Runnable)** — процесс выполняется на ядре процессора прямо сейчас или стоит в очереди на выполнение.
- **`S` (Interruptible Sleep)** — прерываемый сон (процесс ждёт наступления события, например, ввода с клавиатуры или ответа по сети; реагирует на сигналы).
- **`D` (Uninterruptible Sleep)** — непрерываемый сон (процесс ждёт завершения операции ввода-вывода на диске; не реагирует даже на `SIGKILL` до окончания I/O).
- **`T` (Stopped / Traced)** — процесс приостановлен пользователем (через `Ctrl + Z` или сигнал `SIGSTOP`) либо остановлен отладчиком.
- **`Z` (Zombie / Defunct)** — процесс завершил работу, но его запись осталась в таблице процессов, так как родительский процесс ещё не считал его код возврата (`exit status`).

### Базовое управление сигналами:
```bash
kill -l
kill -15 1234
kill -9 1234
```
- `-l` — вывод полного списка поддерживаемых системой сигналов и их числовых номеров.
- `-15` (`SIGTERM`) — вежливый запрос на завершение работы с сохранением данных и закрытием файлов.
- `-9` (`SIGKILL`) — принудительное мгновенное удаление процесса ядром ОС (процесс не может перехватить или проигнорировать этот сигнал).
- **Пример использования:** `killall -HUP nginx` — отправка сигнала `SIGHUP` (`1`) всем процессам `nginx` для перечитывания конфигурации без разрыва соединений.

## 2. Работа `systemd` и его роль в управлении службами

### Основные функции и архитектура:
- **PID 1 (Init System)** — главный процесс Linux, который запускается ядром первым при загрузке системы, монтирует файловые системы и управляет всеми остальными службами.
- **Параллельный запуск** — в отличие от устаревшего `SysVinit`, `systemd` запускает независимые службы одновременно через сокеты и D-Bus, что многократно ускоряет загрузку ОС.
- **Контроль через `cgroups` (Control Groups)** — каждый сервис изолируется в собственную контрольную группу, что позволяет точно отслеживать потребление CPU/RAM и гарантированно завершать все дочерние процессы службы.
- **Встроенное журналирование (`journald`)** — централизованный сбор всех стандартных потоков вывода (`stdout` и `stderr`) служб в бинарный журнал, доступный через утилиту `journalctl`.

### Основные команды управления:
```bash
sudo systemctl start my-app.service
sudo systemctl enable --now my-app.service
sudo systemctl daemon-reload
sudo journalctl -u my-app.service -n 50 --no-pager
```
- `enable --now` — создание символической ссылки для автозагрузки и одновременный запуск службы.
- `daemon-reload` — обновление конфигурации менеджера после правки `.service` файлов.
- `-u` (в `journalctl`) — фильтрация логов по имени конкретного юнита.
- `-n 50 --no-pager` — вывод последних 50 строк журнала напрямую в терминал без открытия постраничного просмотрщика `less`.

## 3. Создание и настройка `systemd` unit для запуска по расписанию (Timers)

Для периодических задач вместо бесконечного цикла в скрипте используется связка из двух файлов: **`.service`** (что запускать) и **`.timer`** (когда запускать).

### Конфигурация службы (`/etc/systemd/system/backup.service`):
```ini
[Unit]
Description=Scheduled Backup Task

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
```
- `Type=oneshot` — служба запускает команду, ждёт её полного завершения и переходит в статус `inactive (dead)` (идеально для разовых скриптов по расписанию).

### Конфигурация таймера (`/etc/systemd/system/backup.timer`):
```ini
[Unit]
Description=Run Backup every 15 minutes

[Timer]
OnBootSec=2min
OnUnitActiveSec=15min
OnCalendar=*-*-* 03:00:00
Persistent=true

[Install]
WantedBy=timers.target
```
- `OnBootSec=2min` — первый запуск задачи через 2 минуты после загрузки ОС.
- `OnUnitActiveSec=15min` — повторный запуск каждые 15 минут после предыдущей активации.
- `OnCalendar=` — запуск по точному календарному расписанию (формат: `ДеньНедели Год-Месяц-День Час:Минута:Секунда`).
- `Persistent=true` — если сервер был выключен в момент планового запуска, задача выполнится сразу после включения.
- **Пример использования:** `systemctl list-timers --all` — просмотр всех активных таймеров, времени последнего срабатывания и обратного отсчёта до следующего запуска.

## 4. Использование `Load Average` для мониторинга нагрузки

### Что означает показатель:
- **Load Average (LA)** — среднее количество процессов, которые находятся в очереди на выполнение на CPU (`Running`) или ожидают завершения дискового ввода-вывода (`Uninterruptible Sleep`).
- **Три временных интервала:** команда `uptime` и файл `/proc/loadavg` выводят три числа — среднюю нагрузку за **1 минуту**, **5 минут** и **15 минут**.

### Интерпретация значений (зависит от числа ядер `nproc`):
- **Формула оценки:** значение `LA` всегда сравнивается с количеством логических ядер процессора.
- **Нормальная нагрузка (`LA < числа ядер`):** например, `LA = 1.5` на 4-ядерном процессоре означает загрузку ~37.5%, процессор справляется без очередей.
- **Полная загрузка (`LA == числу ядер`):** например, `LA = 4.0` на 4 ядрах означает 100% утилизацию ресурсов без простоя, но и без критических задержек.
- **Перегрузка (`LA > числа ядер`):** например, `LA = 6.0` на 4 ядрах означает, что 2 процесса постоянно простаивают в очереди в ожидании процессорного времени или медленного диска.
- **Динамика тренда:** если 1-минутное значение выше 15-минутного (`3.50, 1.80, 0.90`) — нагрузка резко растёт; если наоборот (`0.80, 1.90, 3.40`) — пик нагрузки уже пройден и система остывает.

## 5. Практическое использование `cron` для автоматизации задач

### Синтаксис таблицы `crontab`:
Каждая строка состоит из 5 полей времени и самой команды:
`[Минута (0-59)] [Час (0-23)] [День месяца (1-31)] [Месяц (1-12)] [День недели (0-7)] [Команда]`

### Примеры расписаний и управление:
```bash
crontab -e
crontab -l
```
```cron
*/10 * * * * /usr/local/bin/check.sh >> /var/log/check.log 2>&1
0 4 * * 1-5 /usr/local/bin/workday_sync.sh
30 2 1 * * /usr/local/bin/monthly_cleanup.sh
@reboot /usr/local/bin/on_startup.sh
```
- `*/10 * * * *` — запуск каждые 10 минут.
- `0 4 * * 1-5` — запуск ровно в `04:00` утра с понедельника (`1`) по пятницу (`5`).
- `30 2 1 * *` — запуск 1-го числа каждого месяца в `02:30`.
- `@reboot` — специальный псевдоним для однократного запуска при каждой загрузке системы.
- `2>&1` — перенаправление потока ошибок (`stderr`) в стандартный вывод (`stdout`), чтобы ошибки выполнения также попадали в лог-файл.

## 6. Лучшие практики (Best Practices) для `systemd` и `cron`

### Рекомендации для `systemd`:
- **Принцип минимальных привилегий:** не запускайте прикладные сервисы от `root`, если им не нужен доступ ко всей системе — создавайте отдельного системного пользователя (`useradd -r -s /bin/false appuser`) и указывайте `User=appuser`.
- **Защита от циклических падений:** при использовании `Restart=always` или `Restart=on-failure` всегда задавайте паузу `RestartSec=5`, чтобы неисправный скрипт не перегружал CPU бесконечными попытками старта.
- **Разделение конфигов:** не редактируйте системные файлы в `/usr/lib/systemd/system/` напрямую (они затрутся при обновлении пакетов). Используйте `sudo systemctl edit my-app.service` для создания переопределений в `/etc/systemd/system/my-app.service.d/override.conf`.

### Рекомендации для `cron`:
- **Абсолютные пути:** у `cron` сильно урезана переменная окружения `$PATH` (обычно только `/usr/bin:/bin`). Всегда указывайте полные пути как к самим утилитам (`/usr/bin/awk`), так и к обрабатываемым файлам (`/home/amp/file.txt`).
- **Защита от наложения запусков (`flock`):** если скрипт выполняется дольше интервала расписания, используйте блокировку, чтобы не плодить десятки копий процесса:
  ```cron
  */5 * * * * /usr/bin/flock -n /tmp/my.lock /usr/local/bin/heavy_script.sh
  ```
  - `-n` (в `flock`) — немедленный выход без ожидания, если предыдущий экземпляр скрипта ещё работает.

## 7. Возможные проблемы и ошибки в `systemd` и `cron`

### Типовые сбои `systemd`:
- **Ошибка `status=203/EXEC`:** отсутствует флаг исполнения на скрипте (`chmod +x`), неверно указан путь в `ExecStart=` или в первой строке скрипта пропущен shebang (`#!/bin/bash`).
- **Unit not found:** `.service` файл сохранён не в `/etc/systemd/system/` или после его создания не выполнена команда `sudo systemctl daemon-reload`.
- **Ошибка формата конца строк (CRLF):** если скрипт редактировался в Windows, он содержит невидимые символы `\r`, из-за чего Linux не находит интерпретатор. Лечится утилитой `dos2unix script.sh`.

### Типовые сбои `cron`:
- **Неэкранированный символ `%`:** `cron` воспринимает знак процента как перевод строки. В командах вроде `date '+%Y-%m-%d'` внутри `crontab` знак `%` обязательно экранируется слешем: `date '+\%Y-\%m-\%d'`.
- **Отсутствие пустой строки в конце `crontab`:** старые версии демона `cron` игнорируют последнюю строку файла, если после неё не нажата клавиша `Enter`.
- **Несовпадение прав доступа:** задача добавлена в пользовательский `crontab -e`, но внутри пытается записывать логи в `/var/log/` или перезапускать системные службы без прав `root`.

## 8. Мониторинг процессов и ресурсов (`ps`, `top`, `htop`)

### Команда `ps` (статический снимок процессов):
```bash
ps aux
ps -ef --forest
ps -eo pid,ppid,cmd,%mem,%cpu --sort=-%cpu | head -n 10
```
- `aux` — вывод всех процессов всех пользователей (`a` — все терминалы, `u` — формат с именем владельца и %CPU/%MEM, `x` — фоновые демоны без терминала).
- `--forest` — построение древовидной иерархии родительских и дочерних процессов.
- `--sort=-%cpu` — сортировка списка по убыванию нагрузки на процессор (с выводом топ-10 через `head`).

### Интерактивные мониторы `top` и `htop`:
```bash
top -u amp
htop
```
- `-u amp` — фильтрация процессов в реальном времени только для конкретного пользователя.
- **Горячие клавиши внутри `top`:** `P` (сортировка по CPU), `M` (сортировка по памяти), `k` (отправка сигнала `kill` выбранному PID), `1` (раздельный вывод загрузки по каждому ядру CPU), `q` (выход).
- **Преимущества `htop`:** цветная визуальная шкала нагрузки на каждое ядро и оперативную память, поддержка мыши, удобный поиск по имени (`F3`), фильтрация (`F4`), древовидный вид (`F5`) и отправка любого сигнала из меню (`F9`).

## 9. Расширенное изучение сигналов процессов

### Таблица ключевых сигналов Linux:
- **`SIGHUP` (`1`)** — разрыв связи с терминалом; в современных демонах используется как команда перечитать конфигурационный файл без перезапуска процесса.
- **`SIGINT` (`2`)** — прерывание процесса с клавиатуры (`Ctrl + C`); программа получает шанс корректно завершить текущую операцию и закрыться.
- **`SIGQUIT` (`3`)** — завершение процесса (`Ctrl + \`) с созданием дампа памяти (`core dump`) для последующей отладки.
- **`SIGKILL` (`9`)** — безусловное уничтожение процесса ядром ОС; не перехватывается программой, не оставляет времени на сохранение данных.
- **`SIGTERM` (`15`)** — стандартный сигнал мягкого завершения (используется командой `kill` по умолчанию без флагов).
- **`SIGSTOP` (`19`) и `SIGTSTP` (`20`)** — приостановка (заморозка) процесса; `SIGTSTP` посылается через `Ctrl + Z` и может быть перехвачен, а `SIGSTOP` срабатывает безусловно.
- **`SIGCONT` (`18`)** — возобновление выполнения ранее остановленного процесса (используется командами `bg` и `fg`).
- **`SIGUSR1` (`10`) и `SIGUSR2` (`12`)** — пользовательские сигналы, поведение которых программист определяет сам (например, для ротации логов или сброса статистики).

## 10. Практические сценарии запуска и управления процессами

### Сценарий 1: Долгая задача, не привязанная к закрытию SSH-сессии (`nohup` / `disown`)
Если запустить процесс через обычный `&` и закрыть терминал, система пошлёт ему сигнал `SIGHUP` и убьёт его. Чтобы задача продолжила работать:
```bash
nohup /usr/local/bin/long_task.sh > /var/log/task.log 2>&1 &
```
- `nohup` — игнорирование сигнала `SIGHUP` при разрыве соединения с терминалом.
- **Альтернатива для уже запущенной задачи:** `Ctrl + Z` → `bg` → `disown -h %1` (отвязывает фоновую задачу от текущей сессии оболочки).

### Сценарий 2: Изменение приоритета выполнения процессов (`nice` и `renice`)
Диапазон приоритетов (`niceness`) в Linux составляет от **`-20`** (максимальный приоритет) до **`+19`** (минимальный приоритет, по умолчанию `0`):
```bash
nice -n 15 /usr/local/bin/backup.sh
sudo renice -n -5 -p 2450
```
- `nice -n 15` — запуск ресурсоёмкого резервного копирования с низким приоритетом, чтобы не тормозить работу основных сервисов.
- `renice -n -5 -p 2450` — повышение приоритета уже работающему процессу с `PID 2450` (отрицательные значения задаются только с правами `root`).

### Сценарий 3: Массовый поиск и завершение зависших процессов (`pgrep` и `pkill`)
```bash
pgrep -af python3
sudo pkill -TERM -f "worker.py"
```
- `-a` и `-f` (в `pgrep`) — поиск по полной командной строке с аргументами и вывод PID вместе с именем команды.
- `pkill -TERM -f` — отправка мягкого сигнала завершения всем процессам, в строке запуска которых встречается `"worker.py"`.
