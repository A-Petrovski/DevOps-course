# Теоретический конспект (Часть 1): Файловые системы, ссылки и Inodes (Темы 1–7)

## 1. Типы файловых систем в Linux (ext4, XFS, Btrfs, NFS, SMB)

Файловые системы в Linux делятся на локальные (дисковые), распределенные (сетевые) и псевдо-файловые системы (виртуальные в RAM, например `tmpfs`, `proc`, `sysfs`).

* **ext4 (Fourth Extended Filesystem)** — стандартная журналируемая ФС для большинства дистрибутивов (Ubuntu/Debian). Поддерживает тома до 1 ЭБ и файлы до 16 ТБ.
* **XFS** — высокопроизводительная 64-битная журналируемая ФС (стандарт в RHEL/CentOS/Rocky Linux). Оптимизирована для параллельного ввода-вывода и крупных файлов.
* **Btrfs (B-Tree FS)** — современная ФС с архитектурой Copy-on-Write (CoW). Включает встроенные снапшоты, сжатие данных «на лету», проверку контрольных сумм и программный RAID.
* **ZFS** — корпоративная CoW-файловая система с продвинутым кэшированием (ARC), дедупликацией и защитой от «тихого» повреждения данных (bit rot).
* **NFS (Network File System)** — сетевой протокол и ФС для монтирования удаленных каталогов между Linux/UNIX-серверами поверх TCP/IP.
* **SMB / CIFS (Server Message Block)** — сетевая ФС для обмена файлами в гетерогенных средах (Linux — Windows).

### Практические команды и флаги

```bash
# Просмотр смонтированных ФС с указанием их типа и объема
df -hT

# Просмотр типов ФС и UUID на всех блочных устройствах (даже несмонтированных)
lsblk -f
```

* `df -hT` — выводит размеры в удобном формате (`-h`) и добавляет столбец `Type` (`-T`).
* `lsblk -f` — отображает дерево устройств вместе с типом ФС (`FSTYPE`), меткой (`LABEL`), `UUID` и точкой монтирования (`MOUNTPOINT`).

**Практический сценарий:** `mount -t nfs 192.168.1.10:/srv/backups /mnt/backups` — подключение общего сетевого хранилища резервных копий к серверу приложений.

## 2. Преимущества и недостатки различных файловых систем

| ФС | Ключевые преимущества | Ограничения и недостатки |
| :--- | :--- | :--- |
| **ext4** | Максимальная стабильность, низкие накладные расходы, возможность как увеличивать, так и **уменьшать** размер раздела. | Медленнее XFS при работе с огромными файлами и высокой многопоточной нагрузкой; фиксированное число `inodes` при создании. |
| **XFS** | Высокая скорость параллельной записи/чтения, динамическое выделение `inodes`, мгновенное расширение (`xfs_growfs`). | **Невозможно уменьшить** размер раздела без полного пересоздания и восстановления из бэкапа. |
| **Btrfs** | Мгновенные CoW-снапшоты, прозрачное сжатие (`zstd`/`lzo`), самовосстановление при наличии зеркал. | Падение производительности на базах данных (из-за CoW без отключения `nodatacow`); историческая нестабильность RAID5/6. |
| **NFS** | Низкие накладные расходы в локальной сети Linux, прозрачная работа с правами POSIX. | Зависимость от стабильности сети; в старых версиях (NFSv3) слабая встроенная безопасность. |
| **SMB** | Полная совместимость с Windows-инфраструктурой и Active Directory. | Более высокие накладные расходы на протокол по сравнению с NFS в чисто Linux-среде. |

### Практические команды и флаги

```bash
# Форматирование раздела в ext4 с заданием метки тома
sudo mkfs.ext4 -L app_data /dev/sdb1

# Форматирование в XFS с принудительной перезаписью старой разметки
sudo mkfs.xfs -f /dev/sdc1
```

* `-L <метка>` — присваивает читаемую метку (`LABEL`) разделу для удобного монтирования.
* `-f` — принудительно перезаписывает существующую файловую систему или сигнатуру раздела без ошибки.

**Практический сценарий:** Выбор `XFS` для серверов баз данных (PostgreSQL) и медиахранилищ, а `ext4` — для корневых разделов ОС (`/`) и систем с частым изменением мелких файлов.

## 3. Механизм работы символических ссылок (symlinks)

Символическая (мягкая) ссылка — это специальный тип файла (обозначается буквой `l` в выводе `ls -l`), внутри которого в виде обычной текстовой строки записан **путь** к целевому файлу или каталогу.

* При обращении программы к симлинку ядро Linux перехватывает запрос, считывает целевой путь и перенаправляет операцию на указанный объект.
* Симлинк имеет собственный номер `inode`, независимый от целевого файла.
* Если удалить или переместить целевой файл, ссылка остается в системе, но становится «битой» (dangling symlink).

### Практические команды и флаги

```bash
# Создание относительной символической ссылки
ln -s ../releases/v2.1/app.conf current.conf

# Поиск всех «битых» символических ссылок в каталоге
find /etc -xtype l
```

* `ln -s <цель> <имя_ссылки>` — создает символическую ссылку (`--symbolic`).
* `find -xtype l` — проверяет тип файла после разыменования ссылки; если цель отсутствует, находит сломанный симлинк.

**Практический сценарий:** `ln -sfn /var/www/releases/build_42 /var/www/current` — атомарное переключение активного релиза веб-приложения при деплое без остановки веб-сервера (флаг `-f` перезаписывает старую ссылку, `-n` не позволяет перейти внутрь каталога по старой ссылке).

## 4. Разница между символическими и жесткими ссылками

| Критерий сравнения | Жесткая ссылка (Hard Link) | Символическая ссылка (Symlink) |
| :--- | :--- | :--- |
| **Связь с данными** | Указывает напрямую на тот же **номер `inode`**, что и исходный файл. | Хранит текстовый **путь** к целевому файлу или папке и имеет свой `inode`. |
| **Границы ФС** | Работает **строго внутри одной** файловой системы (одного раздела). | Работает между разными разделами, дисками и сетевыми ФС. |
| **Ссылки на каталоги** | Запрещены в Linux (для предотвращения зацикливания дерева каталогов). | Полностью поддерживаются для любых директорий. |
| **Удаление оригинала** | Данные остаются доступны через оставшиеся жесткие ссылки, пока счетчик ссылок > 0. | Ссылка становится «битой» (`No such file or directory`), данные теряются. |
| **Размер файла** | Идентичен размеру исходного файла (фактически это второе имя тех же данных). | Равен длине строки пути к целевому объекту (несколько байт). |

### Практические команды и флаги

```bash
# Создание жесткой ссылки
ln /var/log/syslog /tmp/syslog_hardlink

# Просмотр номеров inode и счетчика ссылок
ls -li /var/log/syslog /tmp/syslog_hardlink
```

* `ls -li` — выводит номер индексного дескриптора (`-i`) в первом столбце и количество жестких ссылок на этот `inode` в третьем столбце.

**Практический сценарий:** Создание инкрементальных бэкапов через `rsync --link-dest` или `cp -al`, где неизмененные файлы между копиями хранятся в виде жестких ссылок и не занимают дополнительное место на диске.

## 5. Использование символических ссылок для управления файлами и каталогами

В DevOps-практике симлинки применяются как стандартный паттерн управления конфигурациями и версиями без дублирования файлов:

* **Активация конфигураций сервисов (Nginx, Apache, Systemd):** рабочие конфиги хранятся в `sites-available/`, а для включения создается симлинк в `sites-enabled/`. Отключение сайта сводится к удалению симлинка без потери самого конфига.
* **Zero-downtime деплой (переключение релизов):** каждая сборка распаковывается в отдельную папку с номером версии, а веб-сервер всегда смотрит на симлинк `current`.
* **Вынос тяжелых директорий на другой диск:** если на корневом разделе `/` заканчивается место под `/var/lib/docker`, каталог переносят на отдельный смонтированный диск `/mnt/disk2/docker`, а на старом месте оставляют симлинк.

### Практические команды и флаги

```bash
# Включение виртуального хоста Nginx через создание симлинка
sudo ln -s /etc/nginx/sites-available/api.conf /etc/nginx/sites-enabled/

# Проверка корректности конфигурации и перезагрузка сервиса
sudo nginx -t && sudo systemctl reload nginx
```

* `nginx -t` — тестирует синтаксис конфигурационных файлов, включая все подключенные через симлинки.

**Практический сценарий:** `readlink -f /usr/bin/python3` — определение реального физического пути до исполняемого файла через цепочку символических ссылок.

## 6. Концепция Inodes и их использование в файловых системах

**Inode (индексный дескриптор)** — это структура данных в файловых системах семейства UNIX/Linux, которая хранит все метаданные файла, **кроме его имени и самого содержимого**.

### Что хранится внутри Inode:
* Тип файла (обычный файл, каталог, симлинк, сокет, устройство) и права доступа (`rwx`).
* Владелец (`UID`) и группа (`GID`).
* Размер файла в байтах.
* Временные метки: `atime` (последний доступ), `mtime` (изменение содержимого), `ctime` (изменение метаданных/прав).
* Счетчик жестких ссылок (`Link count`).
* Указатели (адреса) на блоки данных на физическом диске.

Имя файла хранится в специальном файле-каталоге в виде таблицы соответствия: `Имя файла -> Номер inode`.

### Практические команды и флаги

```bash
# Вывод полной информации из inode конкретного файла
stat /etc/passwd

# Просмотр номеров inode всех файлов в текущей директории
ls -ia
```

* `stat <файл>` — отображает все поля `inode`: точный номер `Inode`, `Links`, `Access`, `Uid/Gid` и точные таймстемпы.

**Практический сценарий:** Удаление «проблемного» файла со спецсимволами в имени по его номеру `inode`: `find . -inum 134567 -delete`.

## 7. Проблемы нехватки Inodes и способы их решения

В классических файловых системах (например, `ext4`) максимальное количество индексных дескрипторов (`inodes`) жёстко задаётся при форматировании раздела. Если на сервере генерируются миллионы мелких файлов (сессии PHP, кэш, очередь почты, логи), свободные `inodes` заканчиваются раньше, чем гигабайты на диске.

### Симптомы проблемы:
* Система выдаёт ошибку `No space left on device`, хотя команда `df -h` показывает десятки гигабайт свободного места.
* Невозможно создать ни один новый файл (даже пустой через `touch`), перезапустить службу или записать PID-файл.

### Способы диагностики и решения:

1. **Проверка заполненности inodes:** запуск `df -i`. Если столбец `IUse%` равен `100%`, причина подтверждена.
2. **Поиск каталога-виновника:** подсчёт количества файлов (использованных `inodes`) по директориям и удаление накопившегося мусора.
3. **Переформатирование с увеличенным числом inodes (для `ext4`):** уменьшение коэффициента `bytes-per-inode` (по умолчанию выделяется 1 inode на каждые 16384 байта).
4. **Миграция на XFS или Btrfs:** эти файловые системы выделяют `inodes` динамически по мере необходимости, пока на диске есть свободные блоки.

### Практические команды и флаги

```bash
# 1. Проверка использования inodes по всем смонтированным разделам
df -ih

# 2. Поиск топ-10 директорий с наибольшим количеством мелких файлов в /var
sudo find /var -xdev -printf '%h\n' | sort | uniq -c | sort -rn | head -n 10

# 3. Создание ext4 с увеличенным количеством inodes (1 inode на каждые 4 КБ)
sudo mkfs.ext4 -i 4096 /dev/sdb1
```

* `df -ih` — вывод статистики `inodes` в сокращённом человекочитаемом формате (`K`, `M`).
* `find -xdev` — запрещает утилите `find` переходить на другие смонтированные файловые системы при поиске.
* `-printf '%h\n'` — выводит только путь к родительскому каталогу для каждого найденного файла.
* `mkfs.ext4 -i 4096` — задаёт соотношение байт на один `inode`, увеличивая их общее число в 4 раза относительно стандарта.

**Практический сценарий:** `sudo find /var/lib/php/sessions -type f -mtime +7 -delete` — автоматическая очистка старых файлов сессий старше 7 дней в найденной проблемной директории для мгновенного освобождения `inodes`.


## 8. Основные принципы работы LVM (Logical Volume Manager) в Linux

**LVM (Logical Volume Manager)** — это подсистема ядра Linux (работающая поверх драйвера `device-mapper`), которая создает уровень абстракции между физическими жесткими дисками и файловыми системами. Вместо жесткой привязки к границам физического диска LVM позволяет гибко управлять пространством хранения.

### Трехуровневая архитектура LVM:
* **PV (Physical Volume — Физический том):** инициализированное блочное устройство (весь диск `/dev/sdb`, обычный раздел `/dev/sdb1` или RAID-массив), на которое записаны метаданные LVM.
* **VG (Volume Group — Группа томов):** единый пул дискового пространства, объединяющий один или несколько физических томов (PV). Внутри VG пространство делится на мелкие фиксированные блоки — **экстенты (Physical Extents, PE)**, по умолчанию размером `4 МБ`.
* **LV (Logical Volume — Логический том):** виртуальный аналог обычного раздела, который «нарезается» из пула VG. Именно на LV создается файловая система и выполняется монтирование (путь выглядит как `/dev/<имя_vg>/<имя_lv>` или `/dev/mapper/<имя_vg>-<имя_lv>`).

### Практические команды и флаги

```bash
# Просмотр сводной информации по всем трем уровням LVM
sudo pvs
sudo vgs
sudo lvs

# Подробный вывод с указанием размера экстентов и точных путей устройств
sudo pvdisplay
sudo vgdisplay
sudo lvdisplay
```

* `pvs` / `vgs` / `lvs` — компактные табличные отчеты о состоянии физических томов, групп томов и логических томов.
* `pvdisplay` / `vgdisplay` / `lvdisplay` — детальная техническая сводка (показывает UUID, размер экстента `PE Size`, количество свободных экстентов `Free PE`).

**Практический сценарий:** `sudo lvs -a -o +devices` — быстрая проверка того, на каких именно физических дисках (`Devices`) расположены экстенты конкретного логического тома.

## 9. Создание физических, групповых и логических разделов с использованием LVM

Процесс развертывания хранилища на базе LVM всегда идет строго снизу вверх: от физических устройств к логическим томам.

### Этапы создания:
1. Подготовка физических томов из чистых дисков или разделов (`pvcreate`).
2. Объединение физических томов в общую группу (`vgcreate`).
3. Выделение логических томов нужного размера из пула группы (`lvcreate`).

### Практические команды и флаги

```bash
# 1. Инициализация двух дисков как физических томов (PV)
sudo pvcreate /dev/sdb /dev/sdc

# 2. Создание группы томов (VG) с именем vg_data из обоих дисков
sudo vgcreate vg_data /dev/sdb /dev/sdc

# 3. Создание логического тома (LV) фиксированного размера 5 ГБ
sudo lvcreate -L 5G -n lv_logs vg_data

# 4. Создание второго логического тома на 100% оставшегося свободного места
sudo lvcreate -l 100%FREE -n lv_apps vg_data
```

* `pvcreate <устройство>` — записывает заголовок LVM на диск (уничтожает старые сигнатуры разметки).
* `vgcreate <имя_vg> <pv1> <pv2>` — создает группу томов и добавляет в нее перечисленные PV.
* `lvcreate -L 5G -n <имя_lv> <имя_vg>` — создает логический том с точным размером в гигабайтах/мегабайтах (`-L` / `--size`).
* `lvcreate -l 100%FREE` — задает размер в процентах или количестве экстентов (`-l` / `--extents`).

**Практический сценарий:** `sudo vgcreate -s 16M vg_bigdata /dev/sdb` — создание группы томов с увеличенным размером экстента (`16 МБ` вместо `4 МБ`) для высоконагруженных хранилищ большого объема.

## 10. Управление размерами и расширение логических разделов в LVM

Одно из главных назначений LVM — увеличение дискового пространства без остановки сервисов. Если в группе томов (VG) закончилось место, сначала в нее добавляют новый диск (`vgextend`), а затем расширяют нужный логический том (`lvextend`).

### Порядок масштабирования:
1. Подключить новый диск к серверу и инициализировать его через `pvcreate`.
2. Добавить новый PV в существующую группу томов через `vgextend`.
3. Увеличить размер логического тома через `lvextend`.
4. Расширить файловую систему внутри этого тома (можно сделать одной командой вместе с шагом 3 при помощи флага `-r`).

### Практические команды и флаги

```bash
# 1. Подготовка нового диска и добавление его в существующую группу vg_data
sudo pvcreate /dev/sdd
sudo vgextend vg_data /dev/sdd

# 2. Расширение логического тома на 10 ГБ вместе с файловой системой
sudo lvextend -r -L +10G /dev/vg_data/lv_apps

# 3. Расширение логического тома на всё доступное свободное место в VG
sudo lvextend -r -l +100%FREE /dev/vg_data/lv_apps
```

* `vgextend <имя_vg> <новый_pv>` — увеличивает общий пул памяти группы томов за счет нового физического диска.
* `lvextend -L +10G` — добавляет (`+`) указанный объем к текущему размеру тома (без знака `+` команда попытается установить абсолютный итоговый размер).
* `-r` (`--resizefs`) — автоматически вызывает утилиту расширения файловой системы (`resize2fs` для ext4 или `xfs_growfs` для XFS) сразу после увеличения тома.

**Практический сценарий:** Безопасное уменьшение тома с **ext4** (для XFS уменьшение невозможно): `sudo lvreduce -r -L -5G /dev/vg_data/lv_logs` (выполняется только на предварительно отмонтированном разделе!).

## 11. Работа с файловыми системами на логических разделах LVM

Для ядра и утилит работы с файловыми системами логический том LVM выглядит как обычное блочное устройство. На него распространяются стандартные команды форматирования (`mkfs`), проверки (`fsck`) и монтирования (`mount`).

### Особенности работы с ФС поверх LVM:
* **Собственный UUID:** каждый логический том после форматирования получает уникальный идентификатор файловой системы (`UUID`), который используется для надежного монтирования.
* **Разные ФС в одной VG:** внутри одной группы томов можно создать один LV с `ext4` (например, для корневого раздела `/` с возможностью уменьшения) и второй LV с `XFS` (для баз данных и логов).
* **Пути устройств:** обращаться к тому можно как через `/dev/vg_data/lv_apps`, так и через `/dev/mapper/vg_data-lv_apps` — это символические ссылки на одно и то же устройство `dm-*`.

### Практические команды и флаги

```bash
# Форматирование логического тома в XFS и ext4
sudo mkfs.xfs /dev/vg_data/lv_apps
sudo mkfs.ext4 /dev/vg_data/lv_logs

# Создание точек монтирования и подключение томов
sudo mkdir -p /var/www/apps /var/log/apps
sudo mount /dev/vg_data/lv_apps /var/www/apps
sudo mount /dev/vg_data/lv_logs /var/log/apps

# Просмотр UUID и типов ФС на логических томах
sudo blkid /dev/vg_data/*
```

* `blkid` — выводит точные `UUID` и `TYPE` файловых систем на указанных блочных устройствах.

**Практический сценарий:** Если расширение LV было выполнено без флага `-r`, файловую систему расширяют вручную: `sudo xfs_growfs /var/www/apps` (для XFS) или `sudo resize2fs /dev/vg_data/lv_logs` (для ext4).


## 12. Преимущества и возможности использования LVM для управления хранилищем

Использование LVM в продакшн-инфраструктуре решает ключевые ограничения классической таблицы разделов (MBR/GPT):

* **Объединение дисков в единый пул:** позволяет собрать несколько небольших физических дисков в одну большую файловую систему (например, три диска по 500 ГБ в один том на 1.5 ТБ).
* **Масштабирование «на лету» (Online Resizing):** увеличение дискового пространства происходит без перезагрузки сервера и без остановки работающих баз данных или веб-приложений.
* **Мгновенные снимки (LVM Snapshots):** технология Copy-on-Write позволяет за доли секунды заморозить состояние тома для консистентного резервного копирования работающей БД или безопасного тестирования обновлений с возможностью отката.
* **Живая миграция данных (`pvmove`):** позволяет перенести данные со старого или сбоящего физического диска на новый диск прямо во время работы системы, после чего старый диск безопасно выводится из группы (`vgreduce`).
* **Гибкие режимы размещения (Striping / Mirroring):** поддержка чередования блоков для ускорения чтения/записи (аналог RAID 0) и зеркалирования томов для отказоустойчивости (аналог RAID 1).

### Практические команды и флаги

```bash
# Создание снимка (snapshot) логического тома размером 2 ГБ для бэкапа
sudo lvcreate -s -L 2G -n snap_apps /dev/vg_data/lv_apps

# Перенос данных со старого диска /dev/sdb на новый /dev/sdd без остановки работы
sudo pvmove /dev/sdb /dev/sdd

# Удаление освободившегося диска из группы томов и очистка метаданных
sudo vgreduce vg_data /dev/sdb
sudo pvremove /dev/sdb
```

* `lvcreate -s` — создает снимок (`--snapshot`) указанного исходного логического тома.
* `pvmove <источник> <назначение>` — перемещает все выделенные физические экстенты с одного PV на другой в фоновом режиме.
* `vgreduce <имя_vg> <pv>` — исключает пустой физический том из группы томов.

**Практический сценарий:** Откат неудачного обновления приложения из снимка LVM: `sudo lvconvert --merge /dev/vg_data/snap_apps` (после размонтирования тома состояние вернется точно к моменту создания снапшота).

## 13. Использование файла `/etc/fstab` для автоматического монтирования

Файл **`/etc/fstab` (File Systems Table)** содержит статическую конфигурацию дисковых разделов, логических томов и сетевых хранилищ, которые система автоматически монтирует при загрузке (через генератор `systemd-fstab-generator`).

### Структура строки `/etc/fstab` (6 полей через пробел или табуляцию):
`<Устройство/UUID>  <Точка_монтирования>  <Тип_ФС>  <Опции>  <Dump>  <Pass>`

1. **Устройство:** рекомендуется использовать `UUID=...` (для обычных разделов) или путь `/dev/mapper/vg_data-lv_apps` (для LVM, так как имена в devmapper не меняются при перестановке дисков).
2. **Точка монтирования:** существующий пустой каталог (например, `/mnt/data`).
3. **Тип ФС:** `xfs`, `ext4`, `nfs`, `swap` и т.д.
4. **Опции монтирования:** `defaults` (включает `rw, suid, dev, exec, auto, nouser, async`), а также критически важная опция **`nofail`** для дополнительных и сетевых дисков (не дает серверу упасть в аварийный режим `emergency mode`, если диск временно недоступен при загрузке).
5. **Dump (`0` или `1`):** флаг устаревшей утилиты резервного копирования `dump` (всегда ставится `0`).
6. **Pass / fsck (`0`, `1` или `2`):** порядок проверки файловой системы при загрузке (`1` — только для корневого раздела `/`, `2` — для остальных локальных разделов `ext4`, `0` — отключить проверку; для `XFS` и сетевых ФС всегда ставится `0`).

### Практические команды и флаги

```bash
# Пример безопасной записи в /etc/fstab для тома LVM с файловой системой XFS
echo "/dev/mapper/vg_data-lv_apps /var/www/apps xfs defaults,nofail 0 0" | sudo tee -a /etc/fstab

# Проверка синтаксиса /etc/fstab и монтирование всех несмонтированных записей БЕЗ перезагрузки
sudo mount -a

# Обновление конфигурации systemd после правки /etc/fstab
sudo systemctl daemon-reload
```

* `mount -a` — считывает `/etc/fstab` и монтирует все описанные в нем файловые системы; **обязательно выполнять перед перезагрузкой сервера**, чтобы сразу отловить опечатки.
* `nofail` — предотвращает остановку загрузки ОС при отсутствии дополнительного диска.

**Практический сценарий:** Безопасное редактирование конфигурации через `sudo cp /etc/fstab /etc/fstab.bak && sudo nano /etc/fstab` с обязательной проверкой командой `sudo findmnt --verify` перед ребутом.

## 14. Практическое применение и настройка LVM в конкретных сценариях

### Сценарий А: Вынос каталога Docker (`/var/lib/docker`) на отдельный диск LVM
На продакшн-серверах образы и логи контейнеров быстро забивают корневой раздел `/`. Вынос директории на отдельный LV изолирует ОС от падения при нехватке места.

```bash
# 1. Остановка службы Docker
sudo systemctl stop docker

# 2. Создание тома LVM, форматирование в XFS и временное монтирование
sudo lvcreate -L 20G -n lv_docker vg_data
sudo mkfs.xfs /dev/vg_data/lv_docker
sudo mkdir -p /mnt/docker_new
sudo mount /dev/vg_data/lv_docker /mnt/docker_new

# 3. Перенос существующих данных Docker с сохранением всех прав и ссылок
sudo rsync -aHAX /var/lib/docker/ /mnt/docker_new/

# 4. Перемонтирование на постоянное место и прописывание в /etc/fstab
sudo umount /mnt/docker_new
sudo rm -rf /var/lib/docker/*
echo "/dev/mapper/vg_data-lv_docker /var/lib/docker xfs defaults,nofail 0 0" | sudo tee -a /etc/fstab
sudo mount -a

# 5. Запуск службы Docker
sudo systemctl start docker
```

### Сценарий Б: Быстрое расширение корневого раздела `/` на облачном сервере (VPS)
После увеличения размера виртуального диска в панели облачного провайдера (например, с 20 ГБ до 40 ГБ) свободное место нужно передать корневому тому LVM.

```bash
# 1. Расширение физического раздела (например, 3-го раздела на /dev/sda)
sudo growpart /dev/sda 3

# 2. Уведомление LVM об изменении размера физического тома PV
sudo pvresize /dev/sda3

# 3. Расширение корневого LV на 100% нового свободного места вместе с ФС
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv

# 4. Проверка итогового объема корневого раздела
df -h /
```

* `rsync -aHAX` — копирование файлов с полным сохранением прав, владельцев, жестких ссылок (`-H`), списков ACL (`-A`) и расширенных атрибутов (`-X`), критически важных для контейнеров.
* `pvresize <устройство>` — обновляет метаданные физического тома LVM после расширения базового раздела диска.
