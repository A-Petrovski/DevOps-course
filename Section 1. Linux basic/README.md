# Регламент обучения и рабочие DevOps-практики

## 1. Инфраструктура и подключение
- **Основной рабочий инструмент:** Все задачи выполняются удалённо на виртуальной машине `Ubuntu Server` через терминал **Windows PowerShell** по протоколу `SSH` (`ssh user@ip_address`). Это обеспечивает привычную работу с буфером обмена и приближает процесс к реальному администрированию серверов.
- **Снимки состояния (Snapshots):** Перед началом сложного блока или после успешного завершения каждой задачи/модуля обязательно делается снапшот виртуальной машины. Это позволяет мгновенно откатить систему при критических ошибках.

## 2. Фиксация истории команд
- Вся история команд для каждого учебного раздела сохраняется в отдельный текстовый файл по шаблону `history_<раздел>_<подраздел>.txt` (например, `history_1_1.txt`, `history_1_5.txt`).
- Перед выгрузкой истории в файл выполняется принудительная запись буфера текущей сессии на диск:
  ```bash
  history -a
  history | tail -n 100 > ~/history_1_1.txt
  ```
- При необходимости передачи файлов отчётов или логов между `Ubuntu Server` и хост-машиной используется утилита `scp -O` (принудительный классический протокол без SFTP) или перенаправление вывода через SSH (`ssh user@ip "cat ~/file" > file`).

## 3. Инженерные практики при работе с Linux
- **Безопасность и права доступа:** Прикладные сервисы и скрипты по возможности запускаются от имени отдельных системных пользователей без права интерактивного входа (`useradd -r -s /bin/false`), а не от `root`.
- **Отладка и диагностика:**
  - При сбоях в bash-скриптах используется пошаговая трассировка выполнения: `bash -x script.sh`.
  - При проблемах со службами проверяется статус и системный журнал: `systemctl status <service>` и `journalctl -u <service> -n 30 --no-pager`.
  - Соблюдается правило обновления `systemd`: правка `.sh` скрипта требует `systemctl restart`, правка `.service` файла требует `systemctl daemon-reload` + `systemctl restart`.
- **Надёжность скриптов и автоматизации:**
  - В `cron` всегда используются абсолютные пути к утилитам и файлам, а символ `%` экранируется (`\%`).
  - Для защиты от наложения долгих задач в планировщике применяется блокировка `flock -n`.
  - При работе с `awk` и дробными числами учитывается системная локаль (`LC_ALL=C`) и не используются зарезервированные имена переменных (например, `load`).

## 4. Алгоритм ведения базы знаний (GitHub)
1. **Старт модуля:** Создание нового чата с ИИ и передача системной инструкции для генерации конспектов.
2. **Практика:** Выполнение чекпоинтов на `Ubuntu Server` через PowerShell SSH, отладка и сохранение файла `history_X_X.txt`.
3. **Сборка конспекта:**
   - Запрос **Практического блока** (решения чекпоинтов с разбором всех флагов) и сохранение в файл модуля (`tasks.md`).
   - Запрос **Теоретического блока** в двух частях (Темы 1–5 и Темы 6–10) и сохранение в файл теории (`theory.md`).
4. **Фиксация прогресса:** Создание финального снапшота ВМ и отправка (`git push`) обновлённых шпаргалок в репозиторий на GitHub.
