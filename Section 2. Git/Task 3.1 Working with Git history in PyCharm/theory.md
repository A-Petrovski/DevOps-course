## Общее описание Task 3

Поработайте с Git в PyCharm и в Visual Studio Code. Сравните, где удобнее откатывать изменения, резолвить merge-conflicts, сравнивать ветки между собой, переключаться между бранчами и коммитить. В общем, посмотрите все основные функции работы с Git, в том числе — как менять remote origin.

Для Visual Studio Code обратите внимание на плагины, которые расширяют работу с историей коммитов (например, GitLens: `https://www.youtube.com/watch?v=UQPb73Zz9qk`).

Это две основные IDE, которые используются в работе. Работа из командной строки — скорее исключение, она сильно замедляет процесс. Но с ней тоже нужно разобраться, потому что иногда командная строка — это всё, что доступно. Также попробуйте meld (`apt install meld`) или для Windows (`https://meldmerge.org/`).

## Task 3.1. Работа с историей Git в PyCharm

**Цель:** научиться осознанно управлять историей Git через UI PyCharm — без зависимости от командной строки, но с пониманием, что происходит “под капотом”.

### 3.1.1. Базовая навигация по истории

**Задание:**
1. Откройте Git Log в PyCharm.
2. Найдите:
   - последний коммит,
   - коммит по автору,
   - коммит по части сообщения.
3. Откройте diff выбранного коммита.

**Чекпоинты:**
Вы умеете:
- читать граф веток,
- находить нужный коммит,
- смотреть изменения по коммиту и по файлам.

### 3.1.2. Сравнение версий и веток

**Задание:**
1. Сравните:
   - текущую версию файла с предыдущим коммитом (`Compare with Local`),
   - две ветки между собой (`Compare with Branch or Tag…`).
2. Определите:
   - какие файлы отличаются,
   - какие коммиты попадут в merge.

**Чекпоинты:**
Вы понимаете:
- разницу между diff по файлам и diff по коммитам,
- как заранее оценить последствия merge.

### 3.1.3. Откат изменений: Reset vs Revert vs Local History

**Задание:**
1. Сделайте 2–3 тестовых коммита.
2. Выполните:
   - `Reset Current Branch to Here… (soft)`
   - `Reset Current Branch to Here… (mixed)`
   - `Revert Commit` для одного из коммитов.
3. Измените файл без коммита и откатите его через Local History.

**Чекпоинты:**
Вы можете объяснить:
- чем отличается reset от revert,
- когда безопасно использовать reset,
- когда нужно использовать revert,
- чем Git-откат отличается от Local History rollback.

### 3.1.4. Cherry-pick

**Задание:**
1. Создайте вторую ветку от середины истории.
2. Сделайте в ней один коммит.
3. Вернитесь в основную ветку и выполните Cherry-pick этого коммита.
4. (Опционально) создайте конфликт и разрешите его через merge tool.

**Чекпоинты:**
Вы умеете:
- переносить отдельные изменения между ветками,
- решать конфликты в PyCharm,
- понимать, что cherry-pick создаёт новый коммит.

### 3.1.5. Squash и Fixup

**Задание:**
1. В feature-ветке сделайте 5–6 коммитов:
   - часть из них — “мусорные” (`wip`, `fix typo`, `try again`).
2. Используйте:
   - `Squash Commits…` — объедините коммиты в один,
   - `Fixup…` — приклейте исправление к правильному коммиту.
3. Проверьте итоговую историю.

**Чекпоинты:**
Вы понимаете:
- разницу между squash и fixup,
- как делать историю “чистой” перед merge,
- почему это важно для code review.

### 3.1.6. Interactive Rebase from Here

**Задание:**
1. Запустите `Interactively Rebase from Here…`.
2. Выполните:
   - `reorder` коммитов,
   - `reword` сообщения одного коммита,
   - `drop` одного коммита,
   - `squash` двух коммитов.
3. Завершите rebase.

**Чекпоинты:**
Вы умеете:
- переписывать историю осознанно,
- объяснять, что такое interactive rebase,
- понимать риск переписывания истории.

### 3.1.7. Rebase на актуальный main

**Задание:**
1. Обновите main (`pull`).
2. В feature-ветке выполните Rebase на main.
3. Разрешите конфликт (если появится).
4. Завершите rebase.

**Чекпоинты:**
Вы понимаете:
- разницу между merge и rebase,
- зачем rebase используется перед PR,
- как разрешать конфликты в процессе rebase.

### 3.1.8. Checkout revision и работа в detached HEAD

**Задание:**
1. Выберите старый коммит → `Checkout Revision`.
2. Убедитесь, что вы в состоянии `detached HEAD`.
3. Создайте новую ветку из этого состояния.

**Чекпоинты:**
Вы понимаете:
- что такое detached HEAD,
- почему нельзя долго работать без ветки,
- как правильно “спасти” изменения.

### 3.1.9. Управление доставкой изменений

**Задание:**
1. Сделайте несколько локальных коммитов.
2. Используйте `Push All up to Here…`.
3. Смоделируйте ситуацию, где требуется force push (после rebase).
4. Обсудите риски.

**Чекпоинты:**
Вы понимаете:
- когда нужен обычный push,
- когда появляется необходимость в force push,
- почему force push опасен в shared-ветках.
