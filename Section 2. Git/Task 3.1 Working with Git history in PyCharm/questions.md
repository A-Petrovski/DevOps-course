## 3.1.1. Базовая навигация по истории

### Как читать граф веток, находить нужный коммит и смотреть изменения?
- **Ответ:** Граф веток читается снизу вверх (от старых коммитов к новым). Цветные линии показывают ответвления и точки их слияния (`merge`), а ярлык `HEAD` указывает на текущее активное состояние рабочей директории. Поиск осуществляется фильтрацией по автору, ветке, дате или подстроке в сообщении коммита. Изменения внутри коммита просматриваются через окно построчного сравнения (`diff`).
- **Пример в консоли:**
```bash
git log --oneline --graph --all --author="Petrovski" --grep="nginx"
git show <commit_hash>
```

## 3.1.2. Сравнение версий и веток

### В чем разница между diff по файлам и diff по коммитам?
- **Ответ:** **Diff по коммитам** показывает список отдельных шагов (историю изменений), которые есть в одной ветке, но отсутствуют в другой. **Diff по файлам** сравнивает только итоговые снимки (состояние кода) двух выбранных веток или коммитов, игнорируя промежуточные правки, которые были сделаны и позже отменены внутри ветки.
- **Пример в консоли:**
```bash
# Список коммитов, которые есть в feature, но нет в main
git log main..feature --oneline

# Итоговая разница в коде между конечными точками веток
git diff main...feature
```

### Как заранее оценить последствия merge?
- **Ответ:** С помощью сравнения веток (`Compare with Current` в PyCharm или `git diff main...feature` в консоли) можно заранее увидеть весь список затрагиваемых файлов и объем изменений. Если в обеих ветках изменялись одни и те же участки одних и тех же файлов, при слиянии гарантированно возникнет merge-конфликт.
- **Пример в консоли:**
```bash
git diff --stat main...feature
```

## 3.1.3. Откат изменений: Reset vs Revert vs Local History

### Чем отличается reset от revert?
- **Ответ:** `git reset` переписывает историю, перемещая указатель ветки назад и удаляя последующие коммиты из истории ветки. `git revert` историю не удаляет, а создает поверх нее **новый коммит**, который вносит зеркально противоположные изменения для отмены выбранного старого коммита.
- **Пример в консоли:**
```bash
# Удаляет последний коммит из истории, оставляя правки в файлах
git reset --mixed HEAD~1

# Создает новый коммит, отменяющий изменения указанного коммита
git revert <commit_hash>
```

### Когда безопасно использовать reset, а когда нужно использовать revert?
- **Ответ:** **Reset** безопасно использовать только для **локальных** коммитов, которые еще не были отправлены (`push`) в общий удаленный репозиторий, либо в личной ветке, с которой работаете только вы. **Revert** необходимо использовать всегда, когда ошибочный коммит уже попал в общую ветку (`main`, `develop`), чтобы не сломать историю другим разработчикам.
- **Пример в консоли:**
```bash
# Безопасно для локальных коммитов до push
git reset --soft HEAD~1

# Безопасно для публичных веток после push
git revert --no-edit <bad_commit_hash>
```

### Чем Git-откат отличается от Local History rollback?
- **Ответ:** Откат через Git оперирует только зафиксированными коммитами или состоянием индекса (`HEAD`). **Local History** — это встроенный механизм самой IDE (PyCharm), который автоматически сохраняет снимки файлов при каждом их изменении и сохранении на диск (`Ctrl + S`), даже если эти правки ни разу не индексировались и не коммитились в Git.

## 3.1.4. Cherry-pick

### Что делает cherry-pick и почему он создает новый коммит?
- **Ответ:** `cherry-pick` берет изменения из одного конкретного коммита в другой ветке и применяет их к текущей ветке. Он создает **новый коммит с новым SHA-1 хэшем**, так как у перенесенного коммита меняется родительский коммит (база) и время создания, даже если автор и текст изменений остались прежними.
- **Пример в консоли:**
```bash
git cherry-pick -x <commit_hash>
```

### Как переносить отдельные изменения и решать конфликты в PyCharm?
- **Ответ:** В `Git -> Log` нужно нажать ПКМ по нужному коммиту в соседней ветке и выбрать **Cherry-Pick**. Если в текущей ветке те же строки файла уже изменены иначе, PyCharm откроет окно **Conflicts** с кнопкой **Merge…**, где в трехпанельном редакторе можно выбрать нужные строки из левой (текущей) и правой (переносимой) версий в центральный итоговый файл.

## 3.1.5. Squash и Fixup

### В чем разница между squash и fixup?
- **Ответ:** Обе операции объединяют несколько коммитов в один. Разница в обработке сообщений коммитов: **Squash** объединяет тексты сообщений всех склеиваемых коммитов и открывает редактор для написания нового общего описания. **Fixup** молча вливает изменения в родительский коммит, **полностью отбрасывая** сообщение дочернего (мусорного) коммита и оставляя оригинальное описание без изменений.
- **Пример в консоли:**
```bash
git commit --fixup=<target_commit_hash>
git rebase -i --autosquash HEAD~4
```

### Как делать историю «чистой» перед merge и почему это важно для code review?
- **Ответ:** Перед созданием Pull Request / Merge Request промежуточные коммиты вроде `wip`, `fix typo`, `try again` объединяют через `Squash` или `Fixup` в 1–3 логически законченных коммита. Для **code review** это критически важно: ревьюер видит атомарные, осмысленные изменения с понятным описанием причины правки вместо десятков хаотичных попыток исправить опечатки.

## 3.1.6. Interactive Rebase from Here

### Что такое interactive rebase и какие задачи он решает?
- **Ответ:** Интерактивный ребейз (`git rebase -i`) — это инструмент полного редактирования цепочки коммитов перед их публикацией. Он позволяет менять порядок коммитов (`reorder`), переименовывать их сообщения (`reword`), полностью удалять ненужные коммиты (`drop`) и объединять несколько коммитов в один (`squash` / `fixup`).
- **Пример в консоли:**
```bash
git rebase -i HEAD~5
```

### В чем заключается главный риск переписывания истории?
- **Ответ:** Любое изменение коммита при интерактивном ребейзе (даже простое исправление опечатки в сообщении через `reword`) меняет его SHA-1 хэш, а также хэши всех последующих коммитов. Если переписать историю ветки, которая уже была отправлена в общий репозиторий и скачана коллегами, у команды возникнет расхождение историй и дублирование коммитов при попытке синхронизации.

## 3.1.7. Rebase на актуальный main

### В чем разница между merge и rebase?
- **Ответ:** **Merge** сохраняет историю такой, какая она есть, связывая две ветки специальным `merge-коммитом` с двумя родителями (на графе остаются параллельные линии). **Rebase** берет все коммиты из `feature`-ветки и по очереди пересоздает их поверх самого свежего коммита ветки `main`, выстраивая абсолютно ровную линейную историю без лишних коммитов слияния.
- **Пример в консоли:**
```bash
git checkout feature
git rebase main
```

### Зачем rebase используется перед PR и как разрешать конфликты в процессе?
- **Ответ:** `Rebase` на актуальный `main` перед созданием PR гарантирует, что ваша ветка уже содержит все последние изменения команды, а сам PR вольется в `main` чисто и без конфликтов (fast-forward). Если во время `rebase` возникает конфликт, процесс ставится на паузу на конкретном коммите: нужно разрешить конфликт в файле (или через Merge Tool в PyCharm), добавить файл в индекс и продолжить перебазирование.
- **Пример в консоли:**
```bash
# После разрешения конфликта в файлах
git add conflicted_file.txt
git rebase --continue

# Для полной отмены ребейза и возврата в исходное состояние
git rebase --abort
```

## 3.1.8. Checkout revision и работа в detached HEAD

### Что такое detached HEAD и почему нельзя долго работать без ветки?
- **Ответ:** **Detached HEAD** (отсоединенный указатель) — это состояние, когда `HEAD` ссылается напрямую на конкретный хэш коммита, а не на имя ветки. Работать в этом режиме опасно, потому что новые коммиты не привязаны ни к одной ветке: как только вы сделаете `checkout` на другую ветку, эти коммиты исчезнут из лога и через некоторое время будут навсегда удалены сборщиком мусора Git (`git gc`).
- **Пример в консоли:**
```bash
# Вход в detached HEAD
git checkout <old_commit_hash>
```

### Как правильно «спасти» изменения из detached HEAD?
- **Ответ:** Находясь на последнем коммите в состоянии `detached HEAD`, нужно создать от него новую ветку (через **New Branch…** в PyCharm или `git switch -c` в терминале). Все сделанные коммиты автоматически закрепятся за этой новой веткой. Если вы уже ушли на другую ветку без создания новой, найти хэш «потерянного» коммита можно через `git reflog`.
- **Пример в консоли:**
```bash
# Создание ветки прямо из detached HEAD
git switch -c saved-work

# Поиск потерянного коммита, если уже переключились на другую ветку
git reflog
git checkout -b saved-work <lost_commit_hash>
```

## 3.1.9. Управление доставкой изменений

### Когда нужен обычный push, а когда появляется необходимость в force push?
- **Ответ:** Обычный `git push` используется, когда новые локальные коммиты добавляются строго поверх текущего состояния удаленной ветки (fast-forward). Необходимость в `force push` возникает после локального переписывания истории (`rebase`, `squash`, `amend`, `reset`) для коммитов, которые уже были ранее отправлены на сервер, так как сервер отклонит обычный `push` из-за несовпадения хэшей.
- **Пример в консоли:**
```bash
# Обычная отправка новых коммитов
git push origin feature

# Безопасная принудительная отправка после rebase
git push --force-with-lease origin feature
```

### Почему force push опасен в shared-ветках?
- **Ответ:** В общих ветках (`main`, `develop`, общие `feature`-ветки) команда `git push --force` затирает историю на сервере вашей локальной версией. Если другой разработчик успел отправить в эту ветку свои коммиты, они будут уничтожены на сервере, а у остальных участников команды при выполнении `git pull` возникнут тяжелые конфликты и дублирование старых коммитов. Поэтому в shared-ветках `force push` запрещают на уровне настроек GitLab/GitHub (`Protected Branches`), а в личных ветках используют флаг `--force-with-lease`.
