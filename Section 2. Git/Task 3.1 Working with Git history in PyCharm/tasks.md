## Общий блок: Смена remote origin, VS Code (GitLens) и Meld

### Действия в UI и системе
1. **Смена `remote origin` в PyCharm:** Верхнее меню **Git → Manage Remotes…** → выделить `origin` → нажать иконку карандаша (**Edit**) → вставить новый URL репозитория → **OK**.
2. **Работа в VS Code с GitLens:** Установить расширение **GitLens** (`eamodio.gitlens`). Оно добавляет inline-аннотации `blame` в конце каждой строки, всплывающие подсказки при наведении на коммит, верхний `Git CodeLens` над блоками кода и боковую панель **Source Control** для просмотра графа коммитов, веток и откатов (`Revert` / `Reset` через ПКМ по коммиту).
3. **Установка и подключение визуального diff-инструмента Meld:**

```bash
sudo apt update && sudo apt install -y meld
git config --global merge.tool meld
git config --global diff.tool meld
git config --global mergetool.prompt false
```

- `--global` — применяет настройку ко всем репозиториям текущего пользователя (записывает в `~/.gitconfig`).
- `merge.tool meld` / `diff.tool meld` — назначает утилиту `meld` инструментом по умолчанию для разрешения конфликтов слияния и сравнения файлов.
- `mergetool.prompt false` — отключает запрос подтверждения перед запуском окна Meld при вызове `git mergetool`.

**Пример использования:** `git mergetool` (запускает трехпанельное окно Meld для визуального разрешения конфликтов из терминала).

## 3.1.1. Базовая навигация по истории

### Действия в UI PyCharm
1. Откройте вкладку **Git** (`Alt + 9`) → подвкладка **Log**.
2. **Последний коммит:** находится в самом верху списка; ветка с отметкой `HEAD` (зеленый бейдж или значок указателя) показывает текущее положение.
3. **Поиск по автору:** в верхней панели фильтрации над списком коммитов нажмите **User** → выберите имя автора.
4. **Поиск по части сообщения:** введите слово или часть хэша в поле поиска **Text or hash** (`Ctrl + F` внутри окна Log).
5. **Просмотр diff:** кликните на нужный коммит один раз — в правой части окна появится список измененных файлов. Дважды кликните по любому файлу (или нажмите `Ctrl + D`), чтобы открыть окно построчного сравнения.

### CLI-эквивалент
```bash
git log --oneline --graph --all
git log --author="Alexander" --grep="fix" -p -n 2
```

- `--oneline` — выводит каждый коммит в одну компактную строку (короткий хэш + заголовок).
- `--graph` — рисует ASCII-граф ветвлений и слияний слева от списка коммитов.
- `--all` — показывает коммиты всех локальных и удаленных веток, а не только текущей.
- `--author="Alexander"` — фильтрует историю по имени или email автора коммита.
- `--grep="fix"` — ищет коммиты, в сообщении которых встречается указанная подстрока.
- `-p` — выводит полный построчный diff (патч) изменений для каждого найденного коммита.
- `-n 2` — ограничивает вывод двумя последними подходящими коммитами.

**Пример использования:** `git log --oneline --grep="nginx" -n 5`

## 3.1.2. Сравнение версий и веток

### Действия в UI PyCharm
1. **Сравнение файла с предыдущим коммитом:** откройте измененный файл (или нажмите ПКМ по файлу в дереве проекта) → **Git → Compare with…** (или **Compare with the Same Repository Version** для сравнения локальных некоммиченных правок с последним коммитом).
2. **Сравнение двух веток:** в левой панели окна **Git → Log** найдите нужную ветку (например, `feature`), нажмите по ней ПКМ и выберите **Compare with Current** (или в главном меню **Git → Branches… → выбрать ветку → Compare with Current**).
3. **Анализ окна сравнения:**
   - Верхняя панель показывает две вкладки коммитов: коммиты, которые есть в `feature`, но отсутствуют в текущей ветке (именно они попадут в merge), и наоборот.
   - Нижняя панель показывает итоговый список всех отличающихся файлов между конечными точками обеих веток.

### CLI-эквивалент
```bash
git diff HEAD -- path/to/file.txt
git log main..feature --oneline
git diff main...feature --stat
```

- `HEAD` — указатель на последний коммит текущей ветки.
- `main..feature` (две точки) — выводит коммиты, которые присутствуют в `feature`, но еще не влиты в `main`.
- `main...feature` (три точки) — сравнивает ветку `feature` с общим предком веток `main` и `feature`.
- `--stat` — показывает краткую сводку измененных файлов и количество добавленных/удаленных строк без полного текста.

**Пример использования:** `git diff --name-only main...feature`

## 3.1.3. Откат изменений: Reset vs Revert vs Local History

### Действия в UI PyCharm
1. Создайте файл `test.txt` и сделайте 3 последовательных коммита (`Commit 1`, `Commit 2`, `Commit 3`), добавляя по одной строке в каждый.
2. **Soft Reset:** в **Git → Log** нажмите ПКМ по предпоследнему коммиту (`Commit 2`) → **Reset Current Branch to Here…** → выберите **Soft** → **Reset**.
   - *Результат:* `Commit 3` удален из истории, но его изменения остались в файле и сразу отмечены галочкой во вкладке **Commit** (находятся в `staged`). Повторно закоммитьте их для следующего шага.
3. **Mixed Reset:** снова нажмите ПКМ по `Commit 2` → **Reset Current Branch to Here…** → выберите **Mixed** → **Reset**.
   - *Результат:* `Commit 3` удален из истории, текст остался в файле, но галочка во вкладке **Commit** снята (изменения переведены в `unstaged`). Снова закоммитьте их.
4. **Revert Commit:** нажмите ПКМ по `Commit 2` → **Revert Commit** → подтвердите создание нового коммита `Revert "Commit 2"`.
   - *Результат:* история не перезаписана; поверх `Commit 3` добавился новый коммит, отменяющий правки второго коммита.
5. **Local History:** измените любую строку в `test.txt` и сохраните файл (`Ctrl + S`) **без коммита**. Нажмите ПКМ внутри редактора → **Local History → Show History** → выберите предыдущую ревизию слева → нажмите кнопку **Revert** (фиолетовая стрелка).

### Нюансы из практики
- Если в графе видны два подряд коммита `Revert "commit 3"` на раздвоенной линии — это значит, что один `Revert` был сделан в основной ветке, а второй попал туда после случайного `Cherry-Pick` из ответвления.
- Чтобы убрать лишние тестовые коммиты и вернуть ветку в чистое состояние, используйте **Hard Reset** на нужный базовый коммит.

### CLI-эквивалент
```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git revert --no-edit HEAD
```

- `--soft` — перемещает указатель ветки на указанный коммит, оставляя все изменения в индексе (`staged`).
- `--mixed` — перемещает указатель ветки и сбрасывает индекс (`unstaged`), но сохраняет изменения в рабочей директории (режим по умолчанию).
- `HEAD~1` — ссылка на родительский коммит (на один шаг назад от текущего `HEAD`).
- `--no-edit` — создает коммит отмены `revert` со стандартным сообщением без открытия текстового редактора.

**Пример использования:** `git reset --hard HEAD~2` (полностью удаляет два последних коммита и все незакоммиченные изменения в файлах).

## 3.1.4. Cherry-pick и разрешение конфликтов

### Действия в UI PyCharm
1. **Подготовка:** убедитесь, что вы находитесь в основной ветке (`master` или `main`), а не в `Detached HEAD` (в списке веток выберите `master` → **Checkout**).
2. **Создание ветки от середины истории:** в **Git → Log** пролистайте граф вниз, нажмите ПКМ на старый коммит → **New Branch…** → введите имя `cherry-branch`, отметьте галочку **Checkout branch** → **Create**.
3. **Коммит во второй ветке:** измените строку в файле и сделайте коммит `Feature for cherry-pick`.
4. **Перенос в основную ветку:** переключитесь обратно на `master` (**Checkout**). Найдите в логе коммит `Feature for cherry-pick`, нажмите на него ПКМ → **Cherry-Pick**. Коммит скопируется на вершину `master` с новым хэшем.
5. **Моделирование и разрешение конфликта:**
   - В `master` измените 1-ю строку файла `test.txt` на `Версия master` и закоммитьте.
   - Переключитесь в `cherry-branch`, измените ту же 1-ю строку на `Версия branch` и закоммитьте.
   - Вернитесь в `master`, сделайте **Cherry-Pick** нового коммита из `cherry-branch`.
   - В окне **Conflicts** нажмите **Merge…**. В трехпанельном окне перенесите стрелками (`>>` / `<<`) нужные строки в центральную панель и нажмите **Apply**.

### Нюансы из практики
- **Частая ошибка:** если вместо **New Branch…** нажать **Checkout Revision** на старый коммит и сделать там коммит, вы окажетесь в состоянии `Detached HEAD`. При переключении обратно на `master` такой коммит не будет принадлежать ни одной ветке. Всегда создавайте ветку через **New Branch…**.

### CLI-эквивалент
```bash
git checkout -b cherry-branch <commit_hash>
git checkout main
git cherry-pick -x <new_commit_hash>
```

- `-b <name>` — создает новую ветку от указанного коммита и сразу переключается на нее.
- `-x` — добавляет в описание нового коммита строку `(cherry picked from commit <hash>)` для отслеживания источника.

**Пример использования:** `git cherry-pick --abort` (отменяет начатый `cherry-pick` и возвращает файлы в исходное состояние при сложном конфликте).

## 3.1.5. Squash и Fixup

### Действия в UI PyCharm
1. Создайте ветку `feature-squash` от `master` и сделайте 5 коммитов:
   - `Add login logic`
   - `wip`
   - `try again`
   - `Add profile page`
   - `fix typo`
2. **Squash Commits…:** в **Git → Log** зажмите `Ctrl` и выделите первые три коммита (`Add login logic`, `wip`, `try again`). Нажмите ПКМ → **Squash Commits…**. Удалите мусорные строки из описания, напишите чистое сообщение `Implement login logic` и нажмите **OK**.
3. **Fixup…:** нажмите ПКМ на коммит `Add profile page` → **Interactively Rebase from Here…**. В открывшемся окне выделите коммит `fix typo`, нажмите кнопку **Fixup** (он приклеится снизу к `Add profile page` без сохранения своего сообщения) и нажмите **Start Rebasing**.
4. **Проверка:** в логе останутся только два чистых коммита (`Implement login logic` и `Add profile page`).

### CLI-эквивалент
```bash
git commit --fixup=<target_commit_hash>
git rebase -i --autosquash HEAD~5
```

- `--fixup=<hash>` — создает коммит с префиксом `fixup! <сообщение целевого коммита>`, помечая его для автоматического склеивания.
- `-i` (`--interactive`) — запускает интерактивный режим редактирования списка коммитов.
- `--autosquash` — автоматически перемещает все `fixup!`-коммиты под их целевые коммиты и выставляет им действие `fixup`.

**Пример использования:** `git commit --fixup=HEAD~1 && GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash HEAD~3`

## 3.1.6. Interactive Rebase from Here

### Действия в UI PyCharm
1. Подготовьте в ветке 4–5 коммитов (`Commit A`, `Commit B`, `Commit C (typo)`, `Commit D (extra)`, `Commit E`).
2. В **Git → Log** нажмите ПКМ на коммит **перед** `Commit A` (родительский коммит) → **Interactively Rebase from Here…**.
3. В одном окне настройте все 4 операции (список идет сверху вниз от старых к новым):
   - **Reorder:** перетащите `Commit E` выше `Commit A` (или кнопками **Up / Down**).
   - **Reword:** выделите `Commit C (typo)` → кнопка **Reword** → исправьте текст на `Commit C (fixed)`.
   - **Drop:** выделите `Commit D (extra)` → кнопка **Drop** (корзина / `Delete`).
   - **Squash:** выделите через `Ctrl` два соседних коммита (`Commit A` и `Commit B`) → кнопка **Squash** → задайте общее сообщение `Commit A + B`.
4. Нажмите **Start Rebasing**.

### CLI-эквивалент
```bash
git rebase -i HEAD~5
```

В открывшемся редакторе ключевые слова перед хэшами коммитов означают:
- `pick` — оставить коммит без изменений.
- `reword` — использовать коммит, но изменить его сообщение.
- `squash` — объединить коммит с предыдущим и отредактировать общее сообщение.
- `fixup` — объединить коммит с предыдущим, отбросив его сообщение.
- `drop` — полностью удалить коммит и его изменения из истории.

**Пример использования:** `git rebase --abort` (прерывает интерактивный ребейз и возвращает ветку в состояние до запуска команды).

## 3.1.7. Rebase на актуальный main

### Действия в UI PyCharm
1. Переключитесь на `main` (**Checkout**) и обновите его: верхнее меню **Git → Pull…** (или `Ctrl + T`).
2. Переключитесь обратно на вашу `feature`-ветку (**Checkout**).
3. В списке веток (слева в **Git → Log** или в правом/верхнем виджете веток) нажмите ПКМ на `main` и выберите **Rebase 'feature' onto 'main'**.
4. **Если возникнет конфликт:** в окне **Conflicts** нажмите **Merge…**, разрешите противоречия в центральной панели, нажмите **Apply** — PyCharm автоматически выполнит продолжение ребейза (`git rebase --continue`).

### CLI-эквивалент
```bash
git checkout main
git pull --ff-only
git checkout feature
git rebase main
```

- `--ff-only` — обновляет локальный `main` только если возможна быстрая перемотка (fast-forward) без создания лишних merge-коммитов.

**Пример использования:** `git rebase --continue` (продолжает процесс перебазирования после ручного разрешения конфликта и выполнения `git add`).

## 3.1.8. Checkout revision и работа в detached HEAD

### Действия в UI PyCharm
1. Откройте **Git → Log**, выберите любой старый коммит в середине истории, нажмите по нему ПКМ и выберите **Checkout Revision '<hash>'**.
2. Убедитесь, что в верхней/боковой панели веток вместо имени ветки отображается хэш коммита (состояние `Detached HEAD`).
3. Сделайте тестовое изменение и новый коммит в этом состоянии.
4. **Спасение изменений:** чтобы коммит не пропал при уходе на другую ветку, нажмите ПКМ по текущему коммиту с отметкой `HEAD` в **Git → Log** → **New Branch…** → задайте имя ветки (например, `rescued-work`) → **Create**. Теперь коммит закреплен за полноценной веткой.

### CLI-эквивалент
```bash
git checkout <old_commit_hash>
git switch -c rescued-work
```

- `git checkout <hash>` — переводит рабочую директорию на конкретный коммит в режим `Detached HEAD`.
- `git switch -c <branch_name>` — создает новую ветку прямо из текущего состояния `Detached HEAD` и привязывает к ней все сделанные коммиты.

**Пример использования:** `git reflog` (позволяет найти хэш «потерянного» коммита, если вы вышли из `Detached HEAD` без создания ветки).

## 3.1.9. Управление доставкой изменений (Push / Force Push)

### Действия в UI PyCharm
1. Сделайте 3 локальных коммита в вашей `feature`-ветке.
2. **Частичный Push (`Push All up to Here…`):** в **Git → Log** нажмите ПКМ на **второй** (не самый последний) локальный коммит и выберите **Push All up to Here…** → в окне отправки нажмите **Push**. На удаленный сервер уйдут только первые два коммита, а третий останется локальным.
3. **Моделирование Force Push:**
   - Сделайте `Rebase` или `Squash` для уже отправленных на сервер коммитов (история локальной ветки перепишется и разойдется с `origin/feature`).
   - Нажмите `Ctrl + Shift + K` (**Git → Push…**). Обычный **Push** будет отклонен сервером (`rejected`).
   - В окне Push нажмите на стрелку рядом с кнопкой **Push** и выберите **Force Push** (или **Force with Lease**).
4. **Риски:** переписывание истории с последующим `Force Push` категорически запрещено в общих ветках (`main`, `develop`), так как у других участников команды возникнут жесткие конфликты при попытке сделать `git pull`. Использовать только в личных `feature`-ветках.

### CLI-эквивалент
```bash
git push origin <second_commit_hash>:refs/heads/feature
git push --force-with-lease origin feature
```

- `<hash>:refs/heads/feature` — отправляет в удаленную ветку `feature` все коммиты строго до указанного хэша включительно.
- `--force-with-lease` — безопасный вариант принудительной отправки: перезаписывает ветку на сервере только в том случае, если никто другой не успел запушить туда новые коммиты после вашего последнего `fetch`.

**Пример использования:** `git push -u origin feature --force-with-lease`
