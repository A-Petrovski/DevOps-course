### 1. Основные принципы децентрализованной системы контроля версий Git

В отличие от централизованных систем (SVN, CVS), где история хранится только на одном главном сервере, Git построен по распределенной (DVCS) архитектуре:

* **Полная автономность каждого узла:** При клонировании каждый разработчик получает не просто последние файлы, а полноценный репозиторий со всей историей коммитов, ветками и тегами.
* **Работа в оффлайне:** Создание коммитов, переключение веток, просмотр истории и сравнение версий выполняются локально на диске без обращения к сети.
* **Криптографическая целостность:** Все объекты в Git идентифицируются по 40-символьному SHA-1 (или SHA-256) хешу. Невозможно незаметно изменить старый коммит или файл без изменения его хеша и всех последующих коммитов.
* **Нелинейная разработка:** Ветвление и слияние в Git дешевы и мгновенны, что позволяет десяткам разработчиков параллельно вести изолированные фичи и объединять их в произвольной топологии.

Практический сценарий: Если центральный сервер (GitHub/GitLab) упадет или будет недоступен, любой локальный клон любого разработчика содержит 100% данных для полного восстановления проекта.

### 2. Как Git управляет и хранит версии файлов и историю изменений?

* **Снимки (Snapshots), а не дельты:** Большинство старых СКВ хранят базовый файл и список построчных изменений (дельт) к нему. Git при каждом коммите делает **полный снимок состояния** всех отслеживаемых файлов на текущий момент.
* **Оптимизация хранения:** Если файл не менялся между коммитами, Git не дублирует его, а просто сохраняет ссылку на уже существующий идентичный объект в базе.
* **Направленный ациклический граф (DAG):** История изменений представляет собой граф, где каждый коммит содержит указатель на свой родительский коммит (или несколько родителей при merge-коммите), метаданные автора и ссылку на корневое дерево файлов.

Консольная проверка:
```bash
git cat-file -p HEAD
```
* Разбор флагов: `cat-file` — низкоуровневая команда (plumbing) для чтения внутренних объектов Git; `-p` (`--pretty-print`) красиво форматирует содержимое объекта (покажет `tree`, `parent`, `author`, `committer` и сообщение коммита).

### 3. Внутренняя структура репозитория Git: дерево объектов, индекс и журналы коммитов

Вся служебная информация хранится в скрытой папке `.git` в корне проекта:

1. **База объектов (`.git/objects`):** Хранилище типа «ключ-значение» (ключ — SHA-1 хеш, значение — сжатый zlib-файл). Содержит 4 типа объектов:
   * `blob` (Binary Large Object) — содержимое конкретного файла (без его имени и прав доступа).
   * `tree` — аналог директории: хранит имена файлов, права доступа и ссылки на `blob`-объекты и вложенные `tree`.
   * `commit` — снимок проекта в конкретный момент времени, указывающий на корневой `tree`, родительские коммиты и метаданные.
   * `tag` — аннотированный тег, указывающий на конкретный коммит.
2. **Индекс / Staging Area (`.git/index`):** Бинарный файл, который формирует состав следующего коммита. Является буфером между рабочей директорией (Working Directory) и историей коммитов.
3. **Ссылки и указатели (`.git/refs` и `.git/HEAD`):**
   * Ветки (`.git/refs/heads/*`) — обычные текстовые файлы, содержащие 40-символьный хеш последнего коммита в ветке.
   * `HEAD` (`.git/HEAD`) — указатель на текущую активную ветку (например, `ref: refs/heads/main`) или напрямую на коммит (`detached HEAD`).
4. **Журналы ссылок (`reflog`, `.git/logs`):** Локальный журнал всех перемещений указателя `HEAD` и веток (даже после `reset --hard` или удаления ветки).

Консольные команды и флаги:
```bash
git rev-parse HEAD
git reflog -n 5
```
* `git rev-parse HEAD` — преобразует символическую ссылку `HEAD` в полный SHA-1 хеш коммита.
* `git reflog -n 5` — выводит последние 5 записей локального журнала перемещений `HEAD` (флаг `-n` ограничивает количество строк).

### 4. Основные отличия между GitHub, GitLab и Bitbucket

| Критерий | GitHub | GitLab | Bitbucket |
| :--- | :--- | :--- | :--- |
| **Основной фокус** | Крупнейшее сообщество Open Source, социальное программирование, разработка с ИИ | Единая DevSecOps-платформа полного цикла (от идеи до продакшена в одном приложении) | Корпоративная разработка в связке с экосистемой Atlassian (Jira, Confluence) |
| **Модель развертывания** | Преимущественно SaaS (GitHub.com); Self-hosted только в дорогом Enterprise Server | SaaS (GitLab.com) и полноценный бесплатный Self-hosted (Community Edition) | Преимущественно SaaS (Bitbucket Cloud); Data Center для крупных корпораций |
| **Встроенный CI/CD** | GitHub Actions (огромный маркетплейс готовых экшенов) | GitLab CI/CD (эталонная интеграция, Auto DevOps, встроенные раннеры и аналитика) | Bitbucket Pipelines (конфигурация в YAML, тесная связь со статусами задач Jira) |
| **Приватные репозитории (Free)** | Безлимитно для любого числа участников | До 5 участников в группе на бесплатном облачном тарифе | До 5 участников в команде на бесплатном тарифе |
| **Терминология ревью кода** | Pull Request (PR) | Merge Request (MR) | Pull Request (PR) |

### 5. Дополнительные функции и инструменты платформ

* **GitHub:**
  * **GitHub Actions:** мощный движок автоматизации событий репозитория и CI/CD.
  * **GitHub Copilot:** встроенный ИИ-ассистент для генерации и ревью кода.
  * **GitHub Codespaces:** облачные среды разработки (VS Code в браузере на базе контейнеров).
  * **GitHub Packages & Pages:** реестр пакетов/контейнеров и бесплатный хостинг статических сайтов.
  * **Dependabot:** автоматическое сканирование зависимостей на уязвимости и создание PR с обновлениями.
* **GitLab:**
  * **Встроенный Container & Package Registry:** готовый реестр Docker-образов, npm, Maven, PyPI из коробки в каждом проекте.
  * **Инструменты безопасности (DevSecOps):** встроенные SAST, DAST, Dependency Scanning и Secret Detection прямо в пайплайнах.
  * **Интеграция с Kubernetes и Terraform:** встроенное управление агентами Kubernetes, хранение tfstate-файлов инфраструктуры.
  * **Иерархия групп и подгрупп:** гибкая ролевая модель доступа для больших организаций.
* **Bitbucket:**
  * **Глубокая интеграция с Jira и Trello:** автоматический переход статусов задач в Jira при создании ветки, коммита или Pull Request.
  * **Smart Mirroring:** геораспределенное зеркалирование репозиториев для ускорения клонирования в удаленных офисах.
  * **Deployments Dashboard:** визуальное отслеживание, какая версия кода и какая задача Jira сейчас развернуты в окружениях (`dev`, `stage`, `prod`).

### 6. Как выбрать подходящий Git-хостинг для проекта или команды?

Выбор зависит от архитектурных, бюджетных и организационных требований:

1. **Выбирайте GitHub, если:**
   * Проект развивается как **Open Source** или нужно привлекать внешних контрибьюторов.
   * Важна максимальная скорость старта, простота интерфейса и доступ к тысячам готовых интеграций в Marketplace.
   * Команда активно использует GitHub Copilot и облачный SaaS.
2. **Выбирайте GitLab, если:**
   * По требованиям безопасности (ИБ) код и CI/CD должны размещаться на **собственных серверах (On-Premise / Self-hosted)** без привязки к внешнему облаку.
   * Нужен единый комбайн «все в одном» (Git + мощный CI/CD + Docker Registry + Terraform state + сканеры безопасности) без необходимости интегрировать 5 разных сервисов.
   * В компании сложная структура отделов (иерархия групп и подгрупп).
3. **Выбирайте Bitbucket, если:**
   * Вся компания уже живет в экосистеме **Atlassian** (Jira, Confluence, Bamboo) и критически важна бесшовная трассируемость от тикета в Jira до деплоя.
   * Команда небольшая (до 5 человек) и работает над закрытыми коммерческими проектами.

### 7. Общепринятые рекомендации и соглашения по оформлению коммит-сообщений

Хороший коммит-лог читается как документация проекта и помогает быстро находить причины багов (`git bisect`, `git blame`).

* **Повелительное наклонение (Imperative mood):** Пишите заголовок так, как будто он продолжает фразу *«Если применить этот коммит, он...»* — `Add nginx config`, `Fix memory leak`, но не `Added` или `Fixes`.
* **Ограничение длины строки:** Заголовок (первая строка) должен укладываться в **50–72 символа**, чтобы он не обрезался в веб-интерфейсе и при выводе `git log --oneline`.
* **Без точки в конце заголовка:** Точка в первой строке считается лишним символом.
* **Отделение тела коммита пустой строкой:** Если нужно объяснить **почему** и **зачем** сделаны изменения (а не *как* — это видно из diff), оставьте одну пустую строку после заголовка и опишите детали.
* **Ссылки на задачи:** В нижней части (футере) указывайте номера тикетов (например, `Refs: DEVOPS-104` или `Closes #42`).

Пример оформления многострочного коммита в консоли:
```bash
git commit -m "fix(nginx): increase worker_connections limit" -m "Prevents 502 errors under peak load of 1000+ concurrent clients."
```
* Разбор: первый флаг `-m` задает заголовок, второй флаг `-m` автоматически добавляет пустую строку и формирует тело (body) коммита.

### 8. Конвенция коммит-сообщений (Conventional Commits)

**Conventional Commits** — стандарт структурирования сообщений коммитов, который делает историю машиночитаемой (позволяет автоматически генерировать `CHANGELOG.md` и вычислять следующую версию по SemVer).

#### Формат записи
```text
<тип>[необязательный контекст (scope)]: <описание>

[необязательное тело (body)]

[необязательный футер (footer)]
```

#### Основные типы коммитов
* `feat:` — добавление новой функциональности или нового конфигурационного файла (повышает `MINOR` версию).
* `fix:` — исправление ошибки или бага (повышает `PATCH` версию).
* `docs:` — изменения только в документации (`README.md`, комментарии, гайды).
* `style:` — форматирование кода, отступы, пробелы без изменения логики работы.
* `refactor:` — переработка структуры кода/конфига без добавления новых функций и исправления багов.
* `perf:` — изменения, направленные на повышение производительности.
* `test:` — добавление или исправление тестов.
* `build:` — изменения, влияющие на систему сборки или внешние зависимости (Docker, Maven, npm).
* `ci:` — настройка файлов и скриптов CI/CD (`.gitlab-ci.yml`, `.github/workflows/*`).
* `chore:` — рутинные технические задачи, обновление `.gitignore`, обслуживание репозитория.
* `revert:` — откат предыдущего коммита.
* `!` после типа (например, `feat!: drop support for TLS 1.1`) или `BREAKING CHANGE:` в футере — указывает на критическое изменение, ломающее обратную совместимость (повышает `MAJOR` версию).

Пример использования: `git log --grep="^feat" --oneline` — фильтрует историю и показывает только те коммиты, в которых добавлялась новая функциональность.

### 9. Как правильно разделять изменения на отдельные коммиты и описывать их?

Главное правило профессиональной работы с Git — **атомарность коммитов**: один коммит решает ровно одну логическую задачу.

* **Принцип «одна задача — один коммит»:** Не смешивайте в одном коммите добавление нового конфига, исправление опечатки в `README.md` и форматирование старых файлов. Если изменение придется откатить (`git revert`), откат затронет только одну конкретную фичу, а не поломает соседний функционал.
* **Частичное добавление изменений в индекс (`git add -p`):** Если вы успели поправить в одном файле сразу две разные вещи, не добавляйте файл целиком. Разбейте изменения на отдельные фрагменты (hunks).
* **Работоспособность на каждом шаге:** После каждого коммита проект или конфигурация должны оставаться в валидном состоянии (например, конфиг Nginx должен проходить проверку синтаксиса `nginx -t`).

Консольные команды для разделения изменений:
```bash
git add -p nginx.conf
git diff --staged
```
* `git add -p <файл>` (`--patch`) — запускает интерактивный режим, позволяющий выбрать конкретные блоки измененных строк (`y` — добавить в индекс, `n` — пропустить, `s` — разбить блок на более мелкие части).
* `git diff --staged` (или `--cached`) — показывает точные построчные изменения, которые уже добавлены в индекс и попадут в следующий коммит.

Пример использования: `git reset -p` — позволяет интерактивно убрать отдельные фрагменты изменений из индекса обратно в рабочую директорию, если вы случайно добавили лишний блок кода через `git add`.
