## Часть 1. Практический блок (Разбор чекпоинтов)

### Чекпоинт 1. Установка, настройка Git, инициализация репозитория и базовый конфиг Nginx

#### Рабочие команды и конфигурация
```bash
sudo apt update && sudo apt install git -y
git config --global user.name "Alexander Petrovsky"
git config --global user.email "apetrovsky@example.com"

mkdir devops-task1 && cd devops-task1
git init -b main
cp /etc/nginx/nginx.conf ./nginx.conf
```

Если пакет `nginx` не установлен в системе, создайте `nginx.conf` со стандартным содержимым Debian/Ubuntu:
```nginx
user www-data;
worker_processes auto;
pid /run/nginx.pid;
error_log /var/log/nginx/error.log;
include /etc/nginx/modules-enabled/*.conf;

events {
    worker_connections 768;
}

http {
    sendfile on;
    tcp_nopush on;
    types_hash_max_size 2048;

    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers on;

    access_log /var/log/nginx/access.log;
    gzip on;

    include /etc/nginx/conf.d/*.conf;
    include /etc/nginx/sites-enabled/*;
}
```

#### Разбор флагов и параметров
* `apt update` — обновляет локальный индекс пакетов из репозиториев ОС.
* `apt install git -y` — устанавливает консольный клиент Git; флаг `-y` (`--yes`) автоматически подтверждает установку без интерактивного запроса.
* `git config --global` — записывает настройки в глобальный конфигурационный файл пользователя (`~/.gitconfig`), применяя их ко всем репозиториям текущего пользователя.
* `user.name` / `user.email` — обязательные метаданные автора, которые вшиваются в каждый создаваемый коммит.
* `mkdir devops-task1 && cd devops-task1` — создает каталог проекта и сразу переходит в него при успешном создании (`&&`).
* `git init -b main` — инициализирует новый пустой Git-репозиторий (создает скрытую служебную директорию `.git`); флаг `-b main` (`--initial-branch`) задает имя основной ветки `main` вместо устаревшего `master`.
* `cp /etc/nginx/nginx.conf ./nginx.conf` — копирует базовый конфигурационный файл веб-сервера Nginx в корень текущего репозитория.

Пример использования: `git config --list --show-origin` — проверяет все активные настройки Git и показывает пути к файлам конфигурации, откуда они загружены.

### Чекпоинт 2. Создание README.md и поэтапная фиксация файлов (коммиты)

#### Рабочие команды
```bash
echo "В данном репозитории находится дефолтный конфигурационный файл nginx" > README.md

git add README.md
git commit -m "docs: add README.md with repository description"

git add nginx.conf
git commit -m "feat: add default nginx.conf configuration"
```

#### Разбор флагов и параметров
* `echo "..." > README.md` — создает файл `README.md` и записывает в него указанную строку (оператор `>` перезаписывает файл, если он уже существовал).
* `git add <файл>` — переносит изменения указанного файла из рабочей директории (Working Directory) в область подготовленных файлов — индекс (Staging Area).
* `git commit -m "<сообщение>"` — фиксирует состояние индекса в истории репозитория в виде нового коммита; флаг `-m` (`--message`) позволяет передать текст описания коммита прямо из командной строки без открытия текстового редактора.

Пример использования: `git commit --amend -m "docs: update README description"` — перезаписывает последний локальный коммит, если вы допустили опечатку в сообщении или забыли добавить мелкую правку.

### Чекпоинт 3. Проверка истории коммитов и состояния рабочей директории

#### Рабочие команды
```bash
git log --oneline --graph --decorate
git status
```

#### Разбор флагов и параметров
* `git log` — выводит хронологический журнал коммитов текущей ветки (от новых к старым).
* `--oneline` — сжимает вывод каждого коммита до одной строки (сокращенный SHA-1 хеш + заголовок сообщения).
* `--graph` — рисует текстовый ASCII-граф ветвлений и слияний слева от списка коммитов.
* `--decorate` — отображает указатели веток (`main`), тегов и `HEAD` рядом с соответствующими коммитами.
* `git status` — показывает состояние рабочей директории и индекса: неотслеживаемые файлы, измененные файлы и готовность к коммиту (ожидаемый результат: `nothing to commit, working tree clean`).

Пример использования: `git status -s` — выводит состояние файлов в компактном двухколоночном формате (удобно при большом количестве измененных файлов).

### Чекпоинт 4. Регистрация и создание репозиториев на GitHub и GitLab

#### Рабочие инструкции и нюансы конфигурации
1. Создайте учетные записи на [GitHub](https://github.com/) и [GitLab](https://gitlab.com/).
2. На каждой платформе создайте новый репозиторий с именем `devops-task1`:
   * **GitHub:** `New repository` → Repository name: `devops-task1` → Visibility: **Public** → не отмечать `Add a README file` и `.gitignore` → `Create repository`.
   * **GitLab:** `New project` → `Create blank project` → Project name: `devops-task1` → Visibility Level: **Public** → снять галочку `Initialize repository with a README` → `Create project`.
3. **Важный нюанс GitLab:** Если проект создается внутри группы (Group), уровень видимости проекта не может быть выше уровня видимости родительской группы. Чтобы проект стал `Public`, либо сама группа должна иметь статус `Public`, либо проект необходимо создавать/перенести в личное пространство пользователя (*Personal namespace*).

#### Разбор параметров
* **Public** — уровень видимости, при котором любой пользователь интернета может просматривать код и клонировать репозиторий без аутентификации, но изменять код могут только участники с соответствующими правами.
* **Empty / Blank repository (без README)** — предотвращает создание начального коммита на сервере, чтобы локальная история из 2 коммитов загрузилась без конфликтов.

Пример использования: `curl -I https://github.com/<username>/devops-task1` — быстрая проверка доступности страницы репозитория из консоли (код ответа `HTTP/2 200` подтверждает, что репозиторий существует и открыт публично).

### Чекпоинт 5. Подключение двух удаленных серверов и отправка изменений

#### Рабочие команды
```bash
git remote add github https://github.com/<username>/devops-task1.git
git remote add gitlab https://gitlab.com/<username>/devops-task1.git

git remote -v

git push -u github main
git push -u gitlab main
```

#### Разбор флагов и параметров
* `git remote add <имя> <URL>` — регистрирует новый удаленный сервер под локальным псевдонимом (`github` и `gitlab` вместо стандартного `origin`). Синтаксис строго требует два аргумента: псевдоним и адрес.
* `git remote -v` (`--verbose`) — выводит список всех привязанных удаленных репозиториев с их URL для скачивания (`fetch`) и отправки (`push`).
* `git push` — отправляет локальные коммиты на удаленный сервер.
* `-u` (`--set-upstream`) — связывает локальную ветку `main` с удаленной веткой `main`, чтобы в будущем можно было выполнять `git push` и `git pull` без указания имени сервера и ветки.
* `--force` (используется только при необходимости перезаписать пустой/шаблонный коммит в новом репозитории, например `git push -u gitlab main --force`) — принудительно перезаписывает удаленную ветку локальной историей. В GitLab для этого может потребоваться снять защиту ветки (`Settings → Repository → Protected branches → Unprotect`).

Пример использования: `git remote set-url gitlab git@gitlab.com:<username>/devops-task1.git` — переключает протокол подключения уже добавленного сервера с HTTPS на SSH без удаления привязки.

### Чекпоинт 6. Клонирование репозитория, переход к старому коммиту и просмотр файла

#### Рабочие команды
```bash
cd ..
git clone <URL_репозитория_с_заданием> cloned-repo
cd cloned-repo

git log --reverse --oneline
git checkout e8b3ec06b
cat deleted.txt
```

#### Разбор флагов и параметров
* `git clone <URL> [директория]` — скачивает полную копию удаленного репозитория со всей историей коммитов, ветками и тегами в новую папку.
* `git log --reverse` — выводит историю коммитов в хронологическом порядке (от самого первого коммита к последнему), что упрощает поиск 3-го коммита от начала.
* `git checkout <хеш_коммита>` — переключает рабочую директорию на точное состояние файлов, зафиксированное в коммите `e8b3ec06b`. Репозиторий переходит в состояние `detached HEAD` (указатель `HEAD` ссылается напрямую на коммит, а не на ветку).
* `cat deleted.txt` — выводит содержимое файла `deleted.txt` в стандартный поток вывода (терминал).

Пример использования: `git show e8b3ec06b:deleted.txt` — позволяет просмотреть содержимое файла `deleted.txt` из конкретного коммита без переключения рабочей директории (`checkout`).

### Чекпоинт 7. Проверка публичности созданных репозиториев

#### Рабочие команды и способы проверки
```bash
git ls-remote https://github.com/<username>/devops-task1.git
git ls-remote https://gitlab.com/<username>/devops-task1.git
```

#### Разбор флагов и параметров
* `git ls-remote <URL>` — запрашивает список ссылок (веток и тегов) напрямую у удаленного репозитория по сети без его полного клонирования.
* Если команда выполняется в чистом окружении (без сохраненных токенов/SSH-ключей) и возвращает хеши коммитов (`refs/heads/main`) без запроса логина и пароля — репозиторий гарантированно является публичным. Также проверку можно выполнить открытием URL обоих репозиториев в режиме инкогнито браузера.

Пример использования: `GIT_TERMINAL_PROMPT=0 git ls-remote https://gitlab.com/<username>/devops-task1.git` — отключает интерактивный запрос пароля в терминале; если репозиторий приватный, команда сразу завершится с ошибкой аутентификации.
