## 1. Принципы децентрализованной системы контроля версий (DVCS)
* **Полная автономность:** Каждый разработчик хранит на локальной машине полную копию репозитория со всей историей изменений, ветками и тегами.
* **Работа в оффлайне:** Создание коммитов, просмотр истории (`git log`), переключение веток (`git checkout` / `git switch`) не требуют подключения к сети.
* **Отказоустойчивость:** Если центральный сервер выйдет из строя, любой локальный клон репозитория может быть использован для полного восстановления проекта.
* **Гибкость синхронизации:** Репозиторий может быть привязан сразу к нескольким удалённым серверам (`remote`), например, одновременно к GitHub и GitLab.

## 2. Как Git управляет версиями и хранит историю
* **Модель снимков (Snapshots):** В отличие от старых систем (SVN, CVS), которые хранят список изменений (дельт) для каждого файла, Git при каждом коммите делает «снимок» состояния всех файлов проекта. Если файл не менялся, Git не дублирует его, а сохраняет ссылку на предыдущую идентичную версию.
* **Целостность данных (SHA-1):** Любой объект в Git (файл, папка, коммит) хешируется по алгоритму SHA-1 (40-символьная строка). Изменить содержимое файла или историю задним числом без изменения хеша невозможно.
* **Три состояния файлов:**
  1. **Working Directory (Рабочая директория):** Файлы, с которыми вы работаете прямо сейчас на диске.
  2. **Staging Area / Index (Индекс):** Область подготовленных изменений, которые войдут в следующий коммит (`git add`).
  3. **Git Directory (Репозиторий):** База данных в скрытой папке `.git`, где зафиксированы все снимки (`git commit`).

## 3. Внутренняя структура репозитория (.git)
При выполнении `git init` создаётся скрытая директория `.git`, содержащая всю механику контроля версий:
* `objects/` — база данных всех объектов репозитория:
  * **Blob:** Содержимое конкретного файла (без имени и прав доступа).
  * **Tree:** Аналог директории, связывающий имена файлов с их `blob`-хешами и вложенными `tree`.
  * **Commit:** Объект, содержащий ссылку на корневой `tree`, хеш родительского коммита, автора, время и сообщение.
* `refs/` — указатели на коммиты: ветки (`refs/heads/`), теги (`refs/tags/`) и удалённые ветки (`refs/remotes/`).
* `HEAD` — текстовый файл-указатель на текущую активную ветку (например, `ref: refs/heads/main`) или на конкретный хеш коммита (состояние *detached HEAD*).
* `index` — бинарный файл, представляющий собой *Staging Area* (буфер перед коммитом).
* `logs/` — локальный журнал перемещений `HEAD` и веток (используется командой `git reflog` для восстановления потерянных коммитов).

## 4. Сравнение Git-хостингов: GitHub, GitLab и Bitbucket

| Критерий | GitHub | GitLab | Bitbucket |
| :--- | :--- | :--- | :--- |
| **Основной фокус** | Крупнейшее open-source сообщество, стандартизация разработки | Единая DevSecOps-платформа «всё в одном» | Тесная интеграция с экосистемой Atlassian (Jira, Confluence) |
| **Встроенный CI/CD** | GitHub Actions (богатый маркетплейс готовых экшенов) | GitLab CI/CD (мощные пайплайны в `.gitlab-ci.yml`, встроенный Container Registry) | Bitbucket Pipelines |
| **Self-hosted версия** | GitHub Enterprise (платно) | GitLab Community Edition (бесплатно) / Enterprise | Bitbucket Data Center |
| **Приватные репозитории** | Бесплатно без ограничений | Бесплатно (ограничение до 5 пользователей в группе на Free-тарифе) | Бесплатно (до 5 пользователей в команде) |

**Как выбрать хостинг:**
* Для портфолио, пет-проектов и поиска готовых open-source решений — **GitHub**.
* Для построения полного цикла DevOps/DevSecOps, работы с Kubernetes, Docker Registry и развёртывания на собственном сервере — **GitLab**.
* Если в компании задачи уже ведутся в Jira, а документация в Confluence — **Bitbucket**.

## 5. Правила и конвенции оформления коммитов
**Базовые правила хорошего коммита:**
1. **Атомарность:** Один коммит решает одну логическую задачу (не смешивайте правку конфига Nginx и обновление README в одном коммите).
2. **Повелительное наклонение:** Пишите «что сделает этот коммит», а не «что я сделал» (например, `Add nginx config`, а не `Added nginx config`).
3. **Длина заголовка:** Первая строка не должна превышать 50–72 символов, без точки в конце.

**Стандарт Conventional Commits (`тип(область): описание`):**
Позволяет автоматически генерировать списки изменений (CHANGELOG) и запускать нужные этапы CI/CD.
* `feat:` — добавление нового функционала (`feat(auth): add ssh key verification`).
* `fix:` — исправление бага (`fix(nginx): resolve 502 bad gateway timeout`).
* `docs:` — изменение только документации (`docs: update README with setup steps`).
* `chore:` — рутинные задачи, обновление зависимостей, настройка инструментов (`chore: configure gitignore`).
* `refactor:` — правка кода/конфигов без изменения функциональности и исправления багов.
* `ci:` — изменение конфигураций CI/CD (`ci: add gitlab pipeline for docker build`).

**Полезные команды для работы с историей и инспекции:**
```bash
git log --oneline --graph --all
git show <commit_hash>
git diff --staged
```
* `--oneline` — выводит каждый коммит в одну строку (сокращённый хеш + заголовок).
* `--graph` — рисует текстовый граф ветвлений и слияний.
* `--all` — показывает историю по всем веткам, а не только по текущей.
* `--staged` — показывает разницу между последним коммитом и файлами, уже добавленными в индекс (`git add`).
