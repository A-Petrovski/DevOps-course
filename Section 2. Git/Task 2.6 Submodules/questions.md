# Контрольные вопросы для самопроверки (Task 2.6 Submodules)

### 1. Что такое сабмодули в Git и как они позволяют интегрировать другие репозитории в основной репозиторий?
**Ответ:**
Сабмодуль в Git — это механизм, позволяющий встроить один самостоятельный Git-репозиторий внутрь подкаталога другого (родительского) репозитория. Технически основной репозиторий не хранит внутри себя файлы сабмодуля — он сохраняет лишь конфигурационный файл `.gitmodules` (с URL и путём) и специальную запись в индексе (gitlink), которая указывает на конкретный хеш коммита внешнего репозитория в определённый момент времени.

**Пример из практики:**
```bash
# Подключение внешней библиотеки или CMS в подкаталог проекта
git submodule add https://github.com wordpress
```

### 2. Как обновлять сабмодули, следить за изменениями в их истории и переключаться между версиями сабмодулей?
**Ответ:**
Сабмодуль является полноценным локальным репозиторием, поэтому управление его историей происходит внутри его собственной директории с помощью стандартных команд `git fetch`, `git log`, `git tag` и `git checkout`. После переключения сабмодуля на нужную ветку, тег или коммит необходимо вернуться в корень основного репозитория и зафиксировать новый указатель (хеш коммита) отдельным коммитом. Для массового обновления всех сабмодулей до последних версий их отслеживаемых веток используется команда `git submodule update --remote`.

**Пример из практики:**
```bash
# Ручное переключение версии внутри сабмодуля и фиксация в основном проекте
cd wordpress
git fetch --all --tags
git checkout 6.4.3
cd ..
git add wordpress
git commit -m "Update WordPress submodule to 6.4.3"
```

### 3. Какие преимущества и рекомендации связаны с использованием сабмодулей для управления внешними зависимостями?
**Ответ:**
* **Преимущества:**
  * Изоляция истории коммитов: изменения во внешнем коде не засоряют историю основного проекта.
  * Детерминированность сборок: каждый разработчик и CI/CD-пайплайн при клонировании получают строго зафиксированную версию зависимости.
  * Отказ от антипаттерна «скачать-вставить» (vendoring), упрощающий отслеживание изменений и обновление зависимостей.
* **Рекомендации:**
  * При клонировании проекта с сабмодулями всегда использовать флаг `--recurse-submodules` (или выполнять `git submodule update --init --recursive` после обычного `git clone`).
  * Перед отправкой (`push`) основного репозитория убеждаться, что все локальные изменения внутри сабмодулей (если они делались) также отправлены в их удалённые репозитории, иначе коллеги не смогут скачать указанный коммит.

**Пример из практики:**
```bash
# Инициализация и загрузка сабмодулей в уже склонированном проекте
git submodule update --init --recursive
```

### 4. Почему важно иметь строгое управление версиями внешних зависимостей в проекте?
**Ответ:**
Внешние библиотеки, фреймворки и CMS развиваются независимо от вашего кода: в новых версиях могут меняться сигнатуры функций, удаляться устаревшие методы (breaking changes) или появляться новые баги. Строгая фиксация версий гарантирует, что обновление внешнего компонента не сломает ваш проект неожиданно, обеспечивает воспроизводимость среды разработки и продакшена (принцип *Infrastructure/Code as Code*), а также позволяет безопасно тестировать переходы на новые релизы и мгновенно откатываться назад в случае сбоев.

**Пример из практики:**
```bash
# Проверка зафиксированного хеша коммита сабмодуля в основном репозитории
git submodule status
```
