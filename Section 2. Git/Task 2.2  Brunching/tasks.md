## Чекпоинт 1: Создание веток develop и feature/new-site

**Задание:** В репозитории `devops-task1`, загруженном на хостинг в предыдущем задании, создай с помощью `git checkout` и `git branch` две новые ветки: `develop` и `feature/new-site`.

```bash
cd devops-task1
git branch develop
git checkout -b feature/new-site
git branch
```

* `git branch develop` — создает новую ветку `develop` от текущего коммита, но оставляет пользователя в текущей ветке.
* `git checkout -b feature/new-site` — команда-комбинация: создает новую ветку `feature/new-site` (флаг `-b` от *branch*) и сразу переключает рабочую директорию на неё.
* `git branch` — выводит список всех локальных веток и отмечает текущую активную ветку символом `*` и цветом.

> **Важный нюанс:** Обе ветки нужно создавать от актуальной основной ветки (`main` или `master`). Если создать `feature/new-site` уже находясь внутри `develop`, она унаследует историю `develop`, а не основной ветки.

**Пример использования:** `git switch -c hotfix/urgent-bug` (современный аналог `git checkout -b` для быстрого создания ветки и перехода в неё).

## Чекпоинт 2: Настройка nginx.conf в ветке develop

**Задание:** В ветке `develop` измени настройки в `nginx.conf`: замени `worker_connections` на `16384` и закоммить изменения. Затем в ветке `develop` измени `nginx.conf`, включи сжатие ответа для типа `application/json` и закоммить изменения.

```bash
git checkout develop

# Шаг 1: Изменение worker_connections
sed -i 's/worker_connections [0-9]*;/worker_connections 16384;/' nginx.conf
git add nginx.conf
git commit -m "Set worker_connections to 16384"

# Шаг 2: Включение gzip для application/json
# В блоке http { ... } файла nginx.conf раскомментируем и дополняем директиву:
```

Фрагмент блока `http` в файле `nginx.conf`:
```nginx
http {
    ...
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml application/xml application/xml+rss text/javascript;
    ...
}
```

Фиксация второго коммита:
```bash
git add nginx.conf
git commit -m "Enable gzip compression for application/json"
```

* `git checkout develop` — переключает рабочую директорию на ветку `develop`.
* `sed -i` — редактирует файл «на лету» без открытия текстового редактора (флаг `-i` перезаписывает исходный файл).
* `gzip on;` — активирует модуль сжатия ответов в Nginx.
* `gzip_types ...;` — перечисляет MIME-типы файлов, которые сервер будет сжимать перед отправкой клиенту (по умолчанию сжимается только `text/html`).
* `git add nginx.conf` — добавляет измененный файл в индекс (staging area) для подготовки к коммиту.
* `git commit -m "..."` — фиксирует изменения в истории ветки с указанным сообщением (флаг `-m` от *message*).

> **Сложные моменты и частые ошибки:**
> 1. **Несохраненный файл в IDE:** При редактировании в VS Code убедитесь, что белая точка на вкладке `nginx.conf` исчезла (нажмите `Ctrl + S`) до выполнения `git add`, иначе в коммит попадет старая версия файла.
> 2. **Синтаксис Nginx:** Каждая директива в `nginx.conf` обязана заканчиваться точкой с запятой `;`. Пропуск `;` в конце строки `gzip_types` приведет к ошибке запуска Nginx.

**Пример использования:** `git diff nginx.conf` (позволяет построчно проверить внесенные изменения в файле перед выполнением `git add`).

## Чекпоинт 3: Конфигурация статического сайта в ветке feature/new-site

**Задание:** В ветке `feature/new-site` добавь файл `conf.d/mysite.domain.com.conf` с базовым описанием статического сайта и закоммить изменения.

```bash
git checkout feature/new-site
mkdir -p conf.d
cat << 'EOF' > conf.d/mysite.domain.com.conf
server {
    listen 80;
    server_name mysite.domain.com;

    root /var/www/mysite.domain.com;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}
EOF

git add conf.d/mysite.domain.com.conf
git commit -m "Add static site config for mysite.domain.com"
```

* `mkdir -p conf.d` — создает директорию `conf.d` (флаг `-p` предотвращает ошибку, если папка уже существует, и создает промежуточные каталоги при необходимости).
* `listen 80;` — указывает Nginx принимать HTTP-соединения на 80-м порту.
* `server_name mysite.domain.com;` — задает доменное имя виртуального хоста.
* `root /var/www/mysite.domain.com;` — определяет корневую директорию на сервере, откуда будут отдаваться файлы сайта.
* `try_files $uri $uri/ =404;` — проверяет существование запрошенного файла, затем директории, и возвращает код `404`, если ресурс не найден.

**Пример использования:** `git status -s` (выводит компактный статус файлов в репозитории, где `??` означает новый неотслеживаемый файл, а `A` — добавленный в индекс).

## Чекпоинт 4: Добавление легковесного тега v0.1

**Задание:** Добавь легковесный тег `v0.1` на последний коммит в ветке `develop` (где изменял `nginx.conf`).

```bash
git checkout develop
git log -n 2 --oneline
git tag v0.1
git show v0.1
```

* `git log -n 2 --oneline` — выводит 2 последних коммита в компактном виде (короткий хеш + заголовок), чтобы убедиться, что `HEAD` указывает именно на коммит с изменением `nginx.conf`.
* `git tag v0.1` — создает **легковесный (lightweight) тег** с именем `v0.1`, который является простым указателем на текущий коммит (без флага `-a`, который создает аннотированный тег).
* `git show v0.1` — отображает информацию о коммите, на который ссылается тег `v0.1`, и список изменений в нём.

> **Важный нюанс:** Если после нужного коммита в ветке уже были сделаны другие коммиты, тег можно повесить по конкретному хешу: `git tag v0.1 <хеш_коммита>`.

**Пример использования:** `git tag -l "v0.*"` (поиск и фильтрация существующих тегов по шаблону).

## Чекпоинт 5: Настройка .gitignore и проверка папки tmp

**Задание:** Добавь файл `.gitignore` в ветку `feature/new-site`. Файл `.gitignore` должен быть составлен таким образом, чтобы исключать из репозитория папку `tmp` и всё её содержимое. Создай локально папку `tmp` с несколькими файлами в ней, закоммить изменения.

```bash
git checkout feature/new-site
echo "tmp/" > .gitignore
mkdir -p tmp
touch tmp/file1.txt tmp/file2.txt tmp/file3.txt

git status
git add .gitignore
git commit -m "Add .gitignore to exclude tmp directory"
```

* `echo "tmp/" > .gitignore` — создает файл `.gitignore` в корне репозитория и записывает в него шаблон `tmp/`. Завершающий слэш `/` указывает Git, что игнорировать нужно именно директорию `tmp` и всё её содержимое.
* `touch tmp/file1.txt tmp/file2.txt tmp/file3.txt` — создает три пустых тестовых файла внутри локальной директории `tmp`.
* `git status` — проверяет, что папка `tmp/` и файлы внутри неё не отображаются в списке `Untracked files`, а для добавления доступен только `.gitignore`.

> **Сложный момент:** Если папка `tmp` или файлы внутри неё были добавлены в индекс Git (`git add`) **до** создания `.gitignore`, правило игнорирования на них не сработает. В таком случае их нужно удалить из индекса командой `git rm -r --cached tmp/`.

**Пример использования:** `git check-ignore -v tmp/file1.txt` (показывает, какое именно правило и из какого файла `.gitignore` блокирует отслеживание указанного файла).

## Чекпоинт 6: Отправка веток и тега в GitLab и финальная проверка

**Задание:** Загрузи обе ветки на GitLab. Загрузи тег на хостинг с помощью `git push` и проверь его наличие. Присутствует ли директория `tmp` в ветке `feature/new-site`?

```bash
# 1. Проверяем имена подключенных удаленных репозиториев (так как подключены и GitHub, и GitLab)
git remote -v

# 2. Отправляем обе ветки в репозиторий GitLab (предположим, его имя — gitlab)
git push -u gitlab develop feature/new-site

# 3. Отправляем тег v0.1 в GitLab
git push gitlab v0.1

# 4. Проверяем наличие тега на удаленном сервере
git ls-remote --tags gitlab
```

* `git remote -v` — выводит список всех привязанных удаленных репозиториев с их псевдонимами (например, `origin` для GitHub и `gitlab` для GitLab) и URL-адресами.
* `git push -u gitlab develop feature/new-site` — отправляет обе указанные локальные ветки в удаленный репозиторий `gitlab`. Флаг `-u` (`--set-upstream`) связывает локальные ветки с удаленными для последующего использования короткой команды `git push`.
* `git push gitlab v0.1` — отправляет конкретный тег на сервер (по умолчанию `git push` не отправляет теги).
* `git ls-remote --tags gitlab` — запрашивает с удаленного сервера список всех опубликованных тегов для проверки, что `refs/tags/v0.1` успешно загружен.

> **Ответ на контрольный вопрос чекпоинта:**
> **Нет, директория `tmp` отсутствует в удаленной ветке `feature/new-site` на GitLab.** Она существует только локально на вашем компьютере, так как правило `tmp/` в файле `.gitignore` запрещает Git индексировать эту папку и отправлять её в удаленный репозиторий.

**Пример использования:** `git push --all gitlab && git push --tags gitlab` (отправка разом всех локальных веток и всех тегов в указанный удаленный репозиторий).
