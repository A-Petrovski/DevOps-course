# Вопросы для самоконтроля: Task 2.2 Бранчевание

## 1. Что такое коммит в системе контроля версий Git и какие данные он содержит?

**Коммит (commit)** — это снимок (snapshot) состояния всех отслеживаемых файлов проекта на конкретный момент времени. В отличие от многих других систем контроля версий, Git хранит не список построчных отличий (дельт) между версиями, а полноценный слепок файловой структуры проекта (если файл не менялся, Git просто сохраняет ссылку на его предыдущую версию).

Каждый объект коммита в Git содержит следующие данные:
* **Указатель на корневое дерево (tree)** — снимок директорий и файлов (blob-объектов), актуальных на момент фиксации.
* **Указатель на родительский коммит (parent)** — хеш предыдущего коммита (у самого первого коммита в репозитории родителя нет, у коммита слияния — два и более).
* **Метаданные автора и коммиттера** — имя, email и точная временная метка (timestamp) создания изменения.
* **Сообщение коммита (commit message)** — текстовое описание сути внесённых изменений.

```bash
# Посмотреть внутреннее содержимое и структуру конкретного коммита
git cat-file -p HEAD
```

## 2. Каким образом Git создает идентификаторы (хэши) для каждого коммита?

Для идентификации коммитов Git использует криптографическую хеш-функцию **SHA-1** (в современных версиях Git также добавлена экспериментальная поддержка **SHA-256**).

Хеш представляет собой 40-значное шестнадцатеричное число (например, `a1b2c3d4e5f6...`). Git вычисляет его на основе **всего содержимого коммита целиком**:
* структуры файлов и директорий (хеша объекта `tree`);
* хеша родительского коммита;
* имени, email и времени создания;
* текста сообщения коммита.

Благодаря этому алгоритму невозможно незаметно изменить ни один байт в старом коммите, его дате или истории — при малейшем изменении полностью изменится его хеш, а вслед за ним и хеши всех последующих дочерних коммитов.

```bash
# Посмотреть полный 40-символьный SHA-1 хеш последнего коммита
git rev-parse HEAD
```

## 3. Как можно просмотреть историю коммитов и их хэши в Git?

Для просмотра истории изменений в Git используется команда **`git log`**. Без флагов она выводит подробный список коммитов текущей ветки в обратном хронологическом порядке (от новых к старым) с полными 40-символьными хешами, автором, датой и сообщением.

На практике для удобства чаще используют комбинации флагов:

```bash
# Стандартный подробный вывод истории
git log

# Компактный вывод: короткий (7-символьный) хеш и заголовок коммита в одну строку
git log --oneline

# Визуальный граф веток и слияний по всем веткам репозитория
git log --oneline --graph --all

# Показать последние 5 коммитов вместе с построчными изменениями (diff)
git log -n 5 -p
```

## 4. Что такое ветка в Git и как она отличается от основной ветки (master)?

**Ветка (branch) в Git** — это не копия папки с проектом, а всего лишь **легковесный перемещаемый указатель (файл размером 41 байт)**, который содержит 40-символьный SHA-1 хеш конкретного коммита и символ переноса строки. Когда вы делаете новый коммит, указатель текущей ветки автоматически сдвигается вперед на этот новый коммит.

**Отличие от основной ветки (`master` или `main`):**
* **С технической точки зрения** разницы нет никакой — `master` (`main`) является точно таким же указателем на коммит, как и любая ветка `develop` или `feature/new-site`.
* **С организационной точки зрения** основная ветка (`master`/`main`) считается эталонной: в ней хранится стабильный, протестированный код, готовый к развертыванию в продакшн. Все остальные ветки создаются для изоляции разработки новых функций или исправления багов, чтобы не сломать стабильную версию до завершения работы.

```bash
# Убедиться, что ветка — это просто текстовый файл с хешем коммита внутри
cat .git/refs/heads/develop
```

## 5. Как работает файл .gitignore в Git и для чего он используется?

**`.gitignore`** — это служебный текстовый файл, который указывает Git, какие файлы и директории в рабочей области не нужно отслеживать и добавлять в репозиторий.

**Как он работает:**
Перед тем как показать файлы в `git status` или добавить их по команде `git add .`, Git сверяет пути неотслеживаемых файлов со списком шаблонов в `.gitignore`. Если путь совпадает с правилом, Git полностью игнорирует этот файл.

**Для чего используется:**
* Исключение временных файлов, кеша и логов (`tmp/`, `*.log`, `.cache/`).
* Исключение тяжелых директорий с зависимостями и артефактами сборки (`node_modules/`, `venv/`, `dist/`, `build/`).
* Защита конфиденциальных данных — паролей, токенов, ключей API и локальных конфигураций окружения (`.env`, `secrets.json`).
* Исключение системных файлов ОС и настроек локальных IDE (`.DS_Store`, `Thumbs.db`, `.idea/`, `.vscode/`).

> **Важно:** `.gitignore` действует только на **неотслеживаемые (untracked)** файлы. Если файл уже был закоммичен ранее, добавление его в `.gitignore` не остановит отслеживание — сначала его нужно удалить из индекса командой `git rm --cached <файл>`.

```bash
# Проверить, игнорируется ли файл и какое именно правило из .gitignore сработало
git check-ignore -v tmp/test.txt
```

## 6. Как работает файл .gitkeep в Git и для чего он используется?

Git отслеживает **содержимое файлов**, а не сами директории. Если создать пустую папку без единого файла внутри, Git её просто не увидит и не позволит добавить в коммит.

**`.gitkeep`** — это не встроенная функция Git, а **общепринятое среди разработчиков соглашение**. Чтобы сохранить в структуре репозитория пустую папку (например, `logs/`, `uploads/` или `tmp/`, в которую приложение при запуске будет складывать файлы), внутрь неё кладут пустой файл с именем `.gitkeep`. Так как папка перестаёт быть пустой, Git фиксирует её в истории коммитов.

```bash
# Создать пустую директорию logs и зафиксировать её в репозитории с помощью .gitkeep
mkdir -p logs
touch logs/.gitkeep
git add logs/.gitkeep
git commit -m "Keep empty logs directory in repository"
```

## 7. Как правильно настроить .gitignore для исключения определенных файлов или папок из репозитория?

Файл `.gitignore` обычно размещают в корне репозитория и коммитят, чтобы правила действовали для всей команды. Каждое правило пишется с новой строки с использованием шаблонов (glob-паттернов).

**Основные правила синтаксиса `.gitignore`:**

* **Исключение конкретной папки и всего её содержимого** (обязательно ставится `/` в конце):
  ```gitignore
  tmp/
  logs/
  ```
* **Исключение всех файлов с определенным расширением:**
  ```gitignore
  *.log
  *.tmp
  *.swp
  ```
* **Исключение конкретного файла в любом месте или только в корне:**
  ```gitignore
  .env          # игнорировать все файлы .env во всех папках
  /config.local # игнорировать config.local только в корне репозитория
  ```
* **Исключение из правила (инверсия с помощью `!`):**
  ```gitignore
  # Игнорировать всё содержимое папки tmp/, но оставить файл .gitkeep
  tmp/*
  !tmp/.gitkeep
  ```
* **Комментарии** начинаются с символа `#`:
  ```gitignore
  # Временные файлы и кеш
  tmp/
  ```

```bash
# Пример быстрого создания .gitignore с базовыми правилами
cat << 'EOF' > .gitignore
# Временные директории
tmp/
cache/

# Логи и переменные окружения
*.log
.env
EOF
```
