# Контрольные вопросы по теме: Git Flow и стратегии ветвления

## 1. Что такое git flow и какой подход к организации работы с ветками он предлагает?
**Git Flow** — это строгая модель ветвления в Git, предложенная Винсентом Дриссеном (Vincent Driessen) в 2010 году. Она определяет четкую структуру веток и правила их взаимодействия для проектов с запланированными релизами. Подход строится на разделении кода по стадиям жизненного цикла: стабильный продакшн-код хранится отдельно от текущей разработки, новых фич, подготовки релизов и срочных исправлений.

```bash
# Инициализация стандартной структуры веток Git Flow
git branch -M master
git checkout -b develop
```

## 2. Какие основные ветки используются в git flow (например, master, develop, …)?
В модели Git Flow выделяют **две основные (вечные) ветки** и **три типа вспомогательных (временных) веток**:
1. **`master` (или `main`)** — основная ветка, содержащая исключительно стабильный код, готовый к продакшну. Каждый коммит в ней обычно помечается тегом версии.
2. **`develop`** — основная ветка разработки, в которой собираются все завершенные функции для следующего релиза.
3. **`feature/*`** — временные ветки для разработки нового функционала (создаются от `develop` и вливаются обратно в `develop`).
4. **`release/*`** — временные ветки для финального тестирования, исправления мелких багов и подготовки метаданных перед выпуском релиза (создаются от `develop`, вливаются в `master` и `develop`).
5. **`hotfix/*`** — временные ветки для экстренного исправления критических ошибок в продакшне (создаются напрямую от `master`, вливаются в `master` и `develop`).

## 3. Какие правила и рекомендации определяют работу с каждой из этих веток?
- **`master`**: прямой push запрещен; изменения попадают сюда только через слияние из `release/*` или `hotfix/*`.
- **`develop`**: прямой push не рекомендуется; ветка должна оставаться в рабочем состоянии и обновляться через Pull/Merge Request'ы.
- **`feature/*`**: создается от `develop`, именуется по смыслу задачи (например, `feature/auth`), после завершения работы вливается только в `develop` и удаляется.
- **`release/*`**: создается от `develop` (например, `release/1.1`), новые фичи сюда уже не добавляются — только багфиксы. После проверки вливается в `master` (с установкой тега) и обратно в `develop`, затем удаляется.
- **`hotfix/*`**: создается от `master` (например, `hotfix/login-crash`), после исправления вливается в `master` (с новым патч-тегом) и в `develop`, затем удаляется.

## 4. Какие команды Git используются для создания, переключения и слияния веток в рамках git flow?
Для работы по модели Git Flow используются стандартные команды управления ветками, слиянием и тегами:

```bash
# Создание и переключение на ветку feature от develop
git checkout develop
git checkout -b feature/new-login

# Слияние ветки feature в develop с сохранением истории коммитов (--no-ff)
git checkout develop
git merge --no-ff feature/new-login
git branch -d feature/new-login

# Фиксация релиза в master с помощью аннотированного тега
git checkout master
git merge --no-ff release/1.1
git tag -a release_1.1 -m "Release 1.1"
```

## 5. Какие преимущества и недостатки имеет использование git flow?
**Преимущества:**
- Прозрачная и строгая структура, понятная большим командам разработчиков.
- Изоляция разработки новых функций от стабильной продакшн-версии.
- Удобная поддержка нескольких версий продукта одновременно и понятный процесс выпуска срочных хотфиксов.

**Недостатки:**
- Избыточная сложность для небольших команд и простых проектов.
- Долгоживущие ветки могут приводить к сложным конфликтам слияния (merge hell).
- Плохо подходит для непрерывной доставки (Continuous Delivery / Deployment), где релизы выкатываются в продакшн по несколько раз в день.

## 6. Какие инструменты или расширения Git могут облегчить использование git flow (например, git-flow-avh)?
Основным инструментом является расширение **`git-flow-avh`** — набор скриптов-оберток над стандартными командами Git, автоматизирующий создание, переключение, слияние и удаление веток по правилам Git Flow. Также встроенная визуальная поддержка Git Flow есть в графических клиентах (**Sourcetree**, **GitKraken**, **Fork**) и IDE (**IntelliJ IDEA**, **VS Code** через плагины).

```bash
# Пример работы с расширением git-flow-avh
git flow init                          # Инициализация структуры веток
git flow feature start user-profile    # Создает feature/user-profile от develop
git flow feature finish user-profile   # Вливает в develop и удаляет ветку фичи
git flow release start 1.1             # Создает ветку release/1.1 от develop
git flow release finish 1.1            # Вливает в master и develop, ставит тег 1.1
```

## 7. Обсуждение других подходов и стратегий работы с ветками в Git, таких как GitHub Flow, GitLab Flow, OneFlow и т.д.
- **GitHub Flow**: максимально упрощенная модель с одной вечной веткой `main`. Для любой задачи (фичи или бага) создается короткоживущая ветка от `main`, после проверки через Pull Request она вливается обратно в `main` и сразу деплоится в продакшн.
- **GitLab Flow**: гибрид GitHub Flow и Git Flow. Добавляет к `main` ветки окружений (например, `staging`, `production`) или релизные ветки, позволяя контролировать последовательное продвижение кода по стендам.
- **OneFlow**: упрощенная альтернатива Git Flow без вечной ветки `develop`. Вся разработка и релизы ведутся вокруг одной главной ветки `master`, что делает историю коммитов более линейной.
- **Trunk-Based Development (TBD)**: разработка ведется напрямую в основную ветку (`trunk`/`main`) мелкими частыми коммитами или через очень короткие ветки (живут не более 1–2 дней) с использованием фича-флагов (Feature Flags).

## 8. Как выбрать подход, наиболее подходящий для конкретного проекта или команды?
Выбор стратегии зависит от цикла релизов, архитектуры продукта и зрелости автоматизации (CI/CD):
- **Git Flow** выбирают для крупных проектов с жестким графиком релизов, версионированием (десктоп-приложения, мобильные приложения в сторах, коробочные решения) и необходимостью поддерживать старые версии.
- **GitHub Flow / Trunk-Based Development** выбирают для веб-сервисов и микросервисов с непрерывным развертыванием (CI/CD), где изменения попадают в продакшн сразу после прохождения автотестов.
- **GitLab Flow** выбирают, когда нужен баланс между простотой ветвления и строгим контролем деплоя на несколько тестовых сред (`dev` -> `stage` -> `prod`).
