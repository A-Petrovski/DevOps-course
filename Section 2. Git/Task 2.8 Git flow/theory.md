## Введение

Работа с ветками — по-настоящему мощный инструмент системы контроля версий Git. Единственная проблема — создавать их можно сколько угодно и именовать как угодно. Вполне возможно запутаться через некоторое время. Особенно, если ты работаешь в большой команде.

С целью решения этой проблемы был предложен набор правил для работы с ветками в git-репозиториях. Название его — **git flow**. Он не является стандартом и не обязателен к использованию. Также он не высечен в камне, так что может меняться от команды к команде, но общий подход сохраняется. Git flow на данный момент используется большинством команд во всем мире, так что с ним точно необходимо будет познакомиться поближе.

## Чекпоинты

- Создай новый локальный репозиторий. Создай две ветки: `master`/`develop`. Добавь пару коммитов в `master`. Перенеси изменения в ветку `develop`. Добавь один коммит в ветку `develop`. Создай из ветки `develop` новую ветку `feature`. Создай по одному коммиту в ветках `develop` и `feature`. Загрузи все изменения на GitLab.
- Создай pull request из `feature` в `develop` и замержи его. Создай pull request из `develop` в `master` и замержи его. Пометь замерженный коммит в ветке `master` тегом `release_1.1` и загрузи в свой репозиторий.

## Темы на изучение

- Что такое git flow и какой подход к организации работы с ветками он предлагает?
- Какие основные ветки используются в git flow (например, `master`, `develop`, …)?
- Какие правила и рекомендации определяют работу с каждой из этих веток?
- Какие команды Git используются для создания, переключения и слияния веток в рамках git flow?
- Какие преимущества и недостатки имеет использование git flow?
- Какие инструменты или расширения Git могут облегчить использование git flow (например, `git-flow-avh`)?
- Обсуждение других подходов и стратегий работы с ветками в Git, таких как GitHub Flow, GitLab Flow, OneFlow и т.д.
- Как выбрать подход, наиболее подходящий для конкретного проекта или команды?
