# Контрольные вопросы: Task 2.4 — Rebase, Squash и Cherry-pick

### 1. Что такое `rebase` в системе контроля версий Git и как он отличается от `merge`?
`git rebase` — это команда, которая переносит последовательность коммитов из одной ветки поверх последнего коммита другой ветки, создавая новые коммиты с новыми хешами.
* **Отличие от `merge`:** `merge` связывает две ветки через специальный коммит слияния (merge commit) с двумя родителями, сохраняя всю историю ветвлений. `rebase` переписывает историю так, как будто изменения создавались последовательно в целевой ветке, формируя ровную линейную линию коммитов без лишних коммитов слияния.

```bash
git checkout feature
git rebase main
```

---

### 2. Какие преимущества и недостатки `rebase` по сравнению с `merge`?
* **Преимущества:**
  * Чистая, линейная история проекта без множества технических коммитов слияния (`Merge branch...`).
  * Упрощается чтение логов (`git log`) и поиск ошибок с помощью `git bisect`.
* **Недостатки:**
  * Переписывает историю и меняет SHA-1 хеши коммитов.
  * При работе в общей ветке с другими разработчиками вызывает рассинхронизацию истории и требует принудительной отправки (`git push --force`), что может затереть чужую работу.
  * При множестве конфликтов приходится разрешать их пошагово для каждого переносимого коммита отдельно, а не один раз, как при `merge`.

---

### 3. Какие ситуации могут потребовать применения `rebase`, а не `merge`?
* **Актуализация локальной ветки перед созданием Pull/Merge Request:** когда в `main` или `develop` появились новые изменения, а вы хотите подтянуть их в свою локальную ветку `feature`, не засоряя её промежуточными коммитами слияния.
* **Наведение порядка в локальных коммитах перед публикацией:** использование интерактивного ребейза (`git rebase -i`), чтобы объединить мелкие исправления или поправить сообщения коммитов перед отправкой на сервер.

```bash
git fetch origin
git rebase origin/develop
```

---

### 4. Что такое `squash` коммитов и как он позволяет объединять несколько коммитов в один?
`squash` — это механизм объединения нескольких последовательных коммитов в один общий коммит с помощью интерактивного ребейза (`git rebase -i`). При выполнении в открывшемся списке коммитов для первого (базового) оставляют команду `pick`, а для последующих указывают `squash` (сохраняет и объединяет сообщения всех коммитов) или `fixup` (вливает изменения в первый коммит, удаляя сообщения остальных).

```bash
git rebase -i HEAD~3
```

---

### 5. Какие преимущества и рекомендации связаны с использованием `squash` для улучшения истории коммитов?
* **Преимущества:**
  * Избавляет историю от мусорных и промежуточных коммитов (например, `"fix typo"`, `"wip"`, `"fix #2"`).
  * Одна логическая задача или фича представлена в главной ветке ровно одним понятным коммитом, который легко откатить при необходимости (`git revert`).
* **Рекомендации:**
  * Делайте `squash` только для локальных веток до их вливания в общую ветку (`main`/`develop`).
  * Не применяйте `squash` к коммитам, которые уже были опубликованы и на которых базируются ветки других участников команды.

---

### 6. Что такое `cherry-pick` в Git и для чего он используется?
`git cherry-pick` — это команда, которая копирует изменения из одного конкретного коммита (или нескольких выбранных) из любой ветки и применяет их в виде нового коммита в текущей активной ветке. Она используется, когда нужно точечно перенести отдельное исправление (hotfix) или конкретную функцию без слияния всей ветки целиком.

```bash
git checkout master
git cherry-pick <хеш_коммита>
```

---

### 7. Как выбрать нужные коммиты для `cherry-pick` и как обрабатывать возможные конфликты?
* **Выбор коммитов:** с помощью `git log --all --oneline` находят нужный коммит и копируют его хеш. Можно указать один хеш, несколько хешей через пробел или диапазон (`A..B`).
* **Обработка конфликтов:** если строки в целевой ветке отличаются от контекста переносимого коммита, Git приостановит операцию. Нужно вручную исправить конфликтные участки в файлах, добавить их в индекс (`git add`) и продолжить процесс.

```bash
git log --all --oneline
git cherry-pick e4a9855
# После исправления конфликта в файле:
git add main.go
git cherry-pick --continue
```

---

### 8. Какие рекомендации и ограничения существуют при использовании `cherry-pick` в Git?
* **Ограничения и риски:**
  * `cherry-pick` создает **дубликат** коммита с новым хешем. Если позже попытаться сделать полный `merge` ветки-источника в целевую ветку, наличие одинаковых изменений в разных коммитах может привести к лишним конфликтам слияния.
  * Нельзя сделать `cherry-pick` коммита слияния (merge commit) без явного указания родительской ветки через флаг `-m 1`.
* **Рекомендации:**
  * Используйте `cherry-pick` точечно (например, для переноса срочного бага из `develop` в `release`/`master`), а не как замену стандартному процессу слияния веток.
  * При переносе коммита из публичной ветки полезно добавлять флаг `-x`, чтобы Git автоматически дописал в сообщение ссылку на оригинальный хеш коммита (`(cherry picked from commit ...)`).

```bash
git cherry-pick -x e4a9855
```
