## Чекпоинт 1: Перебазирование веток (`git-rebase`)

**Задача:** Клонировать репозиторий `git-rebase`. Переместить коммиты из ветки `feature` в ветку `develop` с помощью `rebase`. Переместить коммиты из ветки `develop` в ветку `master` с помощью `rebase`. Создать репозиторий в своем аккаунте и загрузить в него получившийся локальный репозиторий.

```bash
# 1. Клонирование репозитория и просмотр всех веток
git clone <ссылка_на_репозиторий_git-rebase>
cd git-rebase
git branch -a

# 2. Перенос коммитов из ветки feature на базу develop
git checkout feature
git rebase develop
git checkout develop
git merge feature

# 3. Перенос коммитов из ветки develop на базу master
git rebase master
git checkout master
git merge develop

# 4. Привязка нового удаленного репозитория и отправка всех веток
git remote set-url origin https://github.com
git push -u origin --all
```

* **Разбор команд и флагов:**
  * `git branch -a` — отображает список всех локальных и удаленных (`remotes/origin/...`) веток.
  * `git rebase <базовая_ветка>` — переносит коммиты текущей ветки поверх указанной базовой ветки, выстраивая линейную историю.
  * `git merge <ветка>` — после ребейза выполняет быструю перемотку (`fast-forward`) указателя целевой ветки на последний перенесенный коммит.
  * `git remote set-url origin <URL>` — заменяет адрес удаленного репозитория `origin` на ссылку вашего нового репозитория.
  * `git push -u origin --all` — отправляет все локальные ветки в удаленный репозиторий и устанавливает отслеживание (`upstream`).
* **Нюансы и частые ошибки:**
  * При вводе `git remote set-url origin <URL>` не добавляйте лишних слов в конце команды (например, `gihub`), иначе Git вернет справку об ошибке синтаксиса.
  * Если при `push` через HTTPS возникает ошибка прав доступа (`403`) из-за кэша другого аккаунта, используйте Personal Access Token в URL (`https://github.com...`) или настройте отдельный SSH-алиас в `~/.ssh/config`.

**Пример использования:**
```bash
git rebase --continue
```

## Чекпоинт 2: Объединение FIX-коммитов (`git-squash`)

**Задача:** Клонировать репозиторий `git-squash`. Просмотреть историю коммитов в ветке `develop`. Объединить все `FIX`-коммиты с родительским (`Simplified sum function`) в один коммит. Создать репозиторий в своем аккаунте и загрузить в него получившийся репозиторий.

```bash
# 1. Клонирование и проверка веток и истории коммитов
git clone <ссылка_на_репозиторий_git-squash>
cd git-squash
git branch -a
git log --oneline

# 2. Интерактивный ребейз с самого первого (корневого) коммита
git rebase -i --root
```

Содержимое файла инструкций в редакторе (переименование первого коммита и вливание всех fix-коммитов без сохранения их сообщений):
```text
reword abac525 Initial commit
fixup 5e166bf first fix commit
fixup 70774aa second fix commit
fixup a60ddff third fix commit
```

```bash
# 3. Проверка лога, создание ветки develop и отправка в свой репозиторий
git log --oneline
git checkout -b develop
git remote set-url origin https://github.com
git push -u origin --all
```

* **Разбор команд и флагов:**
  * `git log --oneline` — выводит компактную историю коммитов (один коммит на строку: короткий хеш и заголовок).
  * `git rebase -i --root` — запускает интерактивный ребейз (`-i`), начиная с самого первого корневого коммита репозитория (`--root`).
  * `reword` (`r`) — инструкция в интерактивном ребейзе, позволяющая изменить сообщение выбранного коммита.
  * `fixup` (`f`) — объединяет коммит с предыдущим, отбрасывая его сообщение (в отличие от `squash`, который сохраняет текст обоих сообщений).
  * `git checkout -b develop` — создает новую ветку `develop` из текущей и сразу переключается на нее.
* **Нюансы и частые ошибки:**
  * **Отсутствие ветки `develop` в исходном репозитории:** если `git branch -a` показывает только `main`, ребейз выполняется в `main`, а ветка `develop` создается после склейки коммитов.
  * **Зависший ребейз из-за опечатки в Vim:** при переходе в режим редактирования в Vim легко случайно вписать лишний символ в хеш (например, `reword eabac525`). Git остановит процесс с ошибкой `could not parse`. Чтобы вернуть репозиторий в исходное состояние и начать заново, выполните `git rebase --abort`.

**Пример использования:**
```bash
git rebase -i HEAD~4
```

## Чекпоинт 3: Перенос коммита в целевую ветку (`git-cherry-pick`)

**Задача:** Клонировать репозиторий `git-cherry-pick`. Перенести коммит `"Formatted code"` в ветку `master`. Создать репозиторий в своем аккаунте и залить туда получившийся репозиторий.

```bash
# 1. Клонирование, поиск веток и хеша коммита "Formatted code"
git clone <ссылка_на_репозиторий_git-cherry-pick>
cd git-cherry-pick
git branch -a
git log --all --oneline

# 2. Переключение на основную ветку и перенос коммита по хешу
git checkout main
git cherry-pick e4a9855

# 3. Разрешение конфликта в main.go (после правки файла в редакторе)
git add main.go
git cherry-pick --continue

# 4. Создание ветки master, привязка репозитория и отправка
git checkout -b master
git remote set-url origin https://github.com
git push -u origin --all
```

* **Разбор команд и флагов:**
  * `git log --all --oneline` — показывает историю коммитов сразу по всем веткам репозитория.
  * `git cherry-pick <хеш>` — берет изменения из указанного коммита и применяет их как новый коммит в текущей активной ветке.
  * `git add <файл>` — помечает конфликт в файле как разрешенный и добавляет файл в индекс.
  * `git cherry-pick --continue` — завершает перенос коммита после разрешения конфликтов слияния.
* **Нюансы и частые ошибки:**
  * **Конфликт в файле `main.go`:** при возникновении конфликта откройте файл, удалите маркеры (`<<<<<<< HEAD`, `=======`, `>>>>>>>`), оставив отформатированный код, сохраните файл и выполните `git add main.go` + `git cherry-pick --continue`.
  * **Случайные символы в окне коммита Vim:** при подтверждении сообщения `Formatted code` в Vim проверьте, что в первой строке не добавилась лишняя буква `A` перед текстом (если добавилась — нажмите `Esc`, удалите символ клавишей `x`, введите `:wq` и нажмите `Enter`).

**Пример использования:**
```bash
git cherry-pick --no-commit e4a9855
```
