# Контрольные вопросы по Task 2.5

## 1. Что такое форс-пуш в Git и в каких случаях он может быть использован?

**Ответ:**
Форс-пуш (`git push --force`) — это принудительная отправка локальной ветки на удаленный сервер с полной перезаписью удаленной истории коммитов. По умолчанию Git разрешает отправку изменений только в том случае, если история на сервере является прямым предком вашей локальной истории (режим `fast-forward`). Флаг `--force` отключает эту проверку.

**Случаи использования:**
* После интерактивного перебазирования (`git rebase -i`), объединения коммитов (`squash`) или изменения последнего коммита (`git commit --amend`) в **собственной личной ветке**, с которой не работают другие разработчики.
* При необходимости откатить ошибочно отправленные коммиты на сервере после локального сброса истории (`git reset --hard`).

**Пример команды:**
```bash
git push --force-with-lease origin feature/login
```

## 2. Какие недостатки и риски связаны с применением форс-пуша?

**Ответ:**
Главный риск заключается в необратимой потере коммитов коллег и нарушении синхронизации репозиториев у всей команды.

**Основные недостатки и риски:**
* **Перезапись чужой работы:** Если другой разработчик успел отправить свои коммиты в ту же ветку на сервер до вашего форс-пуша, они будут удалены из истории ветки на сервере.
* **Конфликты истории у команды:** У коллег, которые уже скачали старую версию ветки, при попытке выполнить `git pull` или `git push` возникнут сложные конфликты из-за расхождения хэшей коммитов.
* **Потеря прозрачности:** Изменение истории в общих ветках (`main`, `master`, `develop`) уничтожает хронологию разработки и затрудняет поиск причин багов.

**Пример безопасной проверки перед отправкой:**
```bash
git fetch origin
git log HEAD..origin/feature
```

## 3. Что такое пул-реквест (pull request)?

**Ответ:**
Пул-реквест (Pull Request в GitHub/Bitbucket или Merge Request в GitLab) — это механизм в системах хостинга Git-репозиториев, который позволяет разработчику уведомить команду о готовности изменений в его ветке и запросить их интеграцию (слияние) в другую целевую ветку (например, из `feature` в `develop`). Это не встроенная команда самого Git, а инструмент совместной работы поверх Git.

---

## 4. Как создать пул-реквест для интеграции изменений из одной ветки в другую?

**Ответ:**
Создание пул-реквеста выполняется в три этапа: отправка локальной ветки с коммитами на сервер, выбор исходной (`source`) и целевой (`target`) веток и подтверждение создания запроса. Сделать это можно через веб-интерфейс, CLI-утилиту или опции при `git push`.

**Пример создания через веб-интерфейс:**
1. Запушить ветку на сервер: `git push -u origin feature`.
2. Открыть репозиторий в браузере и перейти во вкладку **Pull requests** (или **Merge requests**).
3. Нажать кнопку создания нового запроса, выбрать **Source branch** (`feature`) и **Target branch** (`develop`), заполнить описание и нажать **Create**.

**Пример создания прямо из терминала (для GitLab):**
```bash
git push -o merge_request.create -o merge_request.target=develop origin feature
```

## 5. Какие преимущества и возможности предоставляют пул-реквесты для командной работы и обзора кода?

**Ответ:**
Пул-реквесты служат барьером качества перед попаданием нового кода в основную кодовую базу проекта.

**Ключевые преимущества:**
* **Code Review (ревью кода):** Коллеги могут просматривать изменения построчно (`diff`), оставлять комментарии к конкретным строкам, предлагать правки и одобрять (`Approve`) или отклонять изменения.
* **Автоматические проверки (CI/CD):** При создании или обновлении PR автоматически запускаются линтеры, сборка проекта и автотесты; слияние блокируется, если тесты упали.
* **Контроль конфликтов:** Система заранее проверяет наличие конфликтов слияния с целевой веткой и подсвечивает их до выполнения `merge`.
* **История обсуждений:** Все дискуссии, причины архитектурных решений и результаты проверок сохраняются в привязке к конкретным коммитам.

## 6. Что такое форк репозитория и как он используется в системе контроля версий Git?

**Ответ:**
Форк (Fork) — это полная независимая копия чужого или основного репозитория, созданная в вашем личном аккаунте или пространстве имен на платформе хостинга (GitHub, GitLab). 

**Как используется:**
* Позволяет вносить любые изменения, создавать ветки и экспериментировать с кодом, не имея прямых прав на запись (`Write` / `Push`) в исходный репозиторий.
* Является стандартом разработки в Open Source проектах и при строгом разграничении прав доступа в крупных компаниях: разработчик работает в своем форке, а затем предлагает свои изменения в основной проект через Pull Request.

## 7. Как взаимодействовать с исходным репозиторием через форк, включая создание пул-реквестов и получение обновлений?

**Ответ:**
Для полноценной работы в локальном клоне вашего форка настраиваются два удаленных репозитория: `origin` (указывает на ваш форк) и `upstream` (указывает на исходный оригинальный репозиторий).

**Алгоритм взаимодействия:**
1. **Подключение исходного репозитория:**
   ```bash
   git clone <URL_вашего_форка>
   git remote add upstream <URL_исходного_репозитория>
   ```
2. **Получение обновлений из оригинала (синхронизация форка):**
   ```bash
   git checkout main
   git fetch upstream
   git merge upstream/main
   git push origin main
   ```
3. **Создание Pull Request в основной проект:**
   * Создаете ветку в форке (`git checkout -b fix-bug`), делаете коммит и отправляете в свой форк (`git push origin fix-bug`).
   * В веб-интерфейсе создаете Pull Request, указав в качестве **Source** ветку `fix-bug` из **вашего форка**, а в качестве **Target** — ветку `main` (или `develop`) **исходного репозитория** (`upstream`).
