# Контрольные вопросы: Task 2.3 Мерж и конфликты

## 1. Что такое мерж (объединение) в контексте системы контроля версий Git?

**Ответ:**  
Мерж (`git merge`) — это операция объединения истории изменений из одной ветки (источника) в другую (целевую ветку). В результате создаётся либо перемотка указателя ветки вперёд (*Fast-Forward*, если целевая ветка не расходилась с источником), либо специальный *merge-коммит* с двумя родителями, который сводит обе линии разработки в одну общую историю.

**Пример:**
```bash
git checkout main
git merge feature/login
```

---

## 2. Как Git автоматически объединяет изменения при мерже, если они не конфликтуют?

**Ответ:**  
Git использует алгоритм трёхстороннего слияния (*3-way merge*). Он находит общего предка двух веток (базовый коммит) и сравнивает с ним состояния обеих веток. Если изменения затронули разные файлы или разные, непересекающиеся участки (строки) одного файла, Git автоматически объединяет оба набора правок в результирующем файле и создаёт merge-коммит.

**Пример:**
```bash
# Просмотр общего предка двух веток, от которого Git считает изменения
git merge-base master develop
```

## 3. Что происходит, когда Git обнаруживает конфликты при мерже и как их решить вручную?

**Ответ:**  
Когда в обеих ветках изменены одни и те же строки файла (или файл изменён в одной ветке и удалён в другой), Git приостанавливает слияние, переводит репозиторий в состояние `MERGING` и записывает в спорные файлы специальные маркеры конфликта:
* `<<<<<<< HEAD` — начало блока изменений из текущей ветки.
* `=======` — разделитель между версиями.
* `>>>>>>> <branch>` — конец блока изменений из вливаемой ветки.

**Алгоритм ручного решения:**
1. Открыть конфликтный файл в редакторе (например, в VS Code).
2. Выбрать нужный вариант кода или объединить оба, полностью удалив строки с маркерами `<<<<<<<`, `=======`, `>>>>>>>`.
3. Сохранить файл, добавить его в индекс (`git add`) и завершить слияние коммитом (`git commit`).

**Пример:**
```bash
git add conflicted_file.txt
git commit -m "Resolve merge conflict in conflicted_file.txt"
```

## 4. Какие инструменты и команды Git помогают разрешать конфликты при мерже?

**Ответ:**  
* `git status` — показывает список файлов со статусом `both modified` (неразрешённые конфликты).
* `git diff` — отображает разницу и блоки конфликтов прямо в терминале.
* `git log --merge -p` — выводит только те коммиты из обеих веток, которые привели к конфликту.
* `git checkout --ours <файл>` / `git checkout --theirs <файл>` — быстрое принятие целиком версии текущей (`ours`) или вливаемой (`theirs`) ветки для конкретного файла.
* `git mergetool` — запуск внешнего визуального инструмента слияния (например, VS Code, Meld, KDiff3, Vimdiff).
* `git merge --abort` — полная отмена процесса слияния и возврат ветки к состоянию до запуска `git merge`.

**Пример:**
```bash
# Настройка VS Code в качестве стандартного mergetool и его запуск
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge REMOTE LOCAL BASE MERGED'
git mergetool
```

## 5. Какие факторы следует учитывать при выборе ветки, которую нужно слить с основной веткой?

**Ответ:**  
* **Завершённость и тестирование:** функциональность должна быть полностью реализована, протестирована и не содержать сломанного кода или заглушек.
* **Актуальность относительно основной ветки:** в ветку-источник предварительно должны быть подтянуты свежие изменения из основной ветки, чтобы все конфликты решались в рабочей ветке, а не в `main`/`master`.
* **Назначение ветки и правила Git Flow:** в `main`/`master` вливаются только стабильные релизные ветки или `hotfix`, а промежуточные `feature`-ветки сначала сливаются в `develop`.
* **Прохождение CI/CD и Code Review:** успешное прохождение автоматических тестов, линтеров и одобрение кода другими разработчиками.

**Пример:**
```bash
# Предварительное обновление рабочей ветки перед её вливанием в основную
git checkout feature/auth
git merge develop
```

## 6. Какие лучшие практики и советы по мержу можно применить для избегания проблем и сохранения стабильности проекта?

**Ответ:**  
* **Короткоживущие ветки и частые слияния:** разбивайте крупные задачи на небольшие части и вливайте их чаще, чтобы не копить масштабные расхождения кода.
* **Регулярная синхронизация:** регулярно подтягивайте изменения из `develop`/`main` в свою рабочую ветку по мере работы.
* **Атомарные коммиты и единый стиль кода:** используйте автоформатирование (линтеры, Prettier) в проекте, чтобы конфликты не возникали из-за разных отступов, кавычек или переносов строк.
* **Проверка перед коммитом слияния:** после разрешения конфликтов обязательно запускайте сборку и тесты проекта до выполнения финального `git commit`.
* **Защита основных веток:** запрещайте прямой пуш в `main` и `develop` на уровне GitLab/GitHub, разрешая изменения только через Pull/Merge Request.

**Пример:**
```bash
# Проверка статуса и диффа перед финальным коммитом после решения конфликтов
git diff --check
git status
```
