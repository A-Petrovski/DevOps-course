### Чекпоинт 1: Объединение develop с master из предыдущего задания

Переходим в директорию репозитория из предыдущего задания, переключаемся на ветку `develop`, вливаем в неё `master` и отправляем результат на сервер.

```bash
cd /path/to/previous-repo
git checkout develop
git pull origin develop
git merge master
git push origin develop
```

**Разбор команд и параметров:**
* `git checkout develop` — переключение рабочей директории на целевую ветку `develop`.
* `git pull origin develop` — получение и слияние актуальных изменений из удалённой ветки `develop` перед началом работы.
* `git merge master` — вливание изменений из ветки `master` в текущую ветку (`develop`).
* `git push origin develop` — отправка локальных коммитов ветки `develop` в удалённый репозиторий `origin`.

**Нюансы и ошибки:**
* Важно убедиться, что ты находишься именно в ветке `develop` (`git status` или `git branch`), так как команда `git merge <ветка>` всегда вливает указанную ветку в **текущую**.

**Пример использования:** `git switch develop && git merge main`

### Чекпоинт 2: Клонирование и мерж feature в develop

Клонируем репозиторий, забираем все удалённые ветки, проверяем время последних коммитов в `develop` и `feature` по логам, выполняем слияние и разрешаем конфликты в пользу более свежего изменения.

```bash
git clone <URL_репозитория>
cd <имя_папки_репозитория>
git fetch --all
git checkout develop
git checkout -b feature origin/feature
git checkout develop
git log -n 3 --pretty=format:"%h | %ad | %an | %s" --date=iso develop
git log -n 3 --pretty=format:"%h | %ad | %an | %s" --date=iso feature
git merge feature
```

После появления сообщения `CONFLICT` открываем проблемные файлы в VS Code:
1. Сравниваем даты коммитов из вывода `git log` выше.
2. В редакторе VS Code над блоком конфликта нажимаем **Accept Current Change** (если свежее изменение в `develop`) или **Accept Incoming Change** (если свежее изменение в `feature`).
3. Сохраняем файлы (`Ctrl + S`) и завершаем коммит слияния:

```bash
git add .
git commit -m "Merge branch 'feature' into develop"
```

**Разбор команд и параметров:**
* `git clone <URL>` — создание полной локальной копии удалённого репозитория.
* `git fetch --all` — загрузка информации обо всех ветках и тегах из всех подключённых удалённых репозиториев без слияния.
* `git checkout -b feature origin/feature` — создание локальной ветки `feature`, отслеживающей удалённую ветку `origin/feature`.
* `git log -n 3` — вывод последних 3 коммитов в указанной ветке.
* `--pretty=format:"%h | %ad | %an | %s"` — форматирование вывода лога: короткий хеш (`%h`), дата автора (`%ad`), имя автора (`%an`), сообщение коммита (`%s`).
* `--date=iso` — отображение даты в строгом формате ISO (`ГГГГ-ММ-ДД ЧЧ:ММ:СС`), что исключает ошибки при сравнении времени.
* `git add .` — добавление всех разрешённых файлов в индекс (staging area) для снятия статуса конфликта.

**Нюансы и ошибки:**
* При клонировании Git по умолчанию создаёт локально только основную ветку (`master` или `main`). Чтобы `git log` и `git merge` видели `develop` и `feature` локально, их нужно предварительно создать через `git checkout -b <ветка> origin/<ветка>` или обращаться к ним как `origin/feature`.
* Если в процессе выбора кнопок в VS Code допущена ошибка, отменить слияние и вернуть исходное состояние можно командой `git merge --abort`.

**Пример использования:** `git log -n 5 --oneline --graph --all --decorate`

### Чекпоинт 3: Мерж develop в master с учётом времени коммитов

Переключаемся на `master`, проверяем историю коммитов обеих веток (исключая merge-коммит из шага 2), запускаем мерж и оставляем изменения из коммита с более поздней датой.

```bash
git checkout master
git log --no-merges -n 3 --pretty=format:"%h | %ad | %s" --date=iso develop
git log --no-merges -n 3 --pretty=format:"%h | %ad | %s" --date=iso master
git merge develop
```

Разрешаем конфликты в VS Code, ориентируясь на даты обычных (не-merge) коммитов из вывода выше, после чего фиксируем результат:

```bash
git add .
git commit -m "Merge branch 'develop' into master"
```

**Разбор команд и параметров:**
* `--no-merges` — ключевой флаг для этого задания; скрывает из вывода `git log` все коммиты слияния (включая merge-коммит, созданный на предыдущем шаге в `develop`), позволяя сразу увидеть реальные даты последних правок кода.
* `git merge develop` — слияние ветки `develop` в текущую ветку `master`.

**Нюансы и ошибки:**
* Без флага `--no-merges` самым свежим коммитом в `develop` всегда будет сам факт слияния из Шага 2, что нарушит условие задания. Обязательно сверяйте дату именно исходного коммита, в котором менялась спорная строка.
* Узнать, какой именно коммит изменил конкретную строку в файле, можно дополнительно через `git log -p -n 2 <имя_файла>`.

**Пример использования:** `git log --no-merges -p -n 2 index.html`

### Чекпоинт 4: Создание репозитория в GitLab и загрузка всех изменений

После создания пустого репозитория `devops-task-merge` в веб-интерфейсе GitLab (без инициализации `README.md`), привязываем его как новый remote и пушим все ветки.

```bash
git remote -v
git remote add gitlab https://gitlab.com<твой_username>/devops-task-merge.git
git push -u gitlab --all
git push gitlab --tags
```

**Разбор команд и параметров:**
* `git remote -v` — просмотр списка текущих удалённых репозиториев и их URL.
* `git remote add gitlab <URL>` — добавление нового удалённого репозитория с псевдонимом `gitlab` (чтобы не перезаписывать существующий `origin`).
* `git push -u gitlab --all` — отправка всех локальных веток (`master`, `develop`, `feature`) в репозиторий `gitlab` с привязкой upstream (`-u`).
* `git push gitlab --tags` — отправка всех локальных тегов (если они есть в репозитории).

**Нюансы и ошибки:**
* Если при создании проекта в GitLab оставить галочку **Initialize repository with a README**, в удалённом репозитории создастся начальный коммит. При попытке сделать `git push` возникнет ошибка `rejected (fetch first)`. Репозиторий нужно создавать полностью пустым.
* Если требуется заменить старый `origin` на новый репозиторий GitLab, вместо добавления нового remote используется команда `git remote set-url origin <URL>`.

**Пример использования:** `git remote set-url origin git@gitlab.com:user/devops-task-merge.git && git push -u origin --all`
